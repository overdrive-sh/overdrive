### LEDGER — what P6 ANSWERED here, and what it did NOT
############################################################################

ANSWERED (arch-independent; the evidence is above):
  A1 --memory shared=on x RLIMIT_FSIZE. shared=on backs guest RAM with a
     memfd (/memfd:ch_ram, mapped rw-s, held as an open fd), and a memfd
     is a FILE for RLIMIT_FSIZE. CH dies with SIGXFSZ (exit 153) unless
     the ceiling covers GUEST RAM. Threshold tracks --memory size, not the
     disk image: 256M guest RAM fails at 192 MiB and passes at 384 MiB.
     => the P5 rlimit must be max(rootfs image, guest RAM) once volumes
        are attached. increment-c sized it off the rootfs alone.
  A2 CH v46 Landlock: --fs socket= IS auto-derived (boot reached the guest
     kernel with the vhost-user socket dir in NO rule, as a SIBLING of the
     granted dir). Contrast --vsock, which is NOT (increment-c).
  A3 [D8e] holds: the volume SOURCE directory was granted in no trial and
     CH created the fs device anyway. Volumes do NOT widen [D7]'s
     hypervisor confinement. US-VM-8's non-widening AC stands.
  A4 virtiofsd 1.13.2 --sandbox=namespace is the DEFAULT and is genuinely
     in effect: mnt and net namespace inodes differ from the shell's.
     pid and user do NOT differ. Say 'mount+net namespace', not 'full
     namespace sandbox' — that precision is exactly what [D8d] exists for.
  A5 --socket-group=<vmm user> makes the vhost-user socket srwxrwx--- root:
     <group>, which is how a uid-dropped CH connects without a chmod 0666.
  A6 virtiofsd lives at /usr/libexec/virtiofsd and is NOT on PATH.
  A7 shared=on reclassifies the VMM's RSS rather than obviously inflating
     it: at the same early lifecycle point, shared=on gave VmRSS 86432 kB
     (RssShmem 83224 / RssAnon 316) and private gave VmRSS 93320 kB
     (RssAnon 90428 / RssShmem 0). Same order of magnitude, different
     accounting bucket. NOTE this is an EARLY-BOOT sample, not the
     controlled post-beacon sample the probe was built to take.

NOT ANSWERED — and NOT refuted. Every one of these needs a guest that
boots under shared=on, which no VMM can do on this host:
  U1 guest<->host file round-trip through the share
  U2 host-side --readonly enforcement against an UNCOOPERATIVE guest
     ([D8g]). The guest-side write was never attempted, so the host-side
     'file unchanged' observation is VACUOUS and is deliberately NOT
     reported as evidence (run.sh skips that block when the guest did
     not complete).
  U3 what a FAILED guest mount looks like from inside the guest
  U4 volume write throughput / per-file latency under --cache=never
     (the host-side direct-write baseline WAS measured: 32 MiB write+fsync
     in 0.0717 s ~= 446 MiB/s, and 200 small files in 0.0203 s; there is
     no virtiofs number to compare it against)
  U5 whether shared=on changes the GUEST's observed MemTotal (the
     [D8b] x US-VM-5 / GH #92 interaction)
  U6 the controlled post-beacon shared=on-vs-private memory delta

WHY UNANSWERABLE HERE — the falsification chain, all of it above:
  * without shared=on the guest reaches /init 11 times out of 12
  * with shared=on it reaches /init 0 times out of 18, always freezing
    immediately after the virtio_blk probe (the root-mount boundary)
  * root+unconfined stalls identically => NOT a confinement interaction
  * prefault=on / thp=off / 128M all stall => NOT a --memory shape
  * QEMU 10.2.1, a completely different VMM, with
    -object memory-backend-memfd,share=on stalls at the IDENTICAL point
    (0/4) while the same QEMU with private memory boots (3/4)
  => MAP_SHARED guest memory does not survive nested KVM on Apple Silicon
     (systemd-detect-virt reports 'apple'). This is a DEV-HOST artifact of
     the same class increment-a documented, not a Cloud Hypervisor defect
     and not evidence against [D8].
