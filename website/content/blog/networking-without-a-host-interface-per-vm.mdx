title: Networking without a host interface per VM

author: The Overdrive team
summary: A single Linux bridge blocked the target attachment population. More bridges and Open vSwitch demonstrated working alternatives, but retained a host network device per VM. Choosing vsock removed that resource class and made socket adaptation, bounded forwarding, and honest completion the next problems to solve.

A microVM runs an application behind its own guest kernel. Networking must get
that application's traffic across the boundary between the guest and the host.
The way it crosses determines which resources the host needs for every VM.

A conventional attachment gives the guest a virtual Ethernet adapter. The
hypervisor, the host program that runs the VM, uses an open queue on a **TAP**
interface to exchange Ethernet frames with that adapter. The TAP is the host's
virtual Ethernet endpoint. A Linux **bridge** acts as
a software switch connecting those TAP interfaces. Add another VM, and the host
needs another TAP and another bridge port.

Overdrive runs its workloads as Linux microVMs under Cloud Hypervisor. Its
networking work aimed to remove the host objects that grew with that population.
An initial design put every VM's TAP on one shared bridge. That bridge could
not reach the target of 16,384 attachments. That forced a choice between distributing the interfaces,
replacing their switch, and removing the per-VM Ethernet attachment altogether.

The selected path uses **vsock**, a socket transport between a guest and its
host that needs no IP network interface between them. Applications still use
ordinary TCP and UDP. Making that work required more than a different cable:
the platform had to preserve destinations, message boundaries, backpressure,
and the meaning of a connection ending.

## One bridge could not hold the attachment target

The native attachment run failed while adding a TAP to the shared Linux bridge.
The kernel returned `EXFULL`, an exhaustion error. The relevant Linux 7.0
allocator has 1,024 port-number slots and reserves port zero, leaving **1,023
usable ports on one bridge**. That is below the intended 16,384-attachment
measurement population.

The retained run proves the provisioning refusal. It did not record the failing
attachment's ordinal or a port inventory at that instant, so the exact
1,023-port interpretation comes from the kernel allocator and the serial
attachment path. It is not a directly counted failure at a particular VM.

The scope matters: this is a limit on one bridge, not on Linux network
interfaces across a machine. The next experiments demonstrated that distinction.

## Changing the switch worked, but kept a device per VM

A tree of Linux bridges held **4,097 TAP interfaces**, spread across five leaf
bridges connected to a root. A separate run booted two real guests on different
leaves among 1,024 TAPs. Both reached peer TCP, gateway TCP, off-subnet TCP,
and gateway DNS endpoints.

That topology introduced another resource to account for. Ethernet delivery
uses ARP to find the hardware address associated with an IPv4 neighbor. Linux
keeps those mappings in a neighbor table. In the tested bridge tree, mappings
appeared on the leaves and root, multiplying the table entries per guest.

In a separate 1,100-TAP burst with untuned neighbor-cache thresholds, gateway
ARP replies stopped at the 342nd distinct source after 341 successes, and the
kernel's table-full counter rose. This was a failure of that configuration and
burst, not a universal 341-VM limit. More bridges solved the port problem but
left per-VM interfaces and neighbor admission to manage.

**Open vSwitch (OVS)** is another software switch with a Linux kernel forwarding
path. Each TAP needs an open file descriptor, its queue handle for exchanging
frames, and a switch port connecting it to that path. The OVS probe held
**16,384 distinct TAPs** with those handles and ports. All endpoints completed
gateway address-discovery and ping exchanges and forwarded byte-identical
synthetic TCP frames through preinstalled kernel rules.

The [OVS findings](https://github.com/overdrive-sh/overdrive/blob/main/docs/feature/netns-density-295/spike/ovs-kernel-findings.md)
prove a working attachment and frame-forwarding alternative. The probe booted
zero VMs and established no workload TCP sessions. It measured neither physical
wire speed nor a 16,384-VM workload population.

OVS remained unselected because it retained the resource class the replacement
was intended to remove: a host network device, open queue handle, and switch
port for each VM. Cleanup made the population visible too. In the final probe,
closing the 16,384 TAP handles took about 100 seconds. That is an observation
from one run, not a general OVS guarantee or a comparison with the delivered
vsock path. OVS solved the bridge ceiling. The selected design also removed
the per-VM host network device.

Hardware networking offered another route: give each VM an endpoint supplied
by the network card. The investigation considered hardware-backed virtual
devices through vDPA and independently assignable card functions through
SR-IOV. The tested hardware and firmware configuration exposed no usable
endpoints. That blocked the hardware experiment on that machine, not the
technologies themselves. Their feasibility remains
[separate work](https://github.com/overdrive-sh/overdrive/issues/329).

## Carry application flows across the guest boundary

Vsock addresses a guest directly through its **context identifier**, or CID.
It does not need a guest Ethernet interface, host TAP, or bridge port. The
hypervisor also stays in the host's shared network namespace rather than getting
a separate host network stack for each VM. Each VM still needs a virtual vsock
device, a CID, sockets, and transport tasks. Removing
network interfaces changes the resources that grow with the population. It
does not make that population unlimited.

Overdrive captures the guest application's socket operations and retains the
address the application intended to reach. A guest flow owner, control code
that sets up and tracks each flow, sends a request over vsock. The host flow
owner reads the request and opens a TCP or UDP socket for the destination.
Kernel forwarding moves the payload between the paired sockets. The diagram
shows that payload route, while the owners control how its sockets are paired.

The host receives a vsock stream, not the guest's original TCP packets. Guest
TCP behavior and the TCP connections opened by the host are therefore separate
parts of the path.

UDP needs another distinction. It carries separate datagrams, while the vsock
stream carries a sequence of bytes. Overdrive prefixes each transported
datagram with its length so the receiver can recover message boundaries. A
zero-length datagram still has a frame and remains a real message, rather than
being mistaken for the end of a stream.

Transport probes established prerequisites at larger populations. One held
16,384 activated Cloud Hypervisor vsock devices with their original Unix-socket
backends. A separate probe held 16,384 kernel transport adapters and exchanged
datagrams through every owner. These were transport-resource experiments, not
16,384 booted guest operating systems or complete production deployments.

The production path uses Linux's kernel vhost-vsock backend rather than
forwarding application payload through the hypervisor. That requires the
project's Cloud Hypervisor source integration. Maintaining that integration,
including its guest-reset behavior, is part of the cost of the choice.

## A slow receiver must slow the sender

Backpressure means the sender stops when the receiver runs out of room. A
forwarder can pass a short byte-exact test and still fail this requirement if
it keeps accepting data into an intermediate queue.

An early Overdrive forwarding design used **eBPF sockmap redirects**: small
programs in the Linux kernel redirected data from one socket toward its paired
socket. For a vsock source, sending permission comes from **credit**, which
tells its peer how much more data it can send.

A native stalled-reader experiment found that Linux returned credit before
the redirected bytes reached the target. The sender kept sending while the
target queue grew, even though the receiver was not reading. The intended
buffer bound did not follow from the selected kernel mechanism. A logically
consistent ownership model could not establish a kernel buffering fact.

The selected forwarder is a kernel module that joins two sockets. It peeks at
the source without removing bytes, attempts a nonblocking send to the target,
and consumes exactly the bytes the target accepted. When the target stops accepting data, those bytes
stay in the source receive queue. That queue's TCP receive window or vsock
credit slows the sender.

The invariant is simple: **a byte leaves its source only after its target
accepts it**. A clean half-close, where one side finishes writing while the
other can still send, follows the last accepted byte. An error aborts the pair.

A working prototype kernel proxy had allocated extra worker threads per peer.
That cost left it unselected. The event-driven module instead queues work when
a socket has data, space, or a state change. Per-CPU workqueues schedule shared
workers without a dedicated forwarding thread for every flow. The
[forwarding decision](https://github.com/overdrive-sh/overdrive/blob/main/docs/product/architecture/adr-0197-guest-flows-are-forwarded-by-an-event-driven-in-kernel-forwarder.md)
records the mechanism and the native evidence behind it.

This choice adds a kernel module built for each supported kernel release. The
host image loads it before the server starts, and node startup checks refuse
to proceed without it. A Linux guest carries a matching **guest kit**: kernel,
module, and `overdrive-init`, the guest's first userspace process. Init checks
the module's kernel release and completes setup before announcing readiness.

## Capture must match the application's socket

Redirecting a guest application's TCP connection into the transport creates an
attribution problem. The guest has an internal listener, called the intake,
that accepts the redirected connection. Its accepted **child socket** is a new
socket. The capture code must associate it with the exact application socket
and original destination before opening a host flow. Timing or a reusable
address tuple is not a reliable substitute for that association.

TCP Fast Open exposed a wrong premise in this association. Fast Open permits
data during connection establishment, changing the path through handshake
validation. An early experiment let the client close before waiting for
correlation to finish. Later traffic could make the result look successful.
Keeping the client open, without post-handshake payload, disproved that result.

The correction observes handshake metadata before the kernel validates the
acknowledgment, then commits the correlation after validation. A small C eBPF
program observes the first point through a kernel function-entry hook. The
existing Rust socket-state callback handles the second. The added hook runs
only during handshake processing, not established data.

Aya `0.13.1`, the Rust library used to load the eBPF programs, loads both the C
and Rust objects. Setup briefly pins kernel tables under filesystem names so
the loaders can share them, then removes those pins before program load and
attachment. Readiness requires the pins to be gone and the programs attached.
The objects remain process-owned, without permanent runtime staging pins.
The important discovery was the validation order, not a need to replace Aya.

## Encryption stays with the host agent

Traffic between mesh workloads uses **mutual TLS**, or mTLS: each side presents
a certificate to authenticate itself, and TLS encrypts the connection. The
node agent holds each workload's certificate and private key and performs the
handshake. The guest application opens an ordinary socket and holds no mesh key.

Linux **kTLS** performs steady-state TLS record processing in the kernel after
the handshake. The socket forwarder refuses TCP sockets carrying that kernel
TLS layer. TLS endpoints and forwarded socket pairs therefore have separate
owners. A temporary userspace relay connects the host's TLS endpoint to guest
delivery. In-kernel forwarding does not mean every VM mesh payload avoids
userspace, and removing TAPs does not establish a throughput improvement.

## Completion must cross back to the flow owner

Overdrive bounds admitted flows with node capacity and a per-allocation quota.
An **allocation** is one physical workload execution. Each admitted flow holds
its places until the host releases them. Half-closing a connection does not
release capacity while it can still hold memory.

Each owner holds a module control handle that owns its kernel pairs. Closing
that handle aborts the remaining pairs. While the handle stays open, an ended
pair queues a completion record whose storage was allocated with the pair. The host owner reads the
record, closes its own descriptors, and releases the capacity. Kernel completion
and owner consumption are separate events.

That interval exposed an audit race. An audit compares the owner's held flows
with the forwarder's inventory to detect missing resources. If it counts only
live pairs, it can see zero kernel pairs while the owner still correctly holds
one place for an unread completion record. Recovery would interrupt a healthy
handoff. The audit must count queued, unread records as occupied too.

A Rust simulation made the schedule reproducible from a seed and action trace.
It drove the production owner and the component supervising shared networking.
The same seed and action trace
triggered false recovery with the old arithmetic and passed with the correction,
with cleanup awaited in both runs. This is evidence about the actual ownership
handoff under simulation, not a formal-model proof of the audit counters.

The allocation's address lease is another owned resource: it reserves the
address until teardown finishes. The platform stops the VM and its mTLS
ownership, waits for guest-network cleanup, and releases that lease only when
the owner reports no remaining allocation resources.

## A clean hypervisor exit is not a workload result

The guest's init process starts the application and reports its exit status to
the host over a separate vsock control channel, called the beacon. A failed
application can be followed by a clean VM shutdown and a successful hypervisor
exit. Using that hypervisor status would report the wrong workload outcome.

Init writes the `EXIT` report, applies a one-second socket linger bound, and
closes the beacon before powering off. Linger gives the queued report a chance
to leave the guest while the transport still exists. The host worker prioritizes
and drains the report reader before handling the hypervisor's exit.

That second is shutdown handling, not a per-VM boot delay. A startup-latency
claim cannot be inferred from it.

## Test each boundary with the evidence it needs

A formal model describes selected state and transitions and checks properties
under its stated assumptions. Overdrive uses Quint, a specification language,
for these protocol models. Rust conformance tests replay model traces against
production owners. Native tests establish what the real kernel and
transport actually do. None automatically supplies the others' evidence.
[The Quint article](/blog/what-quint-can-prove-about-a-flow-owner) explains that
separation in detail, but the backpressure failure already shows why it matters:
model exploration cannot repair a false kernel premise.

Kernel experiments also need their own failure boundary. These tests use the
production Cloud Hypervisor adapter to start disposable fixture VMs. The fixture
supplies a matching kernel, module, and init, then contains the kernel effects
under test inside that VM. Cases that exercise VM launch put the workload
hypervisors inside the disposable fixture, using nested virtualization. A remote physical
machine supplies hardware, not isolation from its own kernel experiments.

Two final correctness tests each exercised 64 VMs. One checked unique live
addresses and one TCP and one UDP exchange per VM, with the node as the observed
source. The other checked fail-closed refusal, cleanup across the next server
boot, and CID reuse. These are correctness results. Density, cold-start time,
throughput, memory, and latency measurements remain
[separate work](https://github.com/overdrive-sh/overdrive/issues/326).

The remaining boundaries are concrete. Guest DNS and remote UDP carry empty
and nonempty datagrams. UDP sent to a **Service VIP**, a stable virtual IP
address naming a service, still cannot be delivered to a VM backend through
that path. That is [deferred](https://github.com/overdrive-sh/overdrive/issues/310).
The host protocol does not depend on the guest's operating system, but the
delivered guest adapter is Linux. A
[non-Linux adapter](https://github.com/overdrive-sh/overdrive/issues/321) is unbuilt.
A server crash can also lose a requested replacement run after it acquires its
lease, a known
[CID recovery window](https://github.com/overdrive-sh/overdrive/issues/325).

The architecture removes a host interface and bridge port per VM. Measuring
what that buys for real workload density and startup is the next task. The
[current networking documentation](/docs/concepts/guest-networking) describes
the implemented operating contract.
