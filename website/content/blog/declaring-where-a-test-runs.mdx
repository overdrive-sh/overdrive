Overdrive runs its integration tests in a shared remote developer environment: a physical x86_64 machine with KVM that `cargo xtask metal run` sends test runs to. A wrapper on that machine executes each test. Each test must say where it runs. Some run on the host. Some need a fresh guest of a named kind, a microVM run by Cloud Hypervisor, whose process is the virtual machine monitor (VMM). A few, the tests of that wrapper's own machinery, use the native launcher kind. Those get a node view: a private network namespace, mount namespace and cgroup namespace, so the test sees its own node and not the shared host's. We run tests with cargo-nextest, which starts each test in its own process, selects tests with its `-E` filter expressions, and drives the standard Rust test harness, libtest. We kept the placement choice in `infra/metal/test-placement.json`, a table keyed by test binary and test name. At the start of this work it held about 4,700 tests, exactly 4,680 entries, in 15,039 lines.

We deleted the table. A test declares its own placement with an attribute, the declaration travels inside the test binary, and `cargo xtask placement-lint` fails before anything is sent to the remote environment if a test is unplaced. This post covers why the table failed, what else we considered, what the design costs, and why sharing a guest between tests needed a protocol we model-checked.

## The table had four owners and one gate

The table was the visible source of truth, but it was not the only one. The guest-suite dispatcher in `crates/overdrive-testing/src/guest_suite.rs` carried its own per-group lists. Retiring it removed 3,057 lines from that file and added 254, and deleted its 23-line binary. It also held about a dozen hand-kept tables, keyed by test name, that chose which files to stage, which modules to load, how much memory to give a guest, and which setup scripts to run. One test was matched by a literal name in the source.

Every rename was a hazard. Rename a test and its table entry no longer matched. If the test was in the table, the wrapper refused it as unclassified. If it was one of the name-keyed variants, the test lost its staged tool and failed inside the guest for a reason that pointed nowhere near the rename.

The only gate was the wrapper in the remote environment, which refuses an unplaced test with status 78 before its body runs. A developer on a laptop or in CI learned about a missing entry only after queuing for that remote machine.

## Why the declaration lives on the test

We wanted one edit site and a check that runs before a test reaches the remote environment. Four designs fit that goal. Each lost.

**A generated table.** A build step would derive the table from the tests. That leaves a second artifact that can go stale and needs a build hook in every crate. We would have kept the file and added a generator.

**A lint over the existing table.** Checking that the table is complete would catch the unplaced test early. It would leave placement defined in three places, and a rename would still need a JSON edit.

**A runtime registry.** A test binary could print its placements on request, the way `inventory`-style crates work. libtest's `main` cannot answer such a query, so every binary would need a custom harness.

**Encoding placement in the test name.** This changes every name, breaks `-E` selection in nextest, and discards test history.

The design that survived is an attribute, `#[overdrive_test(...)]`, that writes a record into the test binary. The macro emits a record into an ELF section named `overdrive_test_placement`. The wrapper reads the section of the binary nextest hands it, finds the record for the exact test, and places the test. No table lookup exists. A test with no record is refused before its body runs, as before.

The attribute covers the five kinds the table held: `host_pure`, `native_launcher`, `guest = "<group>"` with an optional `profile` (a named variant of a group that stages extra files, modules or memory), and `lane_operator` and `lane_owner` for the two sides of a fixture that runs inside a guest. Writing the attribute on each of about 4,700 tests would be churn, so two function-like macros place tests in bulk. `placement!(host_pure)` covers every test of one module. `overdrive_test_default!(host_pure)` covers a host-only binary. A test's own declaration wins over its module's, which wins over the binary default.

## What this costs

The record in the binary is a cross-process contract. The macro writes it, the wrapper reads it, and the lint reads it. Three readers could drift, so we made one of them the only parser. `placement-lint` invokes the wrapper's own reader through `test-wrapper.sh --check-placement` instead of implementing the format a second time.

The macro has build-time costs. Each record is a `#[used]` static in that section, and nothing in the test body references it. In a probe on rustc 1.95.0 the section and all eight records survived dev and release builds without a reference, so we added none. The macro never inserts `#[test]`. We found that "insert it when absent" ran four stackings twice, including a `#[test]` written above the attribute and `#[quint_run]` written above it. The attribute reads only the attributes below it, so it sits above `#[test]`, `#[tokio::test]` and `#[should_panic]`, and below `#[quint_test]`.

A module can declare a shared guest once, and its tests read the declaration by name. We first wanted an attribute on the `mod` itself. On stable Rust that fails with E0658, because proc-macro attributes on modules need a nightly feature, and our `mod integration { mod a; mod b; }` layout hits it. So `shared_guest!` expands to a module-private constant, and a test that carries a bare `#[overdrive_test]` names that constant by ordinary path resolution. A test in a module with no declaration fails to compile with rustc's "cannot find value" error. A proc macro cannot emit a better message, so we made the constant's name the instruction: `OVERDRIVE_TEST_NEEDS_shared_guest_DECLARATION_IN_THIS_MODULE`.

The lint reads ELF sections, so it runs on Linux. The pre-push hook routes it through the Linux environment on a Mac. The CI workflow also runs it beside the nextest step, but that workflow runs only when someone starts it by hand. It lists tests with `integration-tests` and each member's own `kvm-tests` feature. Without `kvm-tests`, 140 tests would have escaped the check.

One more choice has a visible cost. Outside the remote environment, a guest-placed test runs its body in the current process. Guest placement exists to isolate tests from each other on the shared remote machine, and CI runners and local Linux VMs are private. The alternative was to fail closed everywhere else. Failing closed would have turned every guest-placed test red in the pre-push hook and in the CI workflow when someone starts it. Hundreds of tests run in those places, and they would fail to protect against interference that cannot happen on a private machine. It would also have needed CI to run on the remote machine. The price is that a laptop run does not exercise guest isolation. Only a run in the remote environment does.

The guest groups and profiles are a closed registry of 22 environments over eight groups. A typo is a build error at the offending literal, naming the value. Adding an environment is a code change. Moving the name-keyed variants into profiles means a rename can no longer drop one silently. Two dispatcher rows matched no test, and six table entries in the control-plane binary named tests that no longer exist. We deleted them.

## Sharing a guest needed an owner

Before this work, runs in the remote environment already booted a fresh guest for each guest-placed test attempt. In a probe we measured about 0.45 seconds of staging and 2.4 seconds of boot per test, from two samples. The dispatcher had shared a guest across a group, and deleting it would have dropped that sharing. So we required a replacement that kept per-test results, retries and `-E` selection.

Three shortcuts lose them. Running a whole module as one nextest test in one guest folded three passes and a failure into one result in our probe, and it lost per-test retries. A nextest setup script has no teardown hook and does not know the test binary, so it would need the same socket and cleanup process we build below. Letting the first test own the guest kills the guest when that test ends, and the other tests lose it.

Nextest runs every test in its own process, so a shared guest must outlive any one test process. We settled on an owner process. The first test of a module to arrive takes an exclusive `flock` (the kernel's advisory file lock) on a per-scope file, starts the owner, and releases the lock. Later tests find a socket in the run's directory and attach. The owner boots one guest and runs one test at a time, in arrival order.

Four rules follow from that.

The VMM must never outlive its owner. We had the owner call `unshare(CLONE_NEWPID)` and fork, so the owner proper is init of its own PID namespace. When init dies, the kernel kills every other task in the namespace and waits for them. We read that path in the pinned Linux 7.0 source (`kernel/pid_namespace.c:225-234`, `kernel/exit.c`) and then ran it. SIGKILL of the owner left no VMM within 38.6 milliseconds over 13 cycles, and the production launcher worked unchanged inside the namespace. The alternative, a parent-death signal on the VMM, would have changed the production launcher to suit a test.

A running test is never cancelled. The owner marks a guest tainted when it must not run another test, and it discards a tainted guest once the exec in it ends. A client that disconnects while its test runs leaves the exec running and taints the guest.

A failed, lost, bounded or abandoned test discards its guest, and the next test boots a replacement, about three seconds. A retry exists because a test failed, so the retry runs in a fresh guest.

Every shared exec has a bound. When nextest kills a test at its slow timeout, an isolated guest dies with the process. A shared guest does not, and a hung test would hold the slot for up to 24 hours. Each profile carries a bound on one exec, covering its per-test setup, the test body and its cleanup: 300 seconds, 600 for profiles whose name starts with `nested` and for the `nested-boundary` group, and 1,200 for `nested-cohort`. That profile is a `cgroup-default` variant of `nested` that gives the outer guest 12,821 MiB instead of 4,096. These are the limits the same tests already ran under in the old dispatcher. A test that can run longer than its profile's bound cannot live in a shared module. It takes an explicit `guest = "<group>"` and gets its own guest. The owner also exits after 30 seconds without a test, so a finished module does not hold a guest for the rest of the run.

## Why we model-checked the owner

We model-checked the owner because its failure modes are interleavings we could not enumerate by reading. Several processes race for election, a queue orders them, a guest can fail mid-test, and a client can vanish while its test runs. [Quint](/docs/concepts/quint-modeling) is a language for executable models of protocols. You describe states and actions, and a checker explores orderings to find one that breaks a stated property. We wrote the owner's protocol in Quint and checked it before building the owner.

The specification has 19 checks. Two check invariants over every reachable state. Seven are hazard variants, copies of the model with one rule removed that must produce a counterexample. Ten are named runs, scripted sequences of actions that the checker replays and asserts on. A full recorded run takes 128.7 seconds on the remote machine. The decisions held under model checking: both invariants hold and the ten runs pass. Each of the seven hazard variants failed as intended, producing the counterexample we predicted:

- With no election lock, two owners start.
- With no in-flight guard, two tests run at once.
- With no taint, a bad guest is reused.
- If an owner crash leaves the guest, the guest is orphaned.
- If a disconnect frees the slot, the next test starts while the first still runs.
- With no exec bound, a hung test holds the slot forever.
- If the owner exits on idle without its guard, a waiting client is dropped.

That is the evidence that each rule is load-bearing and that the invariants can fail.

The model assumes some behavior it cannot prove. Election, owner crash and the owner's kernel lifetime belong to the operating system, so replaying model traces against the code does not drive them. We checked them directly on the remote machine, running Linux 7.0.0-38. Eight simultaneous first arrivals elected exactly one owner under `flock`, and without the lock they started eight. Clients in seven other per-test network namespaces reached the socket, and the run directory was gone afterwards.

## What the comparison shows and what it leaves open

We moved the table's entries onto their tests and deleted the entries that named tests which no longer exist. We deleted `test-placement.json` and the dispatcher, and put `placement-lint` into the pre-push hook and the manually started CI workflow. A rename needs no JSON edit.

We ran the full workspace in the remote environment for this branch and for its merge base with `main`, then compared the results by test name. The branch run predates our last review fix, which made `placement-lint` run the wrapper's reader. After that change the xtask suite passed 428 of 428. On the branch, 4,726 tests ran: 4,654 passed and 72 failed. 27 more were skipped. On `main`, 4,733 ran: 4,662 passed and 71 failed, and 29 more were skipped. 69 tests fail on both sides. 63 of them are `overdrive-cli` VM integration tests. 59 of the 69 report that `systemd-detect-virt` was not found. We did not investigate the other 10. Three tests failed only on the branch, and each passed when we reran it in isolation on the branch and on `main`. One of them, the VM workload TCP and UDP round trip through `serve` and `deploy`, passes about half the time on both sides. Two tests failed only on `main` and passed on the branch. The tests present on one side only are the retired dispatcher and table tests on `main` and their replacements on the branch. The `overdrive-bpf` integration tests passed 20 of 20 on both sides.

We chose not to run mutation testing for this change, so we have no kill rate for it. We did not measure full-workspace wall time before and after. Our shared-guest timings come from a probe with four tests per module: 11.8 seconds serial with a guest per test, against 3.6 seconds with one shared guest. Part of the shared figure is a 300-millisecond console-flush sleep the probe added, so it is an upper bound. The boot time we quote rests on two samples of `cgroup-default`.

Tests that share a guest share its kernel, cgroup tree, firewall (nftables) tables and `/tmp`. The owner runs each profile's setup and cleanup around every test and resets nothing else. A guest is shared only within one module of one test binary. Sharing is declared per module, so a module of tests that need isolation from each other keeps `guest = "<group>"` on each test. A test that outlives its profile's exec bound must do the same.

Five gateway tests stage the whole 3.9 MB `specs/quint` tree rather than one model file. We chose that over adding a model-file argument to those five tests, which would have meant another argument, another build error and another staging step. The `.qnt` files are 856 KB of that tree. We have not measured the staging cost, and we chose the whole tree to avoid the extra argument.
