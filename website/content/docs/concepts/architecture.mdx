Overdrive is one binary on one node. It runs a control plane that reconciles
declared intent into running microVMs, an eBPF service dataplane, and separate
mutual-TLS paths for the operator and for workloads.

The mental model to hold: **you declare what should run; a loop makes it so.**
Everything below is in service of that loop.

The sections below walk through this diagram — the single binary, the two
stores, the loop that joins them, the microVM driver, the dataplane, and the

## One binary, one node

`overdrive` is a single binary. `overdrive serve` starts a control plane and a
co-resident worker in one process on one host. There is no separate node agent
to install, no scheduler service to run, and no cluster to join — the node
identifies itself as `local` and serves only itself.

When the process starts, it does the following before it accepts work, and it
refuses to boot if any of them fails:

- **Probes the cgroup filesystem.** Each microVM's hypervisor process runs in
  its own cgroup. If the node cannot reach a usable cgroup v2 hierarchy, boot
  stops with a structured `health.startup.refused` event rather than limping
  along.
- **Loads and probes the eBPF dataplane.** The XDP and cgroup programs are
  attached and verified up front, not lazily on first packet.
- **Opens the workload CA.** It decrypts the persistent root under the operator
  key-encryption key. If the envelope will not open, the node refuses to start
  rather than mint a new root.
- **Probes mesh networking.** The transparent-mTLS proxy and its backend index
  must pass their probes. Namespaces and capture rules left by a previous run
  are adopted or swept, and the service-name responder must start.
- **Reclaims stranded microVMs** left behind by a previous run.
- **Mints its operator TLS identity** and binds the listener.

This is "earned trust": the server proves it can do its job at boot instead of
discovering it cannot at the first deploy.

## The shape of a deploy

Following a single `overdrive deploy` through the system is the fastest way to
see how the pieces connect.

1. The CLI reads `~/.overdrive/config`, opens a mutually-authenticated TLS
   connection to the control plane, and submits the parsed spec.
2. The control plane writes the spec to the **IntentStore** and returns an
   outcome — `Inserted` for a new content hash, `Unchanged` for one it already
   holds. The deploy is now durable; nothing is running yet.
3. The **convergence loop** notices the new intent, computes the gap between what
   should run and what is running, and emits actions to close it.
4. A `StartAllocation` action reaches the **action shim**. The shim creates the
   allocation's network namespace, its veth pair, and a TAP device, then hands
   the allocation to the **worker**. The worker boots a Cloud Hypervisor microVM
   inside that namespace.
5. The guest reports that it has booted, and the worker writes the allocation's
   status into the **ObservationStore**. The platform then installs the
   allocation's mTLS capture and only after that releases the workload's
   command inside the guest. The next turn of the loop reads that status as the
   new "actual," and the gap is closed.

Steps 2 and 5 touch the two halves of cluster state; step 3 is the engine that
joins them.

## Two stores, one consistency split

Overdrive keeps **intent** (what should run) separate from **observation** (what
is running) — separate traits, separate types, separate files. The
[intent / observation boundary](/docs/concepts/intent-observation) explains why
this split is load-bearing:

| | IntentStore | ObservationStore |
| --- | --- | --- |
| Holds | declared workload specs, the sealed workload-CA root | allocation status, node health, service backends, probe results, certificate issuance audit |
| Backed by | redb (`intent.redb`) | redb (`observation.redb`) |
| Written by | the control plane, via typed actions | the node that owns each row |
| Conflict rule | content-hash idempotency | last-writer-wins on a logical timestamp |

Both stores are local redb files on the one node. The split does not depend on
the backend: each store sits behind its own trait, so a replicated backend can
replace either one without changing the code that uses it.

## The convergence loop

The loop is the heart of the control plane, and it is deliberately boring: a
real background task wakes on a tick, drains a queue of pending evaluations, and
for each one runs a **reconciler**. The evaluations arrive from three places: an
**interest router** that submits one when an observation row a reconciler cares
about changes, a **cadence table** that submits periodic resyncs for reconcilers
that declare a schedule, and reconcilers themselves handing work to one another.
Each reconciler declares which of these wakes it; the loop holds no reconciler
names and no hardcoded intervals. See
[how the runtime wakes a reconciler](/docs/concepts/reconcilers#how-the-runtime-wakes-a-reconciler).

A reconciler is a pure function. It receives the desired state (hydrated from
intent), the actual state (hydrated from observation), and its own durable memory
(a typed view), and it returns a list of actions plus its next memory. It does no
I/O and reads no clock of its own — the runtime hands it everything, which is
what lets the whole loop be replayed deterministically under
[simulation](/docs/concepts/deterministic-simulation-testing). The runtime owns
the rest: it persists the reconciler's memory to a redb-backed view store
(writing and flushing to disk *before* it treats the action as done, so a crash
mid-tick resumes cleanly), then dispatches the actions through the **action
shim**, the one place their side effects run.

Seven reconcilers run in `overdrive serve`:

- **WorkloadLifecycle** — drives allocations toward the declared replica count
  and emits `StartAllocation`, `StopAllocation`, `RestartAllocation`, or
  `ReleaseServiceVip`. It places work with a first-fit walk over nodes. It is
  the only reconciler that restarts anything, and it backs off restarts on
  repeated failure.
- **ServiceLifecycle** — drives a service through its health gates. It reads the
  latest probe results and decides whether an allocation has passed startup
  (becomes `Stable`) and whether it is ready to receive traffic. It publishes
  each service's backends, with their health, as observation rows. When an
  allocation exhausts its liveness budget, it emits `StopAllocation` and leaves
  the restart to WorkloadLifecycle. See
  [Health checks close a second loop](#health-checks-close-a-second-loop).
- **ServiceMapHydrator** — programs the eBPF service maps from those backend
  rows.
- **WorkflowLifecycle** — the bridge to the [workflow](/docs/concepts/workflows)
  engine: it watches workflow instances and re-emits `StartWorkflow` for one that
  should be running but has no live task, so a workflow resumes after a crash the
  same way a crashed allocation does.
- **SvidLifecycle** — issues a SPIFFE SVID for every running allocation and drops
  it when the allocation stops, emitting `IssueSvid` / `DropSvid`. A near-expiry
  re-issue is a single audited action, not a workflow.
- **VmReclamation** — reclaims microVM allocations and discards stranded host
  artifacts. It reads its actual state from the host rather than an observation
  row, so it declares a periodic `resync_schedule` — a 30-second sweep of the
  local node — instead of an interest.
- **NoopHeartbeat** — a proof-of-life reconciler that emits a no-op every tick;
  it exists to anchor the "reconcilers are pure" invariant the test suite checks.

Adding a behavior to the control plane means adding a reconciler, not threading
logic through the loop. The loop does not know what the reconcilers do. For the
reconciler contract itself — the pure function, its typed memory, and how to write
one — see [reconcilers](/docs/concepts/reconcilers).

The same shape makes the loop self-heal. A reconciler recomputes the gap between
desired and actual every time it runs, so it never assumes a past action took
effect — it checks. A half-finished operation is just a gap the next pass
closes: an allocation that crashed partway through starting is started again, a
veth pair left half-provisioned by an interrupted boot is completed rather than
adopted as-is. The control plane converges toward the declared state or keeps
trying; it does not strand half-applied state for someone to fix by hand.

## The worker runs microVMs

Every workload runs as a Cloud Hypervisor microVM. `VmDriver` launches
`cloud-hypervisor` inside the allocation's network namespace, with the TAP
device as the guest's network interface, and boots an operator-supplied kernel
and root filesystem. Inside the guest, `overdrive-init` runs as process 1. It
configures the guest's network, reports over vsock that the guest has booted,
runs the workload's command once the platform releases it, and reports the
command's own exit status.

A spec's `[vm]` block — `command`, `args`, `kernel`, and `rootfs` — describes
what to boot and run, and the `[resources]` block (`cpu_milli`, `memory_bytes`)
sizes the guest. The spec's top-level section names the workload's *kind* —
`[service]` or `[job]` — which is orthogonal to the driver that runs it. See
[microVMs](/docs/concepts/microvms).

## Health checks close a second loop

A service declares health-check probes — startup, readiness, and liveness — and
the worker runs them. When an allocation reaches running, the worker spawns one
task per declared probe; each ticks on its own interval and executes the probe
through a port trait: `TcpProber` connects to a port and `HttpProber` issues a
plain-HTTP GET. Probes run on the host against the guest's address. The result
of every tick is written to the ObservationStore as a probe-result row.

That write is what closes the loop. The probe runner does not decide anything —
it only observes. The **ServiceLifecycle** reconciler reads those probe results
on the next tick and makes the decisions: a service is not `Stable` until its
startup probes pass, not sent traffic until readiness passes, and stopped once
its liveness failures exhaust the budget, after which WorkloadLifecycle restarts
it. The same intent/observation discipline applies — probing is observation, the
verdict is a reconciler acting on it — which is why the health-check logic is a
pure reconcilable function and not ad-hoc timers scattered through the worker.

## The service dataplane is in the kernel

`EbpfDataplane` loads XDP programs onto the client and backend interfaces of a
host veth pair and attaches cgroup `connect4`, `sendmsg4`, and `recvmsg4`
programs to `overdrive.slice`, all at boot. **ServiceMapHydrator** keeps the BPF
maps in sync with each service's healthy backends, and the kernel does the
forwarding. There is no userspace proxy in this service-VIP load-balancing path.

What the kernel does with a service's traffic turns on **where the backend
runs**.

### Local backends

A backend is *local* when it runs on the same node as the dataplane, which on a
single node is every backend. The `connect4` program rewrites a connection's
destination from the service VIP to the backend's address at `connect()` time —
before a packet leaves the socket — and records the pick in `LOCAL_BACKEND_MAP`.
The return path needs no rewrite: the socket was opened to the backend's own
address, so its replies already carry the address the client expects. The
`sendmsg4` and `recvmsg4` programs do the same for UDP.

### Remote backends

A backend is *remote* when it runs on a different node, and it takes a different
mechanism. XDP matches the VIP in `SERVICE_MAP` and redirects the packet to the
backend's node; then, because that backend replies from its own address, a
reverse-NAT program rewrites the reply's source back to the VIP through
`REVERSE_NAT_MAP`, so the client never sees the backend IP. These programs and
maps are loaded at boot, but no deploy reaches them: the node is always `local`,
so every backend resolves to this host and classifies as local.

## Two mutual-TLS paths

For the **operator ↔ control-plane** connection, the control plane mints an
ephemeral CA at boot, issues itself a server leaf and the operator a client leaf,
and binds a rustls listener. It writes the endpoint, CA pin, and operator
certificate to `~/.overdrive/config` as one unit — the "trust triple" every CLI
command reads. This connection is always mutually authenticated.

The **workload mesh** uses a separate, persistent workload-identity CA. Its
[workload identity lifecycle](/docs/concepts/workload-identity-lifecycle) holds
each running allocation's SPIFFE SVID in the node agent. Every workload's traffic
leaves its microVM through the TAP device and crosses the host end of its veth
pair, where an nftables TPROXY rule hands it to the
[transparent-mTLS proxy](/docs/concepts/transparent-mtls). The proxy presents the
SVID in the handshake and uses kTLS for steady-state encryption. Workloads hold
no key or certificate.

[Service Names](/docs/concepts/service-names) lets a workload reach this
encrypted path by hostname. A node-local DNS responder answers
`<name>.svc.overdrive.local` with a stable address while the service has a
healthy backend.

## Why it is built on a swappable seam

Every source of nondeterminism — the clock, the network, randomness, the
dataplane, the workload driver, the stores — sits behind a port trait in
`overdrive-core`. Production wires the real adapters (`SystemClock`,
`EbpfDataplane`, `VmDriver`, the redb stores); the test harness wires
in-process simulated ones. The core logic never names a concrete implementation,
so the same control plane that runs your workloads can be driven by a simulated
world and replayed bit-for-bit from a seed. A lint gate keeps direct calls to the
real world out of core logic. This seam is the foundation
[deterministic simulation testing](/docs/concepts/deterministic-simulation-testing)
is built on, and it is why the convergence loop can be tested as a pure function
rather than against a live cluster.
