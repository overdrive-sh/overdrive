Overdrive runs a control plane and worker in one process on one node. The
control plane reconciles declared intent into Linux microVM
allocations. eBPF steers supported service traffic; host mTLS enforcement
protects mesh TCP; shared vsock transport connects Linux guests without a host
interface per VM. The [remaining boundaries](#what-is-not-here-yet) distinguish
implemented behavior from design targets.

The mental model to hold: **you declare what should run; a loop makes it so.**
Everything below is in service of that loop.

## One binary, one node

`overdrive` is a single binary. `overdrive serve` starts a control plane and a
co-resident worker in one process on one host. There is no separate node agent
to install, no scheduler service to run, and no cluster to join — the node
identifies itself as `local` and serves only itself. A production multi-node,
role-at-bootstrap topology is the design target; the shipped path is the
single-node one, and the rest of this page describes that path.

Before accepting work, startup validates the required host capabilities and
refuses to boot if a required check fails:

- **Probes the cgroup filesystem.** The worker places VMM processes inside
  cgroups; if it cannot reach a usable cgroup v2 hierarchy, boot stops with a
  structured `health.startup.refused` event rather than limping along.
- **Loads and probes the eBPF dataplane.** The XDP and cgroup programs are
  attached and verified up front, not lazily on first packet.
- **Checks shared guest networking and mesh enforcement.** The host image must
  have loaded `ovd_fwd`. Startup probes its control context, claims shared
  listeners, checks descriptor capacity and address-prefix conflicts, and
  validates the mesh enforcement and resolve paths. These are node startup
  checks, not per-VM launch probes.
- **Mints its operator TLS identity** and binds the listener. The workload CA
  separately adopts its persistent encrypted root before issuing SVIDs.

This is "earned trust": the server proves it can do its job at boot instead of
discovering it cannot at the first deploy.

## The shape of a deploy

Following a single `overdrive deploy` through the system is the fastest way to
see how the pieces connect.

1. The CLI reads `~/.overdrive/config`, opens a mutually-authenticated TLS
   connection to the control plane, and submits the parsed spec.
2. The control plane writes the spec to the **IntentStore** and returns an
   outcome — `Inserted` for a new content hash, `Unchanged` for one it already
   holds. The deploy is now durable; nothing is running yet.
3. The **convergence loop** notices the new intent, computes the gap between what
   should run and what is running, and emits actions to close it.
4. An action like `StartAllocation` reaches the **worker**, which selects a
   VM driver, places the VMM process under a cgroup, boots Cloud Hypervisor,
   and watches guest readiness and exit reports.
5. The worker writes the allocation's status into the **ObservationStore**. The
   next turn of the loop reads that status as the new "actual," and the gap is
   closed.

Steps 2 and 5 touch the two halves of cluster state; step 3 is the engine that
joins them.

## Two stores, one consistency split

Overdrive keeps **intent** (what should run) separate from **observation** (what
is running) — separate traits, separate types, separate files. The
[intent / observation boundary](/docs/concepts/intent-observation) explains why
this split is load-bearing. What ships today is the structural separation, not
yet its multi-node payoff:

| | IntentStore | ObservationStore |
| --- | --- | --- |
| Holds | declared workload specs | live allocation status, node health, service backends, probe results |
| Backed by | redb (`intent.redb`) | redb (`observation.redb`) |
| Written by | the control plane, via typed actions | the node that owns each row |
| Conflict rule | content-hash idempotency | last-writer-wins on a logical timestamp |

Both stores are local redb files on the one node. The gossip propagation the
boundary concept describes — every node writing its own rows and the cluster
converging — is the multi-node design; on a single node there is nothing to
gossip to. The boundary is built now so that adding nodes later is a change of
backend, not a change of architecture.

## The convergence loop

The loop is the heart of the control plane, and it is deliberately boring: a
real background task wakes on a tick, drains a queue of pending evaluations, and
for each one runs a **reconciler**. The evaluations arrive from three places: an
**interest router** that submits one when an observation row a reconciler cares
about changes, a **cadence table** that submits periodic resyncs for reconcilers
that declare a schedule, and reconcilers themselves handing work to one another.
Each reconciler declares which of these wakes it; the loop holds no reconciler
names and no hardcoded intervals. See
[how the runtime wakes a reconciler](/docs/concepts/reconcilers#how-the-runtime-wakes-a-reconciler).

A reconciler is a pure function. It receives the desired state (hydrated from
intent), the actual state (hydrated from observation), and its own durable memory
(a typed view), and it returns a list of actions plus its next memory. It does no
I/O and reads no clock of its own — the runtime hands it everything, which is
what lets the whole loop be replayed deterministically under
[simulation](/docs/concepts/deterministic-simulation-testing). The runtime owns
the rest: it persists the reconciler's memory to a redb-backed view store
(writing and flushing to disk *before* it treats the action as done, so a crash
mid-tick resumes cleanly), then dispatches the actions.

Eight reconcilers run today:

- **WorkloadLifecycle** — drives allocations toward the declared replica count
  and emits `StartAllocation`, `StopAllocation`, or `ReleaseServiceVip`. It
  places work with a first-fit walk over nodes (the same algorithm the
  `overdrive-scheduler` crate defines) and backs off restarts on repeated
  failure.
- **ServiceLifecycle** — reads startup, readiness, and liveness probe rows. It
  commits `Stable` after startup passes or an explicit opt-out, gates a
  startup-probed backend on committed `Stable` and readiness, and stops an
  allocation when its startup deadline or liveness threshold fails.
  WorkloadLifecycle owns restart and
  give-up under one budget. See
  [Health checks close a second loop](#health-checks-close-a-second-loop).
- **BackendDiscoveryBridge** and **ServiceMapHydrator** — together they turn live
  allocations into dataplane state, feeding the service map the eBPF programs
  read.
- **WorkflowLifecycle** — the bridge to the [workflow](/docs/concepts/workflows)
  engine: it watches workflow instances and re-emits `StartWorkflow` for one that
  should be running but has no live task, so a workflow resumes after a crash the
  same way a crashed allocation does.
- **SvidLifecycle** — issues a SPIFFE SVID for every running allocation and drops
  it when the allocation stops, emitting `IssueSvid` / `DropSvid`. A near-expiry
  re-issue is a single audited action, not a workflow.
- **VmReclamation** — reclaims microVM allocations and discards stranded host
  artifacts. It reads its actual state from the host rather than an observation
  row, so it declares a periodic `resync_schedule` — a 30-second sweep of the
  local node — instead of an interest.
- **NoopHeartbeat** — a proof-of-life reconciler that emits a no-op every tick;
  it exists to anchor the "reconcilers are pure" invariant the test suite checks.

Adding a behavior to the control plane means adding a reconciler, not threading
logic through the loop. The loop does not know what the reconcilers do. For the
reconciler contract itself — the pure function, its typed memory, and how to write
one — see [reconcilers](/docs/concepts/reconcilers).

The same shape makes the loop self-heal. A reconciler recomputes the gap between
desired and actual rather than assuming a past action succeeded. The driver
registry, allocation-to-driver index, and exit observers retain separate
ownership even though the only supported workload adapter is `VmDriver`.

## The worker runs Linux microVMs

Every supported workload uses a `[vm]` block. `command` and `args` name the
program inside the guest, while `kernel` and `rootfs` name operator-supplied
host artifacts from a matching guest kit. `[resources]` sizes the guest's CPU
and memory. Job and service are lifecycle kinds, not alternative host-process
execution modes.

The Cloud Hypervisor process runs non-root under seccomp, Landlock, and the
allocation's cgroup. It shares the host network namespace. Guest capture and
a kernel forwarder transport application flows over vsock without a per-VM
host network namespace, veth, TAP, or bridge. The driver reports guest boot
completion and the workload's guest-reported exit status. A successful VMM exit
does not stand in for the workload's exit status.

The host agent, VMM, and helpers are processes. They do not provide a supported
host-process workload driver. VMM absence can leave the registry empty while
the control plane starts, and a later VM launch reports the missing capability.
The composition root declares whether VM capability is optional or required.
A required capability failure refuses startup, while an optional unavailable
capability leaves no VM adapter to execute work.

See [microVMs](/docs/concepts/microvms) and
[guest networking](/docs/concepts/guest-networking) for artifact requirements,
capacity, lifecycle, and traffic limits. Additional guest runtimes remain
future work.

## Health checks close a second loop

A Service has three health-check roles. Startup gates `Stable`. Readiness gates
traffic after `Stable`. Liveness begins at `Stable` and can stop an unhealthy
allocation. The worker's probe runner observes and writes probe-result rows. An
explicit TCP probe connects to a port, and an HTTP probe sends a plain-HTTP GET
through the guest-network owner. Command-execution probes are unbuilt.

When the operator omits startup probes, the worker runs a platform-supplied
guest-listener startup check. Guest kernel hooks report each declared TCP
`listen()` and explicit UDP `bind()` over the VM's beacon channel. The host
keeps only declared protocol-and-port pairs for that allocation. The probe
runner writes a startup `Pass` when every declared listener has been reported,
or a `Fail` at the 60-second deadline naming the missing listeners. The Service
does not become `Stable` or backend-eligible while a declared listener remains
unreported. An explicitly empty startup list opts out of this gate.

The **ServiceLifecycle** reconciler reads the probe rows and commits `Stable`
while the allocation is `Running` and startup has passed, or when the operator
explicitly opts out of startup checks. For a startup-probed allocation,
committed `Stable` precedes backend eligibility. ServiceLifecycle then applies
the readiness result. On a startup deadline or terminal liveness failure, it
stops the live allocation. **WorkloadLifecycle** alone restarts it or records
give-up. The exit observer cancels probe supervision on
a natural VM exit, including when a terminal row write fails. This prevents a
dead allocation's probe tasks from persisting into its successor's lifetime.
Broker submissions wake the convergence loop when they arrive, while its cadence
tick remains a backstop. Probe rows stay observations, and reconciler decisions
stay separate from the worker's measurements.

## Networking uses separate mechanisms for separate boundaries

`EbpfDataplane` loads XDP and cgroup programs at node startup. The control plane
keeps their maps aligned with service backends. Supported IPv4 service traffic
uses a stable VIP and kernel-side steering; local socket hooks and packet-path
XDP programs handle different entry points. These address-rewrite programs do
not implement TLS or replace the workload lifecycle.

Guest eBPF captures ordinary application sockets, and `ovd_fwd` transports their flows over vsock
through shared node listeners. The host opens destination sockets and routes
mesh TCP into the node agent's mTLS enforcement.

The forwarder moves bytes inside the kernel only after the target accepts
them, preserving source-socket backpressure. It refuses kTLS sockets; TLS
termination belongs to the host mTLS path, with a temporary userspace relay for
guest delivery. A kernel forwarder is therefore not a claim that the whole
mesh path avoids userspace payload handling.

The host owns each allocation's address lease and flows through teardown.
An ended pair queues a completion record, and capacity remains occupied until
the owner consumes it. Shutdown waits for the allocation's guest-network
resources to end before releasing its address lease.

Guest DNS and remote TCP/UDP are supported, including empty UDP datagrams.
Guest-to-Service-VIP UDP delivery to a VM backend is
[unbuilt](https://github.com/overdrive-sh/overdrive/issues/310). The implemented
mesh is single-node; loaded XDP support does not imply a deployed multi-node
control plane. See [guest networking](/docs/concepts/guest-networking) and
[transparent mTLS](/docs/concepts/transparent-mtls) for the exact boundaries.

## Identity is mutual TLS, minted at boot

Operator API authentication uses an ephemeral CA. At boot the control plane
mints that CA, issues itself a server leaf and the
operator a client leaf, and binds a rustls listener. It writes the endpoint, the
CA pin, and the operator certificate to `~/.overdrive/config` as one unit — the
"trust triple" every CLI command reads. The connection is mutually
authenticated; there is no flag to turn that off. These are standard X.509
certificates. (SPIFFE identifiers also appear in the data model — every allocation
carries one — and they now drive a separate, transparent handshake for traffic
between workloads; see [transparent mTLS](/docs/concepts/transparent-mtls).)

## Why it is built on a swappable seam

Every source of nondeterminism — the clock, the network, randomness, the
dataplane, the workload driver, the stores — sits behind a port trait in
`overdrive-core`. Production wires the real adapters (`SystemClock`,
`EbpfDataplane`, `VmDriver`, the redb stores). The test harness wires
in-process simulated ones. The core logic never names a concrete implementation,
so the same control plane that runs your workloads can be driven by a simulated
world and replayed bit-for-bit from a seed. A lint gate keeps direct calls to the
real world out of core logic. This seam is the foundation
[deterministic simulation testing](/docs/concepts/deterministic-simulation-testing)
is built on, and it is why the convergence loop can be tested as a pure function
rather than against a live cluster.

## What is not here yet

The full design describes a larger system. The following are design-stage — there
is no wired, functional code for them in what ships today, and these docs will
not describe them as present until there is:

- **High availability.** Intent lives in single-node redb; there is no Raft
  replication. `cluster upgrade --mode ha` parses but is not wired.
- **Gossip-replicated observation.** Observation is local redb; the CR-SQLite /
  Corrosion gossip layer is the multi-node design target.
- **Other guest runtimes.** Non-Linux guest networking, unikernel, and WASM
  drivers are unbuilt. Linux microVMs run through Cloud Hypervisor.
- **The policy engine, native telemetry, and the LLM self-healing agent.** Each
  is part of the design. None is wired into `serve`. The
  [public ingress gateway](/docs/concepts/public-ingress-gateway) is wired
  and runs when `serve` receives the gateway flags.
- **HTTP/2 and automated certificates at the gateway.** The gateway speaks
  HTTP/1.1 and reads certificates from files you supply.
- **Presenting workload identity on every path.** The built-in certificate
  authority issues, holds, and audits a SPIFFE SVID for every running allocation,
  and the mesh dataplane presents it on the wire in both directions — a node-agent
  L4 proxy encrypts connections between workloads with TLS 1.3 (see
  [transparent mTLS](/docs/concepts/transparent-mtls)). The ingress
  gateway holds its own SVID in a dedicated slot and uses it toward backends.
  The telemetry sink that would also read a held SVID is unbuilt.
  See the [identity model](/docs/concepts/identity) and the
  [workload identity lifecycle](/docs/concepts/workload-identity-lifecycle).
- **A deployed multi-node mesh.** The single-node control plane cannot place a
  backend on another node. Kernel service-steering support does not supply
  membership, replicated state, or multi-node workload ownership.
- **Multi-region federation.** The node is always `local`.
