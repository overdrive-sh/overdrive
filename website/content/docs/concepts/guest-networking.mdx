---
title: Guest networking
description: How Linux microVMs use ordinary TCP and UDP sockets over guest-neutral vsock flow transport, with shared node resources, host mTLS enforcement, and explicit flow ownership.
---

A Linux microVM uses ordinary application TCP and UDP sockets. Guest capture
translates those sockets into flows carried over vsock to the host. The host
opens destination sockets and applies mesh resolution and mTLS enforcement.
The VM attachment creates no per-VM host network namespace, veth, TAP, or bridge.

All supported workloads run as Linux microVMs. Shared node listeners, forwarding
capacity, and host policy resources serve their traffic while each allocation
keeps its own address, launch identity, flows, and cleanup ownership. The host
agent and VMM are host processes, not another workload execution mode.

## Application sockets and transport sockets have different jobs

A transported flow uses its own vsock stream. A request carries the flow's
identity and destination. A TCP application's bytes travel as a stream; a UDP
association uses length-prefixed datagram frames in both directions, including
zero-length datagrams. Replies preserve the destination identity the guest
application expects.

The host receives vsock, not guest TCP packets. It opens host-side TCP or UDP
sockets for the requested destination. Guest TCP behavior and host transport
behavior must therefore be considered separately.

The host protocol specifies flow requests, datagram frames, and clean or aborted
ends without a guest-kind field. The host owner and forwarder do not branch on
the guest kernel. Linux guests supply the implemented adapter; a
[non-Linux adapter](https://github.com/overdrive-sh/overdrive/issues/321) is
unbuilt.

## The guest captures connections before admitting flows

`overdrive-init` owns guest transport setup and runs as PID 1. Guest eBPF
programs capture application connects and UDP sends, preserve peer-address
behavior, and track socket release. TCP correlation binds the original
application socket and destination to the exact intake child before that child
can open a host flow.

The guest attaches seven programs before READY. Root-cgroup SockOps handles TCP
correlation; a C/CO-RE `fentry/tcp_check_req` program records a Fast Open
handshake candidate; the remaining cgroup programs capture connects and sends,
restore address observations, and handle socket release. The fentry hook runs
on handshake processing, not established data.

Aya `0.13.1` loads the Rust and C objects. Setup uses temporary pins to prepare
active socket storage and share the child correlation map between objects, then
removes the pins and staging
directory before program load and attachment. READY requires successful setup
and no remaining staging pins. Runtime maps and links remain process-owned.
Missing or incompatible kernel BTF, the target function, or required program
support refuses guest startup.

## The forwarder preserves socket backpressure

The `ovd_fwd` kernel module joins socket pairs on both sides of the VM boundary.
Socket callbacks queue a work item. That item peeks at source data, sends what
the target accepts, and consumes exactly that amount from the source. A stalled
target therefore leaves bytes in the source receive queue, where TCP windows
and vsock credit limit the sender.

A clean half-close propagates after the final accepted byte. An error aborts
the pair. The module uses per-CPU workqueues rather than a thread per pair.
Userspace owners control these pairs; they do not copy their forwarded payload.

The forwarder refuses TCP sockets with an installed upper-layer protocol,
including kTLS. [Transparent mTLS](/docs/concepts/transparent-mtls) owns TLS on
separate sockets. The VM mesh path includes a temporary userspace relay between
the host TLS endpoint and guest delivery; the whole mesh path is not a
userspace-free payload path.

## Every flow keeps its capacity until its owner releases it

The host admits guest flows against a node capacity of 65,536 pairs and a
per-allocation quota of 4,096 flows. These are admission bounds, not measured
node capacity or a fairness guarantee. Probe dials use node capacity and a
separate bounded probe allowance rather than the allocation's ordinary quota.
Exhaustion refuses the new flow.

Pending and half-closed flows retain their places. For a forwarded flow, the
kernel queues exactly one preallocated end record when the pair ends. The host
owner releases the places when it reads that record. A queued unread record
still counts as occupied during ownership audits. For a dialed stream, dropping
the stream or the owner's abort releases its places.

Pairs and watches belong to their control context. Releasing the context ends
its pairs and watches. Allocation teardown retires the lease, stops the VM and
its mTLS ownership, waits for guest-network teardown, and releases the address
lease only after the owner reports no remaining resources for that allocation.

## The node and guest must supply matching kernel support

The host image loads `ovd_fwd` before `overdrive serve`. The server never loads
a module or acquires module-loading privilege. Node startup checks the
forwarder, required listeners, descriptor budget, guest address prefix, and
mesh enforcement before accepting work. A guest prefix that overlaps a node
address or configured service VIP range refuses startup.

A guest kit binds a supported Linux kernel, its `ovd_fwd` module, and
`overdrive-init`. Init compares the module's release with the running kernel
before loading it, opens and probes the forwarder, and completes capture setup
before READY. An arbitrary kernel/rootfs pair is unsupported. See
[microVMs](/docs/concepts/microvms) for the artifact and confinement contract.

Cloud Hypervisor uses the kernel vhost-vsock backend, rendered as
`backend=vhost-kernel` with the allocation's leased CID. The required VMM source
includes the RESET-EXIT change; do not assume an upstream binary has that
behavior. This source integration does not provide a published fork release or
prebuilt download.

Node listeners support fixed or kernel-assigned ports through `ServerConfig`.
[TOML loading for those ports](https://github.com/overdrive-sh/overdrive/issues/327)
is unbuilt; there is no documented operator TOML key for them.

## A guest resolves public names through the same gateway address

A guest keeps one nameserver, the guest gateway `100.95.0.1`. The node's DNS
responder listens on that address over UDP and TCP port 53 and sorts every query
by name:

- **Mesh names.** A name of the form `<workload>.svc.overdrive.local` is answered
  by the node from its list of healthy services, as described in
  [service names](/docs/concepts/service-names). It never goes to an upstream
  resolver.
- **Other names under `overdrive.local`.** The node owns the whole zone. An
  unknown name in it gets NXDOMAIN and is never forwarded.
- **Every other name.** The node forwards the query to the host's resolvers and
  relays the reply.

The node forwards only queries addressed to the gateway. The responder's UDP
socket binds the wildcard address, so it also receives datagrams sent to the
node's other addresses. If another process holds the wildcard on port 53, the
responder falls back to one socket on the gateway address alone. It drops a non-mesh query that arrives that way, which
keeps the node from acting as an open resolver. The TCP listener binds the
gateway address alone.

### Which upstreams the node asks

The node reads the `nameserver` lines of the host's `/etc/resolv.conf` on every
forwarded query. The file is the only upstream source. Issue
[#384: configure the DNS forwarder's upstream resolvers in the worker node configuration](https://github.com/overdrive-sh/overdrive/issues/384)
tracks replacing it. A change to the file, including one made by DHCP after boot,
takes effect on the next query with no restart. Entries that name the gateway are
skipped, because forwarding to the gateway would loop. The node does not cache
answers.

It asks the upstreams in file order. Each attempt waits at most 1500 ms, and the
whole forward stops at 4000 ms. The first reply the node can decode is final,
whatever its response code, so an upstream that answers NXDOMAIN does not trigger
a second attempt. An undecodable reply counts as a failed attempt. When no upstream answers, or the file is absent, unreadable or
lists no usable nameserver, the guest receives SERVFAIL. That reply arrives well
inside the guest resolver's five-second timeout, and the guest sees a failed
lookup instead of a silent wait. Mesh answers over UDP do not depend on the
upstreams.

### The reply is relayed unchanged

The node sends the guest's query bytes upstream as they are and returns the
upstream's reply byte for byte. Every record type passes through, including AAAA,
HTTPS and SVCB. So do EDNS options and the DNSSEC bits, which means a guest that
validates DNSSEC itself still can.

One check applies to the answer section. If an A record, or the `ipv4hint` of an
HTTPS or SVCB record, falls inside an address range Overdrive owns, the node
does not relay the reply. A guest that connected to such an address would reach
the mesh instead of the name it asked for. The owned ranges are the mesh frontend
range `10.98.0.0/16`, the service VIP pool, and the guest prefix `100.95.0.0/16`.
The node returns the reply with its answer, authority and additional sections
emptied, keeps the upstream's response code, and adds an Extended DNS Error with
code 15, "Blocked", when the query carried EDNS. The guest sees a name with no
addresses. Private addresses outside those ranges, such as a corporate
`10.20.4.7`, pass through, so split-horizon DNS works.

The check does not cover AAAA records or addresses in the authority and
additional sections. Guests have no global IPv6 transport, and stub resolvers
ignore those sections. A public answer inside the guest prefix `100.95.0.0/16` is blocked. The rest of
the `100.64.0.0/10` shared address space, which some carrier-grade NAT and
overlay networks return, is relayed.

### TCP

A guest retries over TCP when a reply is truncated, and some clients use TCP
from the start. glibc, for example, writes its A and AAAA queries back to back
on one connection and waits for two replies. The node serves every framed query
on a connection in order on `100.95.0.1:53`, answers or forwards each one exactly
as it does over UDP, and writes the replies in query order. It closes the
connection when the client closes it.

A connection takes one forward permit when the node accepts it and holds that
permit until the connection closes. A five-second read deadline bounds each wait
for the next query, and a five-second write deadline bounds each reply. A
malformed frame, a short read or an expired deadline closes the connection. An
idle client therefore holds its permit for up to five seconds after its last
reply. The node sets no cap on the number of queries per connection. The permit
count and the deadlines bound a connection. A forwarded TCP query goes to the
upstream over TCP.

### Concurrent forwards are bounded

Each forward in flight holds a permit. `overdrive serve` raises its soft limit on
open file descriptors to the hard limit at startup, and the number of permits is
the soft limit minus a reserve for the node's other needs, divided by two, since
a TCP forward uses two descriptors. The node reports the permit count once at
startup in the `dns.forward.permits` event.

A query that finds no permit is shed at once. A UDP query gets SERVFAIL. A TCP
connection takes its permit when the node accepts it, and a connection that finds
none is closed unread. Under shedding, a TCP connection of any kind is closed,
mesh names included. This follows from the mechanism: the node does not know the
class of a connection's queries at accept, and it does not read a connection that
has no permit.

### What the node logs

The node logs a warning only at the edges of an episode, so a long outage does not
write a line per query:

| Event | Level | Meaning |
|---|---|---|
| `dns.forward.failed` | warn | A forward failed and no failure episode was open. The event names the cause, such as an absent resolver file or silent upstreams. Later failures in the same episode log nothing. |
| `dns.forward.recovered` | warn | An upstream answered at least 4000 ms after the last failure, which ends the episode. |
| `dns.forward.shed_started` | warn | The permits ran out and the node began shedding queries. |
| `dns.forward.shed_cleared` | warn | Load drained to half the permits. |
| `dns.forward.owned_range_blocked` | debug | A reply was blocked. The event names the query, address, range and upstream. |

### What we measured

We ran one deployment on a physical x86_64 server (Linux 7.0.0-38) with
`overdrive serve` and `overdrive deploy`. A VM guest with its default single
nameserver `100.95.0.1` resolved `api.anthropic.com`, `github.com`, `crates.io`
and `herdr.dev` in 4 to 28 ms each, and a bare TCP connection to the first
address on port 443 completed in 0 to 1 ms. A nonexistent name under `.invalid`
failed with `EAI_NONAME` in 5 ms. The guest used musl. We did not measure glibc
guests end to end through a deployment, lookups during an upstream outage, a blocked reply seen from a guest, or
behavior under saturation. Tests with scripted upstreams cover those paths on the
node side.

### Limits of guest DNS

- **Upstreams come only from the host's resolver file.** The node configuration
  has no setting for them. Issue
  [#384: configure the DNS forwarder's upstream resolvers in the worker node configuration](https://github.com/overdrive-sh/overdrive/issues/384)
  tracks lifting this.
- **No per-guest fairness.** Every guest query reaches the responder from the
  gateway address, so one guest that floods lookups can use all the permits and
  starve other guests' public lookups. Mesh answers over UDP are unaffected.
  Issue [#385: per-guest fairness for forwarded non-mesh DNS queries](https://github.com/overdrive-sh/overdrive/issues/385)
  tracks this.
- **No allowlist.** The node forwards every non-mesh name a guest asks for. Issue
  [#383: a per-workload allowlist for non-mesh DNS lookups](https://github.com/overdrive-sh/overdrive/issues/383)
  tracks this.
- **No health status for upstream failure.** A failing upstream appears in the
  node's log and as SERVFAIL in guests. No CLI command reports it. Issue
  [#386: node health conditions readable through the operator CLI](https://github.com/overdrive-sh/overdrive/issues/386)
  tracks this.
- **AAAA answers are not checked against owned ranges.** Guests have no IPv6
  transport. Issue
  [#308: IPv6 over the guest transport](https://github.com/overdrive-sh/overdrive/issues/308)
  tracks it. The check does not cover AAAA records.

## Supported traffic and current limits

- **TCP and mesh identity.** Guest flows reach host resolution and mTLS
  enforcement; incoming mesh streams can be delivered to guest applications.
  VM services declare listeners and use the service health lifecycle.
- **DNS and remote UDP.** Guest DNS resolves mesh and public names through the
  gateway, as described above. Connected and unconnected remote UDP preserve
  datagram boundaries, including empty datagrams.
- **Service-VIP UDP to a VM backend is unbuilt.** The guest-flow owner refuses a
  datagram addressed to a Service VIP with a policy error before it creates a host
  socket, so the datagram never reaches the host network. Issue
  [#310: UDP service delivery to VM workloads](https://github.com/overdrive-sh/overdrive/issues/310)
  tracks delivery. Remote UDP support does not imply that service path works.
- **Linux guests, single node.** The host protocol is guest-neutral, but that
  does not supply an adapter for another guest OS or a multi-node mesh.
- **CID generation recovery has an open crash window.** Replacement generation
  state can be lost across a `serve` crash; see
  [the recovery issue](https://github.com/overdrive-sh/overdrive/issues/325).
- **No measured density or startup promise.** Native 64-VM tests establish
  correctness, address uniqueness, traffic outcomes, refusal, and cleanup.
  [Performance measurements](https://github.com/overdrive-sh/overdrive/issues/326)
  remain separate work.

Hardware offload through
[vDPA or SR-IOV](https://github.com/overdrive-sh/overdrive/issues/329) is a
feasibility question, not an enabled networking mode.
