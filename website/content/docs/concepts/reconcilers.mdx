---

Overdrive's control plane is built from two primitives, and a **reconciler** is
the first: a pure function that looks at what should be true and what is true, and
returns the actions that close the gap. The runtime runs it on a loop, forever.
Its peer, the [workflow](/docs/concepts/workflows), runs a terminating sequence
once; [reconcilers and workflows](/docs/concepts/reconcilers-and-workflows)
explains how the two combine.

The [architecture overview](/docs/concepts/architecture#the-convergence-loop)
introduces the convergence loop at the system level. This page is the contract:
what a reconciler is, why it is a pure function, and what the runtime does around
it.

## A reconciler is a pure function

A reconciler implements one trait, and the shape of that trait is the whole idea:

```rust
#[async_trait::async_trait]
pub trait Reconciler: Send + Sync {
    const NAME: &'static str;
    type State: Send + Sync;
    type View: Serialize + DeserializeOwned + Default + Clone + Eq + Send + Sync;

    fn name(&self) -> &ReconcilerName;

    fn reconcile(
        &self,
        desired: &Self::State,
        actual: &Self::State,
        view: &Self::View,
        tick: &TickContext,
    ) -> (Vec<Action>, Self::View);

    // Project intent and observation into desired/actual. Impure and async —
    // the reconciler's only I/O. Every fact is read through the context.
    async fn hydrate_desired(&self, ctx: &HydrationContext<'_>, target: &TargetResource)
        -> Result<Self::State, HydrateError>;
    async fn hydrate_actual(&self, ctx: &HydrationContext<'_>, target: &TargetResource)
        -> Result<Self::State, HydrateError>;

    // Declare how the runtime wakes this reconciler. Both default-provided.
    fn resync_schedule(&self) -> Option<ResyncSchedule> { None }
    fn interests(&self) -> &'static [ObservationRowKind] { &[] }
}
```

`reconcile` is the whole *pure* computation. The two `hydrate_*` methods project
its inputs — the reconciler's only impure surface, covered in
[the next section](#the-reconciler-hydrates-its-own-inputs) — and the two
default-provided hooks below only declare *when* the runtime runs it, covered in
[how the runtime wakes a reconciler](#how-the-runtime-wakes-a-reconciler).

`reconcile` takes the desired and actual state its hydration methods produced,
the reconciler's own prior memory, and a time snapshot — and returns a list of
actions plus its next memory. It is
**synchronous**: no `async`, no `.await`. It does no I/O, opens no socket, touches
no database, and reads no clock except through `tick`. The same inputs produce a
byte-identical result every time.

That purity is the design, not an accident of it. A function with no hidden inputs
can be replayed: feed it the same desired, actual, view, and tick under
[simulation](/docs/concepts/deterministic-simulation-testing) and it produces the
same actions, every run, from a seed. The control plane is testable as a function
instead of against a live cluster. `reconcile` takes data and returns data — a
list of actions to perform and the next memory to persist. It performs nothing
and writes nothing itself.

## The reconciler hydrates its own inputs

`reconcile` is pure, so it cannot read intent or observation itself. Two `async`
methods do that — `hydrate_desired` and `hydrate_actual` — and they are the
reconciler's only impure code. Each reads the facts for one target and projects
them into the typed `desired` or `actual` that `reconcile` consumes. The runtime
calls both before every tick and hands the results straight to `reconcile`.

They read through a `HydrationContext` the runtime builds once per tick: a bundle
of the intent and observation stores, the driver registry and host-state handle,
and four narrow read-ports — `ListenerFacts`, `ServiceVipView`, `WorkflowLiveSet`,
`HeldSvidView`. A reconciler fetches every fact through a port and never reaches a live
runtime field or calls the host directly. That constraint is what makes the loop
testable: each hydration input is a port, so
[simulation](/docs/concepts/deterministic-simulation-testing) supplies a `Sim*`
implementation for every one and drives the reconciler against fabricated intent,
observation, and host state — no live cluster, no real clock. Reach around a port
to a concrete field and you hydrate an input the harness cannot substitute; the
replay guarantee stops holding for it. The port is the seam.

Contract and implementation live in separate crates on purpose. The `Reconciler`
trait, the read-port traits, and `HydrationContext` are core — the shared source
of truth every reconciler and adapter agrees on. The reconciler implementations,
`hydrate_*` bodies included, consume those ports, so they are adapters and live in
`overdrive-reconcilers`. Core holds the contract; the adapter crate holds the code
that reads the world.

## Observe, diff, converge

The loop calls `reconcile` every tick with freshly hydrated desired and actual.
The reconciler recomputes the gap each time; it never assumes a past action took
effect. A half-finished operation is just a gap the next pass closes — a crashed
allocation is started again, a drifted dataplane map is rewritten, a
half-provisioned interface is completed rather than adopted as-is. The control
plane converges toward the declared state or keeps trying; it does not strand
half-applied state for someone to fix by hand.

This is why the *computation* is level-triggered. `reconcile` reads the current
state of the world, not a running tally of events, and recomputes the gap from
what it is handed. A stale or missing signal cannot leave it holding a wrong
decision: the next pass reads what is actually true and closes whatever gap
remains. What *wakes* the reconciler to run that computation — a change, a timer,
another reconciler — is a separate question, and the answer is
[how the runtime wakes a reconciler](#how-the-runtime-wakes-a-reconciler).

## How the runtime wakes a reconciler

The runtime does not run every reconciler on every tick. It runs one when its
target is worth re-evaluating. Most reconcilers declare what that means through
one of two default-provided hooks; a few instead take their work from another
reconciler, covered at the end.

`interests()` declares an **edge wake**: the observation-row kinds whose change
should re-evaluate the reconciler. A reconciler that converges on an observation
row — the running-allocation set, the service backends — lists the kinds it
reads. One runtime task, the **interest router**, subscribes to the observation
store's change feed once and, on every accepted row change, submits an evaluation
to each reconciler that declared interest in that kind. An allocation exiting
writes a single `alloc_status` row, and the router wakes the four reconcilers
that read it — workload lifecycle, backend discovery, service lifecycle, and SVID
lifecycle — without the writer naming any of them.

`resync_schedule()` declares a **level wake**: a period and a scope —
"re-evaluate `node/<id>` every 30 seconds." A reconciler that hydrates its actual
state from the host instead of from a row has no change feed to watch — nothing
writes a row when a microVM dies or an interface drifts — so the clock is its
only trigger. `VmReclamation` declares a 30-second sweep of the local node; the
loop resolves the scope to a concrete target and submits the evaluation. This is
why the loop holds no reconciler names and no hardcoded intervals: a reconciler
that needs a periodic sweep declares one, and the loop reads the declaration.

Which hook fits depends on where the reconciler reads its actual state: from an
observation row (declare an interest, and the router wakes it on a change) or from
the host (declare a resync schedule, and the clock wakes it).

An edge wake alone is fragile — one dropped change would strand a reconciler
until some unrelated change happened to wake it. So the edge path keeps a
level-triggered backstop: the interest router **relists the whole snapshot on a
fixed period**, re-deriving every wake it might have missed. A lost change only
delays a re-evaluation the relist delivers anyway. That is what makes the
level-triggered guarantee hold end to end — the reconciler always recomputes from
current state, and the runtime always wakes it again.

A reconciler can also wake another directly by emitting
`Action::EnqueueEvaluation`, so one reconciler's output becomes another's
trigger. The two hooks are the declarative wake surface; this action is the
producer-push path that complements them.

## The View is typed memory

A reconciler's only persistent state is its **View** — a typed struct it returns
at the end of each tick and receives at the start of the next. The author derives
the bounds the trait demands
(`Serialize + DeserializeOwned + Default + Clone + Eq + Send + Sync`) and writes
nothing else for persistence. The runtime owns the rest end to end: it
CBOR-encodes the View into a redb-backed store at `reconcilers/memory.redb`,
bulk-loads every View once at startup, and serves them from memory on every tick
thereafter. A reconciler author never writes SQL, never
opens a database handle, never declares a schema.

Two properties make this durable across a crash:

- **Write-through, flushed before dispatch.** After `reconcile` returns, the
  runtime persists the next View and flushes it to disk *before* it dispatches the
  tick's actions. On a crash between the flush and the dispatch, the next boot
  reloads the View and convergence resumes — the acknowledged memory is never
  lost.
- **Persist inputs, not derived state.** The View holds the inputs a decision
  depends on, not the decision's output. A retry reconciler stores `attempts` and
  `last_failure_seen_at` and recomputes the next-attempt deadline every tick
  against the live backoff policy — rather than a `next_attempt_at` field, which
  would freeze today's policy into the stored value and silently ignore a policy
  change until the row aged out.

## Time is an input

A reconciler cannot call `Instant::now()`. Reading the clock directly is exactly
the non-determinism the replay harness cannot control, so time arrives as data, in
the `TickContext` the runtime passes to every `reconcile`:

- `now` — a monotonic snapshot for in-process deadline arithmetic.
- `now_unix` — a persistable wall-clock snapshot, for deadlines that must survive
  a restart.
- `deadline` — this tick's budget.
- `tick` — a monotonic counter, useful as a deterministic tie-breaker.

The snapshot is taken once per tick, so every `reconcile` sees a single consistent
"now." That single consistency is part of what makes the function pure over its
inputs.

## Actions are data; the shim runs them

`reconcile` returns `Vec<Action>` — typed descriptions of what should happen, not
the happening itself. A separate **action shim** executes them: `StartAllocation`
launches a process, `DataplaneUpdateService` programs an eBPF map,
`WriteServiceBackendRow` records observation, `StartWorkflow` launches a durable
sequence. This boundary is load-bearing. It keeps `reconcile` pure and puts every
side effect behind one gate the runtime drives, which is what lets the loop be
replayed. One of those actions, `EnqueueEvaluation`, wakes another reconciler —
the producer-push path from
[how the runtime wakes a reconciler](#how-the-runtime-wakes-a-reconciler).

## The reconcilers that ship

Eight reconcilers run in `overdrive serve`:

- **WorkloadLifecycle** — drives allocations toward the declared replica count
  and owns every restart. A crash and a liveness kill both draw down its one
  `restart_counts` budget, and it backs off on repeated failure. It is the sole
  restart authority; no other reconciler restarts anything.
- **ServiceLifecycle** — drives a service through its health gates from probe
  results: not `Stable` until startup passes, not sent traffic until readiness
  passes. On a terminal liveness failure it emits `StopAllocation` and stops
  there — the restart belongs to WorkloadLifecycle's single budget, not the
  service layer.
- **BackendDiscoveryBridge** — turns live allocations into `service_backends`
  observation rows.
- **ServiceMapHydrator** — programs the eBPF service map when the backend set
  drifts, emitting `DataplaneUpdateService`.
- **WorkflowLifecycle** — the bridge to the workflow engine: re-emits
  `StartWorkflow` for a workflow instance that should be running but has no live
  task. See [reconcilers and workflows](/docs/concepts/reconcilers-and-workflows).
- **SvidLifecycle** — issues a SPIFFE SVID for every running allocation and drops
  it when the allocation stops, emitting `IssueSvid` / `DropSvid`. A near-expiry
  re-issue is a single audited action, not a workflow.
- **VmReclamation** — reclaims microVM allocations and discards stranded host
  artifacts. It reads its actual state from the host, not from a row, so it is the
  host-backed reconciler that declares a `resync_schedule` — a 30-second sweep of
  the local node — rather than an interest.
- **NoopHeartbeat** — a proof-of-life reconciler that emits a no-op every tick; it
  anchors the "reconcilers are pure" invariant the test suite checks.

Adding a behaviour to the control plane means adding a reconciler, not threading
logic through the loop. The loop does not know what the reconcilers do.

## Working with workflows

A reconciler runs forever; some operations instead need a terminating, durable
sequence — rolling a certificate through four steps, migrating an allocation
between nodes. For those a reconciler starts a
[workflow](/docs/concepts/workflows) by emitting `Action::StartWorkflow`, and
later observes the workflow's terminal status to converge the instance.
`WorkflowLifecycle` is the reconciler that ships for exactly this. The full loop —
including how a workflow emits actions back into the same pipeline — is in
[reconcilers and workflows](/docs/concepts/reconcilers-and-workflows).
