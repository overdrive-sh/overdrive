Every Overdrive workload runs as a Cloud Hypervisor microVM: its own Linux
kernel, its own memory, isolated from the host by the same hardware
virtualization a cloud instance uses. A spec's `[vm]` block says what to boot and
run. Its top-level section — `[service]` or `[job]` — says whether the workload
serves traffic or runs to completion.

<Callout title="The short version">
	A `[vm]` block boots a Cloud Hypervisor microVM from a kernel and rootfs you
	supply. The allocation reaches `Running` only after the guest has booted, and
	its terminal state carries the guest's real exit code — not the hypervisor's.
	The hypervisor process runs non-root, seccomp-filtered, and Landlock-confined.
	Services and jobs both run as microVMs, and every guest joins the encrypted
	mesh.
</Callout>

## Why every workload is a microVM

A container or a plain process shares the host kernel. That is the boundary an
attacker crosses with a single kernel bug: every workload on the node sits
behind the same kernel.

A microVM moves the boundary down to the hardware. The guest runs its own kernel
on virtual CPUs the host schedules but does not share, so a kernel exploit inside
the guest lands in the guest, not the host. That buys two things a shared kernel
cannot offer. The workload can run a kernel that isn't the host's — a different
version, different modules, a different configuration. And the isolation holds
against a guest that has been fully compromised, because the wall is the CPU's
virtualization boundary, not a kernel permission check.

The cost is real and worth naming. A microVM boots a kernel and mounts a
filesystem before the workload runs, so it starts slower than a process that just
`exec`s a binary. It also needs a kernel image and a root filesystem, where a
process needs only a binary. Overdrive pays that cost for every workload in
exchange for hardware isolation by default.

## An honest exit code

The failure this driver is built to avoid: a VM boots, runs a workload that
crashes, and shuts down cleanly — while the platform reports success. The
hypervisor exited zero. The workload did not.

Overdrive reports the guest's outcome, not the hypervisor's. `overdrive-init`
runs as process 1 inside the guest. It opens a channel to the host over vsock
before the guest has any network, signals once the guest has booted, and reports
the workload's real exit status when it ends. Two consequences follow. The
allocation reaches `Running` only after that boot signal arrives, so a guest that
never starts its init never reads as running. And the terminal state carries the
workload's own exit code, so a crash inside the guest shows up as a crash in
`overdrive workload describe`, not a clean exit.

This is what makes a microVM a first-class workload rather than a black box the
platform launches and hopes for. Restarts and their backoff run off the same
honest exit signal.

## The guest joins the mesh

Each allocation gets its own network namespace, with a veth pair to the host and
a TAP device that the guest uses as its network interface. The platform assigns
the guest's address and points the guest's DNS resolver at the node's
[service-name responder](/docs/concepts/service-names). The spec carries no
network settings.

Every connection the guest opens crosses the host end of its veth pair, where the
[transparent-mTLS proxy](/docs/concepts/transparent-mtls) captures it. A
service's declared listener ports are reachable through the same proxy. The guest
holds no certificate and no key. Health probes run on the host and target the
guest's address.

## How it stays confined

The `cloud-hypervisor` process is a host process, and Overdrive treats it as one.
It runs inside the allocation's own cgroup and network namespace. On top of that
placement, the hypervisor takes a stricter security posture, and the guest sits
behind the hardware boundary of the VM itself:

- **Non-root.** The hypervisor drops to an unprivileged user before it boots the
  guest.
- **Seccomp-filtered.** Cloud Hypervisor's default seccomp filters restrict the
  syscalls each of its threads can make.
- **Landlock-confined.** A Landlock ruleset restricts the filesystem paths the
  process can open to the artifacts that VM needs — its kernel, its rootfs copy,
  its own socket directory — and nothing else.

If that confinement cannot be applied, the workload does not run. The driver fails
closed rather than launch an unconfined hypervisor.

State the boundary precisely: this is KVM plus seccomp plus Landlock plus cgroup
and namespace placement. It is not a jailer-style chroot jail, and the guest does
not run in its own PID namespace on the host. The isolation is strong and it is
specific; calling it "a full jail" would overclaim.

## You supply the kernel and rootfs

A `[vm]` spec names two host paths: a bootable kernel image and an ext4 root
filesystem. Overdrive builds neither — there is no image factory and no registry
pull. You bring the artifacts; the driver boots them.

Each launch clones the rootfs first, so the running guest writes to its own copy
and the master image stays untouched. The clone is a copy-on-write reflink —
near-instant, and it costs no extra disk until the guest writes. The rootfs must
sit on a filesystem that supports reflinks; there is no full-copy fallback, and a
node that cannot reflink does not run VMs at all. The clone and its VM are torn
down when the allocation ends.
