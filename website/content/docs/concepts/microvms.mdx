A `[vm]` workload runs as a Cloud Hypervisor microVM: its own Linux kernel, its
own memory, isolated from the host by the same hardware virtualization a cloud
instance uses. This is Overdrive's only supported workload execution mode. You
deploy it with the same `overdrive deploy`, describe it with the same
`overdrive workload describe`, and stop it with the same `overdrive job stop` —
the driver underneath differs, the verbs do not.

<Callout title="The short version">
	A `[vm]` block boots a Cloud Hypervisor microVM from a kernel and rootfs you
	supply. The allocation reaches `Running` only after the
	guest has booted, and its terminal state carries the guest's real exit code —
	not the hypervisor's. The hypervisor process runs non-root, seccomp-filtered,
	and Landlock-confined. A microVM runs as a `[job]` or `[service]` on a single
	node. Shared volumes and snapshots are not built — see
	[Where it stands](#where-it-stands).
</Callout>

## The guest kernel is the workload boundary

Every workload runs behind hardware virtualization with its own guest kernel.
The node agent and Cloud Hypervisor remain host processes, but application
commands execute inside the guest. A guest kernel exploit must also cross the
virtualization and VMM boundary to reach the host.

The guest kernel can differ from the host kernel, but it must come from a
supported guest kit. Each launch needs a kernel image and root filesystem,
then boots the guest before releasing the application command. These artifact
and lifecycle requirements apply to every supported workload.

## An honest exit code

The failure this driver is built to avoid: a VM boots, runs a workload that
crashes, and shuts down cleanly — while the platform reports success. The
hypervisor exited zero. The workload did not.

Overdrive reports the guest's outcome, not the hypervisor's. A small agent runs
as process 1 inside the guest. It opens a channel to the host over vsock before
the guest has any network, signals once the guest has booted, and reports the
workload's real exit status when it ends. Two consequences follow. The allocation
reaches `Running` only after that boot signal arrives, so a guest that never
starts its init never reads as running. And the terminal state carries the
workload's own exit code, so a crash inside the guest shows up as a crash in
`overdrive workload describe`. Init writes EXIT and closes its beacon channel
before powering off. The host drains the report before finalizing the VMM exit;
a zero VMM exit is not evidence of a zero workload exit.

This is what makes a microVM a first-class workload rather than a black box the
platform launches and hopes for. Restart and backoff decisions use that guest-reported exit signal.

## How it stays confined

The `cloud-hypervisor` process is a host process, and Overdrive treats it as one.
It runs inside the allocation's cgroup and shares the host network namespace.
VM attachment creates no per-VM host namespace, veth, TAP, or bridge. The guest
uses vsock flow transport to reach shared node networking; its own kernel remains
behind the hardware virtualization boundary. The hypervisor is also:

- **Non-root.** The hypervisor drops to an unprivileged user before it boots the
  guest.
- **Seccomp-filtered.** Cloud Hypervisor's default seccomp filters restrict the
  syscalls each of its threads can make.
- **Landlock-confined.** A Landlock ruleset restricts the filesystem paths the
  process can open to the artifacts that VM needs — its kernel, its rootfs copy,
  its own socket directory — and nothing else.

If that confinement cannot be applied, the workload does not run. The driver fails
closed rather than launch an unconfined hypervisor.

State the boundary precisely: this is KVM plus seccomp plus Landlock plus cgroup
placement. It is not a jailer-style chroot jail, and the guest does
not run in its own PID namespace on the host. The isolation is strong and it is
specific; calling it "a full jail" would overclaim.

## You supply the kernel and rootfs

A `[vm]` spec names two host paths: a bootable kernel image and an ext4 root
filesystem. There is no image factory or registry pull. You supply artifacts
from a matching guest kit: a supported Linux kernel, its `ovd_fwd` module, and
`overdrive-init`. Init checks the module release against the running kernel
before READY; arbitrary kernels are unsupported. See
[guest networking](/docs/concepts/guest-networking#the-node-and-guest-must-supply-matching-kernel-support)
for the host and guest prerequisites.

Each launch clones the rootfs first, so the running guest writes to its own copy
and the master image stays untouched. The clone uses a copy-on-write reflink
and allocates private data blocks as the guest writes. The rootfs must
sit on a filesystem that supports reflinks; there is no full-copy fallback, and a
node that cannot reflink does not run VMs at all. The clone and its VM are torn
down when the allocation ends.

## Where it stands

A `[vm]` workload boots, runs, and reports honestly through `overdrive serve` and
`overdrive deploy` on a single node. The current boundaries:

- **Jobs and services.** A `[vm]` block can run a job to completion or supply a
  service with declared listeners and health checks.
- **No shared volumes.** A microVM writes to its own rootfs copy, discarded when
  it ends. A persistent or host-shared volume is unbuilt.
- **No snapshots or persistence.** The driver boots a VM and tears it down.
  Snapshot, restore, and persistent stateful microVMs are outside this scope.
- **Fixed size.** `[resources]` sizes the guest's vCPUs and memory at boot.
  Resizing a running VM is rejected — CPU and memory hotplug are not wired.
- **Shared node networking.** Guest capture and vsock transport connect Linux
  guests to DNS, remote TCP/UDP, and the host mesh mTLS path. Guest-to-Service-VIP
  UDP delivery to a VM backend remains
  [unbuilt](https://github.com/overdrive-sh/overdrive/issues/310). See
  [guest networking](/docs/concepts/guest-networking).
- **You supply the artifacts.** The kernel and rootfs are host paths you provide.
  Building them from an image or a Dockerfile is unbuilt.
