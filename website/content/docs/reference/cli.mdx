`overdrive` is the single binary for both running the control plane and
operating it. This page documents the command surface that ships today. Phase 1
is single-node: there is no node-join flow and no multi-region configuration, so
the commands here assume one machine running one control plane.

## How the CLI finds the server

Every command except `serve` talks to a running control plane, and they all
learn where it is the same way: from `~/.overdrive/config`. When `serve` binds
its listener it writes three things to that file as one unit — the endpoint, the
CA pin, and your operator certificate. Later commands read the unit back.

The trust posture is fixed, not tunable per command:

- There is **no `--endpoint` flag** and **no `OVERDRIVE_ENDPOINT` variable**. The
  config file is the only source of the server address.
- There is **no `--insecure` flag**. `overdrive --insecure ...` is rejected as an
  unknown argument. The connection is mutually authenticated or it does not
  happen.

To point the CLI at a different control plane, swap the active config directory
with `OVERDRIVE_CONFIG_DIR`. That moves the whole trust triple — endpoint, CA
pin, and certificate together — never just the address.

## `overdrive serve`

Start the control plane on a TLS-bound listener. This is the one command that
does not read an existing config; it writes one.

```bash
overdrive serve [--bind <ADDR>] [--data-dir <PATH>] \
  [--gateway-address <IPV4> --gateway-certified-key-id <ID> \
   --gateway-certificate-chain <PATH> --gateway-private-key <PATH>]
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `--bind <ADDR>` | `127.0.0.1:7001` | Socket address to bind. Pass `127.0.0.1:0` to request an ephemeral port. |
| `--data-dir <PATH>` | `dirs::data_dir()/overdrive` | Parent directory for the IntentStore file, the per-primitive state files, and the trust-triple config. |
| `--gateway-address <IPV4>` | none | Host IPv4 address the public ingress gateway binds. The port is fixed at TCP/443. |
| `--gateway-certified-key-id <ID>` | none | Identity the manual certificate source installs. A Route names it in `certified_key`. |
| `--gateway-certificate-chain <PATH>` | none | Absolute path to the leaf-first PEM certificate chain. |
| `--gateway-private-key <PATH>` | none | Absolute path to the PKCS#8 PEM private key. |

The four `--gateway-*` flags go together. Pass all four to enable the
[public ingress gateway](/docs/concepts/public-ingress-gateway) or none to leave
it disabled. A partial set fails with a gateway configuration error before
`serve` takes any startup action. The certificate files must be regular files
(not symlinks) owned by the effective user, and the key file must carry no group
or other permission bits. See
[Expose a service publicly](/docs/how-to/expose-a-service-publicly) for the full
file requirements.

The recorded endpoint names the *resolved* port, not the requested one — so a
`--bind 127.0.0.1:0` server writes the concrete port it actually got, and the
next command connects to it without you reading the port off the logs.

Node startup also validates shared guest networking: the host must have its
matching `ovd_fwd` module loaded, and required listeners, capacity, and
address-prefix checks must pass. See
[guest networking](/docs/concepts/guest-networking#the-node-and-guest-must-supply-matching-kernel-support).
Node vsock listener ports are configured through `ServerConfig`;
[TOML loading](https://github.com/overdrive-sh/overdrive/issues/327) is unbuilt.
The `--bind` flag above controls the operator API, not guest flow listeners.

## `overdrive deploy`

Deploy a workload from a TOML spec file. See
[Deploy a workload](/docs/how-to/deploy-a-workload) for the spec shape and a
worked run. Every supported workload uses a `[vm]` driver table. The command
and arguments execute inside the guest. HTTP and TCP are the supported health
probe mechanics.

```bash
overdrive deploy <SPEC> [--detach]
```

| Argument / flag | Meaning |
| --- | --- |
| `<SPEC>` | Path to a TOML spec file. |
| `--detach` | Wait only for the IntentStore commit; do not stream lifecycle events. |

Deploy is idempotent on the spec's content hash. A new spec reports `Inserted`.
Re-deploying identical content reports `Unchanged` and commits nothing.
`--detach` consumes the commit acknowledgement and exits. Streaming Service
deploy waits for `Stable`, a recorded give-up or stop, or its progress deadline.
On an unchanged Service, the stream reads the current allocation's recorded
verdict before waiting for new events.

For a Service, an omitted startup section gates `Stable` on the guest reporting
every declared TCP and UDP listener. `Running` alone does not satisfy this gate.
`health_check.startup = []` explicitly opts out. The default startup deadline
is 60 seconds. The Service stream's progress deadline is the greater of 90
seconds and the startup deadline plus 30 seconds. A timeout does not end the
restart lifecycle. Its optional `last attempt` detail is context, not the final
give-up cause. Use `overdrive workload describe <ID>` to inspect later attempts.

A streaming Service deploy exits `0` on `Stable` or an operator stop and `1`
on a Service failure or progress timeout. A local TOML parse error also exits
`1`. Pre-acceptance transport and server errors exit `2`. `--detach` reports
only the intent commit, so its success does not assert Service health.

### Route documents

`deploy` also accepts a public Route document. A Route file holds exactly one
top-level `[route]` table, and unknown fields are rejected.

```toml
[route]
id = "public-api"
hostname = "api.example.com"
path = "/"
path_match = "segment_prefix"
certified_key = "api-origin"

[route.target]
service = "api"
port = 8080
protocol = "tcp"
```

| Field | Meaning |
| --- | --- |
| `id` | Route identifier. |
| `hostname` | One exact DNS name. Wildcards, IP literals, and a trailing dot are rejected. |
| `path` | Absolute raw path with no query or fragment. |
| `path_match` | `exact` or `segment_prefix`. |
| `certified_key` | The id passed to `serve --gateway-certified-key-id`. |
| `[route.target]` | `service` (a deployed Service id), `port`, and `protocol`, which must be `tcp`. |

Deploying a Route prints three lines:

```text
Route 'public-api' declared.
Generation: ...
Endpoint: ...
```

The first line reads `declared`, `replaced`, or `unchanged`. The output is the
same with or without `--detach`. A node holds one Route. Deploying a Route with a
different `id` returns a 409 conflict. When `serve` started without the gateway
flags, a Route deploy is refused with `gateway_disabled`. See
[the public ingress gateway](/docs/concepts/public-ingress-gateway) for what a
Route does.

## `overdrive job`

Workload lifecycle.

```bash
overdrive job stop <ID>      # stop the workload with this id
```

`stop` declares that the named workload should no longer run; the control plane
records the intent and its allocations wind down. To read back what is running,
use [`workload describe <ID>`](#overdrive-workload) — `job list` is parsed but not
yet wired (see [Accepted but not yet functional](#accepted-but-not-yet-functional)).

## `overdrive workload`

Workload lifecycle — restart and inspect.

```bash
overdrive workload restart <ID>    # replace the workload's backend with a fresh one
overdrive workload describe <ID>   # spec digest + live allocation rows
```

`restart` replaces a declared workload's running backend instance with a fresh
one. The control plane tears down the current allocation and starts a new one
from the same spec.

`describe` returns the canonical `spec_digest` the control plane holds for the
workload and the number of live allocations for it. This is the command to
confirm that a deploy took effect: match the returned digest against the spec you
deployed, and check the allocation count.

For each running allocation that has been issued an identity, the `describe`
output also lists its current certificate — serial, SPIFFE identity, issuer
serial, and expiry — drawn from the issuance audit trail. These are the facts of
issuance only; the certificate bytes and the private key never appear. The
section is omitted for allocations with no issued certificate.

## `overdrive node`

Node inspection.

```bash
overdrive node list          # list nodes the control plane knows about
```

## `overdrive cluster`

Cluster mode and membership.

```bash
overdrive cluster status
```

`cluster status` reports the control plane's current mode — `single` on a fresh
node.

## Accepted but not yet functional

Two subcommands are part of the `clap` argv surface — they parse, and
`--help` lists them — but their handlers are not wired in Phase 1. Each
currently logs `command not yet wired` and exits `0` without doing anything:

| Command | State |
| --- | --- |
| `overdrive job list` | Parsed, no handler. Use [`workload describe <ID>`](#overdrive-workload) to inspect a workload today. |
| `overdrive cluster upgrade --mode <single\|ha> --peers <list>` | Parsed, no handler. High-availability mode is design-stage; Phase 1 is single-node. |

They are documented here so the behavior is not mistaken for a bug: the command
appears to succeed (exit `0`) but has no effect.

## Global behavior

- `overdrive --version` prints the build version; `overdrive --help` and
  `overdrive <command> --help` print usage.
- Unknown flags are rejected rather than ignored — there is no silent
  pass-through for options like `--insecure`.
