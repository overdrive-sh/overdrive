title: Write a reconciler
description: Add a behaviour to the Overdrive control plane by writing a reconciler — implement the trait as a pure function, keep its memory in a typed View, emit actions instead of doing I/O, and register it.
---

This guide shows how to add a behaviour to the control plane by writing a
reconciler: a pure function the runtime drives on a loop. It is written for
engineers extending Overdrive itself — reconcilers are authored in Rust, and
adding a control-plane behaviour means adding one. For the model behind the steps —
purity, the View, the action boundary — read [Reconcilers](/docs/concepts/reconcilers)
first; this guide assumes it.

<Callout title="Reconcilers are internal">
	You author a reconciler in Rust inside the control-plane crates and register it
	at boot. There is no `overdrive` command that adds one at runtime.
</Callout>

## Implement the Reconciler trait

A reconciler is a type that implements `Reconciler`: a name, a `State` projection,
a `View` for its memory, one pure `reconcile`, and two `hydrate_*` methods that
read its inputs. The smallest possible one observes nothing and emits a no-op
every tick:

```rust
use overdrive_core::reconcilers::{
	Action, HydrateError, HydrationContext, Reconciler, ReconcilerName, TargetResource,
	TickContext,
};

#[async_trait::async_trait]
impl Reconciler for NoopHeartbeat {
	const NAME: &'static str = "noop-heartbeat";

	type State = ();
	type View = ();

	fn name(&self) -> &ReconcilerName {
		&self.name
	}

	fn reconcile(
		&self,
		_desired: &Self::State,
		_actual: &Self::State,
		_view: &Self::View,
		_tick: &TickContext,
	) -> (Vec<Action>, Self::View) {
		(vec![Action::Noop], ())
	}

	// Observes nothing, so both hydration methods produce the unit state.
	async fn hydrate_desired(
		&self,
		_ctx: &HydrationContext<'_>,
		_target: &TargetResource,
	) -> Result<Self::State, HydrateError> {
		Ok(())
	}

	async fn hydrate_actual(
		&self,
		_ctx: &HydrationContext<'_>,
		_target: &TargetResource,
	) -> Result<Self::State, HydrateError> {
		Ok(())
	}
}
```

`const NAME` is the kebab-case anchor; the type's constructor builds a
`ReconcilerName` from it once. `State` and `View` are your own typed projections —
both `()` here, because a heartbeat observes nothing and remembers nothing.

## Hydrate desired and actual

`reconcile` is pure, so it cannot read intent or observation. The two `async`
`hydrate_*` methods do — they are the only impure code you write. Each derives an
id from `target`, reads the facts it needs through the `HydrationContext` the
runtime builds per tick, and returns your typed `State`:

```rust
async fn hydrate_desired(
	&self,
	ctx: &HydrationContext<'_>,
	target: &TargetResource,
) -> Result<Self::State, HydrateError> {
	// Read declared intent through the context, never around it.
	let bytes = ctx
		.intent_store
		.get(&intent_key(target))
		.await
		.map_err(|e| HydrateError::IntentRead(e.to_string()))?;
	Ok(project_desired(bytes))
}

async fn hydrate_actual(
	&self,
	ctx: &HydrationContext<'_>,
	target: &TargetResource,
) -> Result<Self::State, HydrateError> {
	// Read observation through the context, filter to this target.
	let rows = ctx
		.observation_store
		.alloc_status_rows()
		.await
		.map_err(|e| HydrateError::ObservationRead(e.to_string()))?;
	Ok(project_actual(rows, target))
}
```

Read every fact through `ctx`, never around it. The context carries everything a
reconciler hydrates from: the intent and observation stores, the driver registry,
host state, and four narrow read-ports — `ListenerFacts`, `ServiceVipView`,
`WorkflowLiveSet`, `HeldSvidView`. Reach
for a live runtime field or a host call instead and you hydrate an input the
simulation harness cannot substitute, which breaks the replay the whole design is
built on. If you need a fact the context does not carry, add a read-port for it
rather than a direct read.

## Compute the gap — and nothing else

A real `reconcile` observes the gap between desired and actual, emits actions to
close it, and returns its next memory:

```rust
fn reconcile(
	&self,
	desired: &Self::State,
	actual: &Self::State,
	view: &Self::View,
	tick: &TickContext,
) -> (Vec<Action>, Self::View) {
	let mut actions = Vec::new();
	if actual.running < desired.replicas {
		actions.push(Action::StartAllocation { /* … */ });
	}
	(actions, view.clone())
}
```

Three rules the runtime enforces:

- **No I/O, no `async`.** `reconcile` is synchronous and returns data. It never
  awaits, opens a socket, or writes a store — side effects are actions, covered
  below.
- **No clock but `tick`.** Read time from `tick.now` / `tick.now_unix`, never
  `Instant::now()`. The direct call breaks deterministic replay, and the lint gate
  rejects it.
- **Deterministic.** The same `(desired, actual, view, tick)` must produce a
  byte-identical `(actions, next_view)`. That is what lets the whole control plane
  be replayed under simulation.

## Keep memory in the View — store inputs, not outputs

A reconciler's only persistent state is its `View`. Derive the bounds the trait
demands and let the runtime persist it:

```rust
#[derive(Serialize, Deserialize, Default, Clone, PartialEq, Eq)]
pub struct RetryMemory {
	pub attempts: u32,
	pub last_failure_seen_at: UnixInstant,
}
```

Store the inputs a decision depends on, not the decision. A retry reconciler keeps
`attempts` and `last_failure_seen_at` and recomputes the next-attempt deadline each
tick from the live backoff policy — never a persisted `next_attempt_at`, which
would freeze today's policy into the stored value and ignore a later change to it.
The runtime CBOR-encodes the View, flushes it to disk before dispatching the tick's
actions, and reloads it on the next boot. You never touch a database.

## Emit actions for every effect

`reconcile` returns `Vec<Action>`; the action shim runs them behind its single I/O
boundary. To start a process, return `Action::StartAllocation`; to program the
dataplane, `Action::DataplaneUpdateService`; to wake another reconciler,
`Action::EnqueueEvaluation`; to launch a durable sequence,
`Action::StartWorkflow` (see
[reconcilers and workflows](/docs/concepts/reconcilers-and-workflows)). Never
perform the effect inside `reconcile` — return the action and let the shim execute
it.

## Declare how it wakes

By default the runtime wakes a reconciler only when another reconciler hands it
work. Most reconcilers instead declare their own trigger through one of two hooks;
pick the one that matches where the reconciler reads its actual state.

If it converges on an observation row, declare an **interest** in that row's kind.
The interest router re-evaluates the reconciler whenever a row of that kind
changes:

```rust
fn interests(&self) -> &'static [ObservationRowKind] {
	&[ObservationRowKind::AllocStatus]
}
```

If it reads its actual state from the host — a cgroup, an interface, a VMM — no
row change can wake it, so declare a periodic **resync** instead. The loop
resolves the scope to a concrete target and re-evaluates it every period:

```rust
fn resync_schedule(&self) -> Option<ResyncSchedule> {
	Some(ResyncSchedule {
		period: Duration::from_secs(30),
		scope: ResyncScope::LocalNode,
	})
}
```

Declare one or the other, not both. A row-backed reconciler gets its
level-triggered backstop for free — the interest router relists the whole
snapshot on a fixed period — so it does not also need a schedule. And as a rule,
do not declare interest in a row this reconciler writes itself: its own write
would wake it to write again. The
[wakeup model](/docs/concepts/reconcilers#how-the-runtime-wakes-a-reconciler)
covers the partition and the one exception to that rule.

## Register it

A reconciler runs once it is registered in the control-plane runtime at boot —
the same place the eight first-party reconcilers are registered in `overdrive serve`:

```rust
runtime.register(my_reconciler()).await?;
```

Registration bulk-loads the reconciler's persisted Views into memory and reads its
declared wakeup — an interest joins the interest router's table, a schedule joins
the cadence table — so the runtime evaluates it whenever its trigger fires.

<Callout type="warn" title="Purity is the contract">
	A reconciler that reads the clock, does I/O, or returns different actions for
	the same inputs cannot be replayed — and replay is how the control plane is
	tested. If you reach for `Instant::now()` or an `.await` inside `reconcile`, the
	work belongs in an `Action` the shim runs, or in a time value the runtime hands
	you through `tick`.
</Callout>
