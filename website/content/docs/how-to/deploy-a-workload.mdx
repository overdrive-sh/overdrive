title: Deploy a workload
description: Start a single-node Overdrive control plane, declare service listeners and health checks, and deploy a Linux microVM with the CLI.
---

This guide takes you from an empty machine to a deployed workload using the
commands Overdrive ships today. You start a control plane, write a TOML spec,
deploy it, and confirm the control plane accepted it. The service and job
examples below require artifacts you supply. These paths are placeholders,
not downloads or images bundled with the CLI. Every command here runs on
a single node — Phase 1 is single-node by design, so there is no cluster to join
and no membership to configure first.

<Callout title="Prerequisites">
	A supported Linux node, a build of `overdrive`, and a writable home directory.
	The node needs cgroup v2, the required eBPF, nftables and kTLS support, and the
	matching `ovd_fwd` module loaded before `serve`. Startup checks these
	capabilities and refuses incomplete setup. See
	[guest networking](/docs/concepts/guest-networking#the-node-and-guest-must-supply-matching-kernel-support)
	for the shared transport prerequisites. The control plane stores state locally;
	there is no external database to configure.
</Callout>

## Start the control plane

`overdrive serve` runs the control plane. It binds a TLS listener, mints the
operator credentials, and writes them to `~/.overdrive/config` — the single
file every other command reads to find and authenticate to the server.

<Steps>
	<Step>
		**Start the server.** It binds `127.0.0.1:7001` by default:

		```bash
		overdrive serve
		```

		Leave it running. On bind it writes the endpoint, the CA pin, and your
		operator certificate to `~/.overdrive/config` as one trust triple. There
		is no `--endpoint` flag and no `--insecure` flag — the config file is the
		sole source of where the CLI connects and how it trusts the server, and
		that posture is not tunable per command.
	</Step>
	<Step>
		**Confirm it is up.** In a second terminal:

		```bash
		overdrive cluster status
		```

		This reads the endpoint from the config the server just wrote and reports
		the control plane's mode — `single` on a fresh node.
	</Step>
</Steps>

## Write a workload spec

A workload is a TOML file. Its top-level section names the workload's **kind**:
`[service]` for a long-running workload that serves traffic, `[job]` for one that
runs to completion. Every supported workload carries a `[vm]` driver block and
a `[resources]` block. A service additionally declares one or more
`[[listener]]` ports and, under them, its health-check probes:

```toml title="payments.toml"
[service]
id       = "payments"   # name across the cluster — stop / inspect / re-deploy by it
replicas = 1

[vm]
command = "/opt/payments/bin/payments-server" # path INSIDE the guest
args    = ["--port", "8080"]
kernel  = "/srv/vm/kernel"       # operator-supplied supported guest-kit kernel
rootfs  = "/srv/vm/payments.ext4" # operator-supplied guest root filesystem

[resources]
cpu_milli    = 500         # sizes the guest vCPUs
memory_bytes = 134217728   # guest RAM in bytes (128 MiB)

[[listener]]
port     = 8080   # a port the service holds open
protocol = "tcp"

# Readiness — may it receive traffic yet?
[[health_check.readiness]]
type = "http"
path = "/healthz"
port = 8080

# Liveness — is it still healthy, or should it be restarted?
[[health_check.liveness]]
type = "http"
path = "/healthz"
port = 8080
```

### Health checks

Health checks answer three different questions for a Service. A run-to-completion
`[job]` takes none because its exit code reports the job's outcome.

- **Three roles.** `startup` gates `Stable` and backend eligibility. `readiness`
  decides whether a stable allocation can receive traffic. `liveness` starts
  only after `Stable` and can stop an unhealthy allocation. WorkloadLifecycle
  owns the subsequent restart and its shared restart budget.
- **Two mechanics.** `type = "tcp"` connects to a `port`. `type = "http"`
  issues a plain-HTTP GET to a `path` starting with `/` on a `port`. Both dial
  through the guest-network owner. In-guest command probes are unbuilt.
- **Omitting startup uses the guest listener gate.** The guest reports each
  declared TCP listener after `listen()` and each declared UDP listener after an
  explicit `bind()`. The default gate passes when the host has received reports
  for **every** declared listener. A `Running` VM has booted, but a Service with
  this gate reaches `Stable` only after those reports arrive. A listener that
  never opens prevents `Stable` and backend eligibility. The default startup
  deadline is 60 seconds. To opt out for a workload that opens a listener lazily,
  write `health_check.startup = []` at the top level of the TOML spec, before
  `[service]`. The opt-out reaches `Stable` at `Running` and has no listener
  startup gate.
- **Explicit TCP and HTTP probes remain available.** Declare
  `[[health_check.startup]]` to use your own startup check. TCP and HTTP probes
  accept `timeout_seconds` (default 5), `interval_seconds` (startup 2,
  readiness 2, liveness 10), and `max_attempts` (default 30, giving a
  60-second startup deadline at the default startup interval). Liveness also
  accepts `failure_threshold` (default 3), and readiness accepts
  `success_threshold` (default 1). `guest_listeners` is a platform-only mechanic,
  so an operator cannot select it as an explicit TOML probe.

The guest listener gate observes sockets created by tasks in the workload's
guest cgroup. A loopback bind, UDP autobind, or a socket created after a task
moves out of that cgroup does not satisfy it. Reports identify a protocol and
port, not whether the application can answer a request. Declare a readiness
probe when traffic should wait for application-level health. If a guest report
is lost, the gate does not guess that the listener opened. It fails at the
startup deadline. A report records an opening, not continued socket health.
The hooks cannot distinguish an IPv6 wildcard socket with `IPV6_V6ONLY` from
one that also accepts IPv4, so that report alone does not prove IPv4
reachability. Overdrive does not support IPv6 service traffic yet.

## Supply the guest artifacts

The `[vm]` table is the only supported workload driver table. Its command runs
inside a Cloud Hypervisor guest with its own Linux kernel. Use `[service]` for
a long-running VM with listeners and health checks, or `[job]` for a VM that
runs to completion. This job example uses the same guest artifact contract:

```toml title="nightly-report.toml"
[job]
id = "nightly-report"   # name across the cluster — stop / inspect / re-deploy by it

[vm]
command = "/usr/bin/report"      # the command run INSIDE the guest
args     = ["--out", "/var/out"]
kernel   = "/srv/vm/kernel"      # host path to a bootable kernel image
rootfs   = "/srv/vm/report.ext4" # host path to an ext4 root filesystem

[resources]
cpu_milli    = 500         # sizes the guest's vCPUs
memory_bytes = 134217728   # sizes the guest's memory (128 MiB)
```

All four `[vm]` fields are required. `command` and `args` name the program to run
inside the guest; `kernel` and `rootfs` are host paths to a bootable kernel and an
ext4 root filesystem from a matching guest kit. The rootfs must contain the
kit's `overdrive-init` and `ovd_fwd` module; an arbitrary kernel is unsupported.
`cpu_milli` derives the guest vCPU count, and `memory_bytes` sets guest memory.

Deploy, inspect, and stop a microVM job with the same verbs as any other workload
— the steps below are identical. The allocation reaches `Running` once the guest
has booted, and its terminal state carries the guest's own exit code, not the
hypervisor's.

<Callout title="What the node needs">
	A microVM boots through KVM, so the node needs `/dev/kvm` and the required
	Cloud Hypervisor source integration, including RESET-EXIT and the kernel
	vhost-vsock backend. There is no published fork binary to download from these
	docs. The host must load its matching forwarder module before `serve`. Supply
	a supported guest kit and a rootfs on a reflink-capable filesystem. The VM
	uses vsock flow transport; it does not need a per-VM host TAP or bridge. For
	the confinement and artifact contract, see
	[microVMs](/docs/concepts/microvms).
</Callout>

## Deploy it

<Steps>
	<Step>
		**Deploy the spec.** Pass the file to `deploy`:

		```bash
		overdrive deploy payments.toml
		```

		The CLI submits the spec, the control plane commits it to the IntentStore,
		and the command streams lifecycle events until it receives a verdict or
		reaches the progress deadline. A Service returns success when it reaches
		`Stable`. A progress timeout returns exit code `1` and does not stop the
		Service's restart lifecycle. Check `overdrive workload describe payments`
		for the latest allocation state. The command reports the workload id and
		the derived intent key
		(`workloads/payments`), the canonical `spec_digest`, and an outcome of
		`Inserted` for a spec the cluster has not seen before.
	</Step>
	<Step>
		**Re-run it.** Deploy the same unchanged file again:

		```bash
		overdrive deploy payments.toml
		```

		The outcome is `Unchanged`. Deploy is idempotent on the spec's content
		hash: an identical spec commits nothing new. The Service stream reads the
		current allocation's recorded verdict after subscribing to new events. It
		can therefore report an existing `Stable`, give-up failure, or operator stop
		without waiting for another event. If the Service is still starting, the
		command waits under a fresh progress deadline. Edit the file — change the
		args, bump the replica count, adjust a probe — and the next deploy reports
		`Inserted` against the new digest.
	</Step>
	<Step>
		**Skip the event stream.** For a script that wants the commit
		acknowledgement and nothing else, pass `--detach`:

		```bash
		overdrive deploy payments.toml --detach
		```

		`--detach` waits only for the IntentStore commit and exits — it does not
		stream lifecycle events. Reach for it the way you reach for `docker run -d`
		or `nomad job run --detach`: when you want the workload submitted, not
		watched.
	</Step>
</Steps>

<Callout type="info" title="Service deploy waits for a verdict">
	`Inserted` and `Unchanged` describe the intent commit, not service health.
	A streaming Service deploy exits `0` on `Stable` or an operator stop, `1` on
	a Service failure or progress timeout, and `2` for transport or server-side
	pre-acceptance errors. A locally rejected TOML spec also exits `1`.
	`--detach` waits only for the commit acknowledgement. The Service progress
	deadline is `max(90 seconds, startup deadline + 30 seconds)`, counted from
	stream open. It is 90 seconds with the default 60-second startup deadline.
	The CLI allows another 30 seconds for its HTTP request. The stream can time
	out before the restart budget is spent, and its optional `last attempt` block
	is context rather than the final failure cause. A later deploy can read the
	recorded give-up verdict.
</Callout>

## Inspect what you deployed

The CLI reads live state back through the same config:

```bash
overdrive workload describe payments   # spec digest + live allocation count
overdrive node list                    # nodes the control plane knows about
```

`workload describe` is the command to reach for when you want to confirm a deploy
took effect: it returns the canonical `spec_digest` the control plane holds for
the workload alongside the number of live allocations, so you can check that the
digest matches the spec you just deployed and that the workload is actually
running.

## Stop it

Stop a workload by its id:

```bash
overdrive job stop payments
```

This declares that the workload should no longer run. The control plane records
the new intent and the workload's allocations wind down.
