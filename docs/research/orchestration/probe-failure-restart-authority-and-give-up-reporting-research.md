## Executive Summary

Both mature orchestrators run **one restart authority per instance, and it covers crash, liveness kill and startup-probe kill under the same budget/backoff**. Kubernetes derives the kill each sync from the stored probe result (level-triggered); Nomad's check watcher asks the task runner to restart with `failure=true`, which increments the same restart tracker a crash does. Neither finalises an instance as a terminal failure on a probe verdict. Neither classifies "crashed before the startup probe passed" differently from "crashed later": a pre-startup crash is just a restart.

Neither orchestrator bounds a rollout by the restart budget. K8s `restartPolicy: Always` never gives up (backoff caps at 300 s); a separate Deployment `progressDeadlineSeconds` (default 600 s) flips `Progressing=False/ProgressDeadlineExceeded` while the kubelet is still restarting, and its message names no cause. Nomad has `restart` (default 2 attempts / 30 m / mode fail), then reschedule, and a deployment `progress_deadline` (10 m) plus `healthy_deadline` (5 m); the deployment fails early only when the allocation is unhealthy and reschedule attempts are exhausted. The give-up reasons they emit name the **budget**, not the underlying cause (`Exceeded allowed attempts 2 in interval 30m0s and mode is "fail"`); the cause lives in preceding task events. ECS uses a third model: a count-based deployment circuit breaker independent of any per-task restart.

Against this, Overdrive D7's direction (stop on startup-probe failure, one restart authority) and D5 (never act on a terminal row) match best practice. D6's naming of a pre-startup crash loop at give-up and D7's naming of `StartupProbeFailed` at give-up go further than either reference (additive, not contradicted). Three points diverge: **K1** (the deploy stream is bounded only by the restart budget plus a 90 s cap; both references use a separate progress deadline), **P-6** (a single-shot startup stop; K8s is level-triggered, Nomad retries the kill 5 times), and **P-7** (Overdrive spawns liveness probe tasks at `on_alloc_running` with the startup tasks, and `liveness_terminate_action` gates only on `Running`; K8s disables liveness until startup succeeds, Nomad restarts the grace window per instance).

## Findings

### F1 (Q1): a startup-probe kill, a liveness kill and a crash share one restart path in K8s
**Evidence (source).**
- The probe worker only publishes a result. After the threshold is met it writes `results.Failure` (`pkg/kubelet/prober/worker.go:386-392`) and parks itself ("onHold") until a new container ID appears, to avoid exec on a dying container (#21751) and extra probes (#117153) (`worker.go:394-404`). It kills nothing.
- Kubelet sync loop: a liveness `Failure` or any startup update calls `HandlePodSyncs` for the pod (`pkg/kubelet/kubelet.go:2822-2843`, `handleProbeSync` `:2881-2892`).
- `computePodActions` (`pkg/kubelet/kuberuntime/kuberuntime_manager.go:1440-1447`): for a running container, liveness `Failure` gives message "Container %s failed liveness probe" / reason `reasonLivenessProbe`; else startup `Failure` gives "Container %s failed startup probe" / `reasonStartupProbe` (reasons `:566-567`). Both then run the same tail: `if restart { message += ", will be restarted"; ContainersToStart = append(...) }` then `ContainersToKill[id] = {message, reason}` (`:1460-1470`). `restart` is the pod `restartPolicy` (`shouldRestartOnFailure`, `:1427`), or the container-level policy when `ContainerRestartRules` is on (`:1428-1434`).
- A crash enters the same `ContainersToStart` via `ShouldContainerBeRestarted` (`pkg/kubelet/container/helpers.go:90-126`) and is paced by `doBackOff` (`kuberuntime_manager.go:1809`, `:2068-2100`).
- Recording: `killContainer` emits a `Killing` Normal event carrying the message (`kuberuntime_container.go:884-887`); `reason` only selects the per-probe `terminationGracePeriodSeconds` (`:1422-1442`). The restarted container's `lastState.terminated` is the killed process's exit, not "StartupProbe" (`pkg/kubelet/kubelet_pods.go:2321-2341`). So in K8s the **probe cause lives in an event message, not on the status field**; `lastState`+`restartCount` do not distinguish probe kill from crash.
**Docs corroboration.** kubernetes.io probes page: "If the startup probe fails, the kubelet kills the container, and the container is subjected to its restart policy." (https://kubernetes.io/docs/concepts/workloads/pods/probes/, accessed 2026-11-02).
**Nomad.** check_restart: `asyncRestart` hard-codes `failure := true` ("Check watcher restarts are always failures", `client/serviceregistration/watcher.go:105-117`); `Restart(ctx, event, failure)` -> `restartImpl` -> `restartTracker.SetRestartTriggered(failure)` (`client/allocrunner/taskrunner/lifecycle.go:75-88`); `SetRestartTriggered(true)` sets `failure=true` (`restarts/restarts.go:105-118`), after which `GetState` does `count++` against `Attempts` (`:201-226`). A crash goes through `SetExitResult` with the same flag (`:96-103`). Docs: "it is restarted according to the task group's restart policy ... Once a restart is triggered the task group's restart policy takes control" (https://developer.hashicorp.com/nomad/docs/job-specification/check_restart). A restart signalled with `failure=false` (operator/template/identity restarts) takes the "hot path" and is **not** counted (`restarts.go:172-176`).
**Cause recording (Nomad).** `Restart Signaled` task event with `RestartReason = healthcheck: check "<name>" unhealthy` (`watcher.go:94-96`), then `Terminated` (exit result) and `Restarting` events carrying `RestartReason` + delay (`task_runner.go:900-902`; description `structs.go:9542-9548`). `TaskState.Restarts` / `LastRestart` increment on the `Restarting` event (`task_runner.go:1436-1439`).
**Disagreement.** K8s: one policy, cause in an event. Nomad: one policy, cause in an ordered event list, with an explicit `failure` flag choosing whether the restart is charged. Both: single restart authority, probe kill is charged like a crash.
**Confidence**: High (2 primary sources + 2 docs).

### F2 (Q2): a crash before the startup probe passes is just a restart in both
**Evidence.** K8s: `computePodActions` branches on `containerStatus.State != Running` -> `ShouldContainerBeRestarted` (`kuberuntime_manager.go:1405-1423`); no code consults whether the startup probe passed. Nomad: `SetExitResult` + `GetState` (`restarts.go:96-103`, `:153-240`); no notion of "started". Occurrence preservation: K8s `restartCount` + `lastState` (bounded last + monotone counter; `kubelet_pods.go:2321-2341`, `:2428`, `:2796`), `BackOff` Warning event "Back-off restarting failed container" (`kuberuntime_manager.go:2088-2095`). Nomad `TaskState.Restarts`, `LastRestart`, plus the ordered task events (`Terminated` with exit code, `Restarting` with reason).
**Docs.** kubernetes.io pod-lifecycle: restarts "with an exponential backoff delay (10s, 20s, 40s, ...), that is capped at 300 seconds (5 minutes)"; "Once a container has executed for 10 minutes without any problems, the kubelet resets the restart backoff timer" (https://raw.githubusercontent.com/kubernetes/website/main/content/en/docs/concepts/workloads/pods/pod-lifecycle.md). KEP-4603 confirms the same curve and that it applies to `Always` and `OnFailure`; it does not state a separate counter for probe kills (https://github.com/kubernetes/enhancements/blob/master/keps/sig-node/4603-tune-crashloopbackoff/README.md).
**Where K8s differs from Nomad.** K8s keeps one container identity and resets the backoff after 10 min healthy; Nomad budgets by `attempts` per `interval` window (`restarts.go:193-199`).
**Confidence**: High.

### F3 (Q3): give-up reasons name the budget, not the cause
**Nomad evidence.** At exhaustion in `fail` mode: ``Exceeded allowed attempts %d in interval %v and mode is "fail"`` (`restarts.go:226-232`), emitted as a `Not Restarting` event that sets `Failed` on the task (`task_runner.go:894-899`; description `structs.go:9549-9554`). With `Attempts == 0` the reason is `ReasonNoRestartsAllowed`. `mode=delay` instead waits to the interval end (`restarts.go:233-234`). Docs: "The allocation will be marked as failed and the scheduler will attempt to reschedule the allocation" (https://developer.hashicorp.com/nomad/docs/job-specification/restart; defaults for service jobs: attempts 2, interval 30m, delay 15s, mode fail).
**K8s evidence.** `restartPolicy: Always` has no give-up: the kubelet returns `ErrCrashLoopBackOff` from `doBackOff` forever (`kuberuntime_manager.go:2095`), surfaced as the `CrashLoopBackOff` waiting reason. A pod-level give-up exists only for `Never`/`OnFailure` semantics (pod phase `Failed`), not for `Always`.
**Observation.** Neither reference names "startup probe" or "crashed before ready" in the give-up text. Overdrive D6/D7 naming the final attempt's cause at give-up (`EarlyExit`, `StartupProbeFailed`, `LivenessProbeFailed`) is **more informative than either**; it is consistent with Nomad's "last event explains the final attempt". ADR-0087 D4 "last cause wins" is the same trade-off.
**Confidence**: High (source + docs).

### F4 (Q3, Q4): the deployment-level bound is a separate clock from the restart budget
**K8s evidence.** `progressDeadlineSeconds` defaults to 600 (`pkg/apis/apps/v1/defaults.go:70-71`). `DeploymentTimedOut` compares `Progressing` condition `LastUpdateTime + deadline` to now (`pkg/controller/deployment/util/deployment_util.go:771-809`); `LastUpdateTime` is refreshed only on observed progress (`pkg/controller/deployment/progress.go:63-84`, comment "change just lastUpdateTime iff we notice any progress"); otherwise the controller writes `Progressing=False, reason=ProgressDeadlineExceeded`, message "ReplicaSet %q has timed out progressing." (`progress.go:86-94`, reason const `deployment_util.go:86`). A crash-looping pod makes no progress, so this fires while the kubelet is still restarting; the condition message carries **no cause**. `kubectl rollout status` returns the error ``deployment %q exceeded its progress deadline`` (`staging/src/k8s.io/kubectl/pkg/polymorphichelpers/rollout_status.go:78`) and otherwise prints `Waiting for deployment %q rollout to finish: %d of %d updated replicas are available...` (`:81-87`); its own `--timeout` defaults to 0 = wait forever (`staging/.../cmd/rollout/rollout_status.go:91,119`). So the reported failure comes from the controller's clock, not the CLI's; the CLI does not print per-attempt failures.
**Nomad evidence.** Defaults `MinHealthyTime 10s, HealthyDeadline 5m, ProgressDeadline 10m` (`nomad/structs/structs.go:5387-5396`). `RequireProgressBy` starts at the first placed alloc (`nomad/state/state_store.go:6043-6048`) and is extended only when an alloc becomes healthy (`:6049-6052`). The deployment watcher fails the deployment with description "Failed due to progress deadline" when that timer fires (`deployment_watcher.go:444-462`, `:557-558`; const `structs/deployment.go:39`). It fails **early** with "Failed due to unhealthy allocations" only when an alloc is unhealthy and the group has no reschedule attempts left, or `ProgressDeadline == 0` (`deployment_watcher.go:701-724`; const `deployment.go:38`). An alloc is marked unhealthy by the client tracker when a task failed/dead (`client/allochealth/tracker.go:356-360`) or at `healthy_deadline` with events like "Task not running for min_healthy_time of %v by healthy_deadline of %v" (`tracker.go:714-741`). Each restart resets the min-healthy clock (`tracker.go:383-395`: new `StartedAt` -> `setTaskHealth(false,false)` and re-wait). Docs: "If no allocation transitions to the healthy state before the progress deadline, the deployment is marked as failed"; "If progress_deadline is set to 0, the first allocation to be marked as unhealthy causes the deployment to fail"; "If progress_deadline is non-zero, it must be greater than healthy_deadline" (https://developer.hashicorp.com/nomad/docs/job-specification/update).
**CLI.** `nomad job run` monitor follows the evaluation, then hands to the deployment status monitor (`command/monitor.go:296-318`); exit 1 unless the deployment status is `successful`, exit 2 for scheduling failure. The monitor has no wall-clock of its own; it ends when the **server** marks the deployment terminal, so its bound is `progress_deadline` (or earlier on reschedule exhaustion). `deployment status` shows per-group Placed/Healthy/Unhealthy and the Progress Deadline column (`command/deployment_status.go:692-722`) while waiting, i.e. it exposes per-attempt failure counts without ending.
**ECS (third model).** Circuit breaker counts consecutive tasks that fail to reach RUNNING (or fail health checks after running), threshold `BOUNDED_PERCENT` 50% clamped to [3,200] or `COUNT`; on breach the deployment goes `FAILED` with `rolloutStateReason` and optional rollback (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html). Count-based, not time-based, and independent of per-task restarts.
**Conclusion.** All three give the deployment its own bound, independent of the per-instance restart budget, and none ends the deployment at the first failed attempt. Time bound defaults: K8s 600 s, Nomad 600 s progress / 300 s healthy.
**Confidence**: High.

### F5 (Q5): failed stop handling. K8s derives it every sync; Nomad retries the kill but not the trigger
**K8s.** `killContainer` returns an error unless the runtime says NotFound (`kuberuntime_container.go:915-920`); `SyncPod` logs it and records a failed sync result (`kuberuntime_manager.go:1613-1619`). The decision is recomputed from observed state at the next sync: the container is still `Running` and the stored startup/liveness result is still `Failure` (the worker has parked, but the stored result persists until the container ID changes, `worker.go:171-176`, `:250-253`, `:402`), so `computePodActions` emits the kill again (`:1440-1447`). Pure level-triggered retry; no attempt counter.
**Nomad.** Kill is retried inside the task runner: `killTask` loops `killFailureLimit` = 5 times with exponential backoff base 5 s, limit 2 min (`task_runner.go:54-64`, `:1129-1153`); on exhaustion it logs "Resources may have been leaked" (`lifecycle.go:146-149`). The **trigger** is single-shot: after a check_restart trigger the check is removed from the watch set and re-registered on the next instance start (`watcher.go:314-317`), and a `Restart` error is only debug-logged (`:114-117`, "Restart errors are not actionable").
**Disagreement.** K8s fully level-triggered; Nomad retries the effect (kill) but not the decision.
**Confidence**: High.

### F6 (Q6, P-7): K8s disables liveness until startup succeeds; Nomad scopes check_restart by grace per instance
**K8s.** `worker.go:348-359`: when the container is not yet `Started`, "Disable other probes until container has started" (`if w.probeType != startup { return true }`). `Started` is computed from the startup manager result (`pkg/kubelet/prober/prober_manager.go:287-296`, `:353-357`). Docs: "If a startup probe is configured, Kubernetes does not execute liveness or readiness probes until the startup probe succeeds" (https://kubernetes.io/docs/concepts/workloads/pods/probes/). Consequence: liveness cannot kill an instance still waiting for first startup.
**Nomad.** `grace` ("Duration to wait after a task starts or restarts before checking its health", default 1 s; `watcher.go:72-75`, `:196`) and "Once the task restarts Nomad waits the grace period again" (docs, check_restart page). No structural link between a startup phase and check_restart; the grace is the only guard. Meanwhile the deployment tracker independently needs `min_healthy_time` of continuous running (`tracker.go:383-395`), so a check_restart during first-healthiness is possible and resets that clock, but the deployment stays pending until `healthy_deadline`/`progress_deadline`.
**Disagreement.** K8s is structural (liveness impossible before started); Nomad is temporal (grace window). Both prevent a liveness-class kill from being the first thing that fires before the application had a chance to start.
**Overdrive reality (verified in this session).** `ProbeRunner::start_alloc` spawns a task for **every** descriptor of every role at `on_alloc_running` (`crates/overdrive-worker/src/probe_runner/mod.rs:328-361`); only `Stable` cancels the startup role (`stop_role`, `:393-`). `liveness_terminate_action` fires when `fact.state == Running`, the streak crossed the threshold and it is newer than the last act (`crates/overdrive-reconcilers/src/service_lifecycle.rs:1002-1013`); `collect_liveness_actions` skips only `terminal_announced` and "stable this tick" (`:980-983`). Nothing gates a liveness stop on a startup pass. So the P-7 question is answered: **yes, a liveness kill can fire while the deployment is still waiting for first readiness**, if the workload declares a liveness probe.
**Confidence**: High (K8s source+docs; Overdrive source read).

### F7 (Q7): ordering, stale results, and who stops the probes
- **Probe results are keyed by instance identity.** K8s keys every result by container ID and removes it when the container ID changes (`worker.go:250-253`, cleanup `:171-176`); `computePodActions` looks results up by the current container's ID (`kuberuntime_manager.go:1440-1444`). A late result from a dead instance cannot act on its successor. Overdrive's `ProbeResultRow` is keyed by `AllocationId` and ADR-0105 gives every restart a fresh id, so the equivalent holds; D1 plus "no reader acts on a stale row" (Q3 in the feature-delta) matches.
- **Probes read instance state; they are not told it ended.** The K8s worker self-terminates when the pod phase is terminal (`worker.go:228-233`), marks a non-running container `Failure` and keeps probing only if the container will restart (`:308-327`), and stops at pod deletion (`:330-341`). Nomad unwatches checks on service removal (`serviceregistration/nsd/nsd.go:203`) and re-registers per instance (`watcher.go:314-317`). Overdrive's design is edge-driven (explicit `on_alloc_terminal`), which makes D1 (one author per observed end) and D3 (register before gate release) necessary; the references avoid D3's hazard class by level-triggering off instance state, not by an ordering edge.
- **Initial values are conservative and per-probe.** New container ID: readiness `Failure`, liveness `Success`, startup `Unknown` (`worker.go:112-125`, `:293`). A startup `Unknown` never kills (`computePodActions` acts only on `== Failure`, `:1444`). Overdrive's "absent row is pending" (ADR-0054 section 5) is the equivalent.
- **Probe-driven decisions consult only running instances.** K8s checks probe results only for `ContainerStateRunning` (`kuberuntime_manager.go:1405-1448`); Nomad `Restart` returns `ErrTaskNotRunning` for Pending/Dead (`lifecycle.go:26-29`). This is exactly D5's guard (terminal rows are never acted on by the probe consumer).
- **Crash racing the probe stop (E-2).** Nomad appends ordered events (`Restart Signaled`, `Terminated`, `Killing`) so a crash during a probe-triggered kill is not overwritten; K8s keeps the previous termination in `lastState`. Overdrive's row is depth-1 and can be overwritten (feature-delta E-2). Neither reference models the cause as "last write wins on one record".
**Confidence**: High on K8s/Nomad mechanics; the comparison to Overdrive depends on the feature-delta text and the files read above.

## Answers to the questions

**Q1 (D7).** Both kill-and-restart under the same policy/budget as a crash (F1). K8s: same code path, `restartPolicy`; Nomad: check_restart is a `failure=true` restart that increments the tracker. Cause: K8s `Killing` event message ("failed startup probe"), not on `lastState`; Nomad `Restart Signaled` event with reason. Distinguished from a liveness kill by message/event reason only. Neither finalises terminally on a probe verdict. **Recommendation: D7 direction is right** (confidence High). Putting the cause on the row (`StoppedBy::StartupProbe`) is stronger than K8s (event only) and consistent with Nomad's event reason; keep it.

**Q2 (D6).** Restarted under the normal policy; no distinction between pre-startup and later crashes; occurrence preserved by restartCount+lastState (K8s) and task events + `Restarts`/`LastRestart` (Nomad) (F2). **Recommendation:** D6's restart behaviour is right. Classifying the pre-startup case at give-up is additive and has no precedent; justify it by the K1 honest-failure goal, not by best practice (Medium). Note the references preserve occurrence in a *list* (Nomad) or counter+last (K8s); per-attempt rows (ADR-0105) are an acceptable equivalent.

**Q3 (give-up).** Nomad: budget-naming reason, task `Failed`, then alloc reschedule, then deployment failure (F3). K8s `Always`: never gives up; the deployment bound reports `ProgressDeadlineExceeded` without cause (F4). **Recommendation:** naming the final attempt's cause at give-up (D6/D7) is an improvement over both; keep "last cause wins" but also keep `attempts` = restart budget consumed (matches Nomad's budget-first wording). Confidence Medium-High.

**Q4 (K1).** Both references use a progress deadline distinct from the restart budget (F4): K8s 600 s from last progress, Nomad 600 s progress / 300 s healthy and requires progress > healthy, ECS a count threshold. Both keep waiting without ending on per-attempt failure; K8s CLI prints only "waiting" lines, Nomad `deployment status` shows placed/healthy/unhealthy counters and progress deadline. **Recommendation (Medium-High):** yes, bound `overdrive deploy` by a **progress deadline distinct from the restart budget**, started at first allocation and extended only by a *Stable* (the equivalent of Nomad "healthy"), and require it to exceed one `startup_deadline` with margin (Nomad rule: progress > healthy). The present 90 s cap vs 60 s default startup deadline leaves 30 s margin, so it cannot ever observe an attempt past the first. When the deadline fires mid-restart-loop, follow Nomad's split: report a **generic, honest timeout** ("did not become Stable within X; restart budget not yet spent") as the stream terminal, and attach the **most recent observed attempt's cause** (crash code / startup probe fail / stopped by startup probe, plus attempt number) as detail, labelled "last attempt", not as the final verdict. Keep the restart authority's give-up as the only authoritative `Failed { cause }`. Nomad does exactly this: "Failed due to progress deadline" generic, specifics in alloc events. Exit code should be non-zero in both cases (kubectl and nomad both non-zero).

**Q5 (P-6).** K8s: level-triggered retry, implicit (F5). Nomad: kill retried 5x with 5 s..2 min backoff; the *trigger* is single-shot. **Recommendation (Medium-High):** do not leave E-1 as an unretried single-shot. K8s's shape is cheaper: make the decision a function of observed state (still `Running`, startup streak still crossed, not yet stopped) and dedup on the *effect* (row no longer `Running`), not on emission. Overdrive's liveness path already does this via `liveness_last_acted_run` (`service_lifecycle.rs:1008-1015`), so extending the same pattern to startup is consistent with in-tree precedent. Not adding it makes the startup path strictly weaker than the liveness path.

**Q6 (P-7).** K8s: liveness (and readiness) are structurally disabled until startup succeeds (`worker.go:348-359`, docs). Nomad: grace window per instance. Overdrive: liveness runs from `on_alloc_running` and can stop a pre-Stable allocation (F6). **Recommendation (Medium-High):** gate the liveness stop (and ideally the liveness task spawn) on "startup passed or no startup probe declared"; this also removes the need for the P-7 stream guard for `Stopped { LivenessProbe }`. If the user prefers not to add scope, at minimum the stream must not project a restartable liveness stop as a success, as D7 item 5 does for startup.

**Q7 (other divergences).** (a) Stale results: equivalent (keyed by fresh alloc id) - fine. (b) Probe stop ordering: references are level-triggered off instance state; Overdrive's edge-driven registration needs D3's happens-before edge, which is sound but a design smell the references do not have. A defensive level-triggered backstop (supervisor exits when its allocation's latest row is terminal) would remove the whole ordering class, but is extra mechanism; the feature-delta Alt B rejected it for stated reasons. Treat as a note, not a finding. (c) K8s parks a probe worker after publishing a failure to avoid hammering a dying instance (`worker.go:402`); Overdrive's streak freeze after D1 is the equivalent. (d) Cause overwrite on crash-race (E-2) is a real divergence from Nomad's event list; bounded and acknowledged. (e) `attempts` meaning change on `StartupProbeFailed` (probe streak -> restart budget) aligns with Nomad's budget-first reason strings.

## Decision map: Overdrive vs best practice

| Decision | Verdict | Basis |
|---|---|---|

| D3 register supervision before releasing the exit-event gate | **No direct precedent**; the hazard class does not exist in K8s/Nomad because probing reads instance state and is keyed by instance id. The fix (a happens-before edge) is sound | F7; Medium |
| D5 `startup_probe_failed_action` skips terminal rows | **Matches**: K8s consults probe results only for running containers (`kuberuntime_manager.go:1405-1448`), Nomad `Restart` rejects non-running (`lifecycle.go:26-29`) | F7; High |
| D6 restart authority alone ends a crashed Service allocation; names a pre-startup crash loop at give-up | **Matches** on single authority and restart-under-policy (F1, F2). **No precedent** for classifying the pre-startup case at give-up; both name the budget only (F3). Additive, not contradicted | High / Medium |
| D7 startup-probe failure stops the instance; restart authority restarts and names it at give-up | **Matches** (K8s same path as liveness `manager.go:1440-1470`; Nomad `failure=true` charged restart).
