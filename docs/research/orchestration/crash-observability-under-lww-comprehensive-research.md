# Research: How Production Orchestrators Keep a Crash-and-Recover Durably Observable When the Current-State Record Is Last-Write-Wins

**Date**: 2026-08-01 | **Researcher**: nw-researcher (Nova) | **Confidence**: High | **Sources**: 16

## Executive Summary

Every production orchestrator examined — Kubernetes and HashiCorp Nomad — solves "keep a crash-and-recover durably observable" the same structural way, and neither does it by making the current-state record itself an unbounded log. Kubernetes bounds crash history in `PodStatus` to exactly **one** prior state (`containerStatuses[].lastState`, overwritten on every subsequent restart) plus a monotone `restartCount` scalar, and relies on a **separate**, TTL'd, count-aggregated `Events` object — explicitly not an audit log — for anything beyond the latest occurrence. Nomad independently converges on the identical shape: a fixed 10-event ring buffer per task plus a monotone `Restarts` counter, both held in **per-node, non-gossiped** Raft state, with HashiCorp's own guidance directing operators to an external durable sink (the Event Stream API) for real history retention. This is the general CQRS/event-sourcing pattern (Martin Fowler, Chris Richardson) applied twice, independently, by two unrelated production systems: a small, always-converged **current-state projection** paired with a larger, explicitly lossy **history side**.

CRDT theory (Shapiro et al.'s foundational INRIA report, formalized in Almeida's 2023 ACM Computing Surveys treatment) supplies the precision the requester's hard constraint demands. A scalar counter merged under plain last-write-wins is safe **only** under a single-writer-per-key invariant — exactly the invariant Overdrive's `alloc_status` row already assumes today — and is a materially weaker primitive than a true G-Counter (which merges per-writer slots component-wise and tolerates genuinely concurrent writers). Corrosion, cross-referenced directly against its own documentation, confirms it ships plain LWW-per-column semantics that explicitly discard the losing value on conflict; it does not confirm a native, schema-exposed counter or OR-Set type is available to Overdrive today. An append-only table keyed by a per-row-unique key, however, sidesteps LWW conflict entirely — each row has exactly one writer for its whole lifetime, making it the practical, gossip-safe analogue of a G-Set. Bounding such a table's storage while remaining provably safe under concurrent gossip requires "causal stability," a real and non-trivial protocol property neither Kubernetes nor Nomad's *gossiped* layer actually implements — both systems avoid the problem by bounding to a small fixed depth or externalizing entirely, rather than solving unbounded-durable-history-under-gossip in-platform.

The recommendation follows the prior art directly: add a Kubernetes-`lastState`-shaped `last_terminated` sub-struct plus a monotone `restart_count` scalar to the existing `alloc_status` row as the minimum viable, immediately-shippable fix (zero new CRDT primitives, inherits the row's existing correctness argument, closes the exact reported defect for the most recent crash). A separate append-only crash/event table — the CRDT-cleanest of all candidates examined — is the natural follow-up if bounded-depth history proves insufficient. One shape is explicitly disqualified: a single LWW-merged blob encoding "the last N events," overwritten wholesale on each write, which a concurrent gossip race can cause to lose an entire peer's contribution outright — a failure mode strictly worse than any recommended candidate, and a shape neither Kubernetes nor Nomad uses.

## Problem Framing (from requester)

Overdrive is a Rust workload orchestrator. Its observation layer stores one
`alloc_status` row per allocation, merged **last-write-wins** on a
`LogicalTimestamp { counter, writer }` (Lamport-style). A just-fixed defect
(ADR-0077) removed a counter collision; the side effect is that a
crash-then-immediate-restart sequence `Running(1) -> Failed(2) -> Running(3)`
now correctly converges to `Running` and the `Failed` state becomes
transient/invisible to an operator polling `overdrive workload describe`.

**Ruling (not up for debate):** a crash-and-recover MUST be durably
observable. This research evaluates *how*, not *whether*.

**Hard constraint:** Phase 2 replaces the single-node store with gossiped
CR-SQLite (Corrosion), still LWW per row, peer-to-peer, no coordinator. Any
candidate surface must merge correctly under LWW gossip across peers
(a CRDT-correctness question, not just an API-design question). A design
that only works single-node is disqualified from being the durable answer
and must be flagged as such.

## Findings

### Finding 1: Kubernetes bounds crash history in `status` to exactly ONE prior state, overwritten on every subsequent restart
**Evidence**: `ContainerStatus.LastTerminationState` (godoc/CNCF paraphrase of the Kubernetes source): "will be empty if the container is still running successfully... **the field is overwritten whenever the container restarts**." The `kubectl describe pod` rendering exposes it as a single `Last State:` block (`State: Running / Last State: Terminated, Reason: OOMKilled, Exit Code: 137, Started/Finished timestamps`) alongside a single scalar `Restart Count: 2` — there is no `[]LastState` array and no indexed history of prior terminations in the object itself.
**Source**: [Tracking container restarts and termination events in Kubernetes — CNCF Blog](https://www.cncf.io/blog/2022/08/23/tracking-container-restarts-and-termination-events-in-kubernetes/) - Accessed 2026-08-01
**Confidence**: High
**Verification**: [Kubernetes Pod Lifecycle — Container states (kubernetes.io, official)](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#container-states) - Accessed 2026-08-01; corroborating community documentation ([sysdig.com CrashLoopBackOff guide](https://www.sysdig.com/blog/debug-kubernetes-crashloopbackoff)) shows the identical single-`Last State`-block shape in `kubectl describe pod` output.
**Analysis**: This is the Kubernetes precedent the requester asked to pin precisely. `PodStatus.containerStatuses[].lastState` is a **current-state projection field**, not a history log — it is LWW-shaped itself (each restart overwrites the prior value) and bounded to depth 1. `restartCount` is the only part of the crash *history* that survives more than one restart, and it survives as a **monotonically-incrementing scalar counter**, not as a log of individual events. On a **second** restart, the detail of the *first* crash (its exact exit code / reason / timestamps) is **permanently lost** from `status` — only the fact that "it has restarted N times" and the most recent crash's detail remain. This directly validates the "monotone counter" and "current-state + last-state struct" candidates in the requester's ranked list, and directly falsifies the idea that `status` alone gives full crash observability — Kubernetes relies on a *second*, independent object (Events; see Finding 2) for anything beyond the latest crash.

### Finding 2: Kubernetes Events are a separate, TTL-bounded, count-aggregated object — explicitly NOT an audit log, and NOT itself durable
**Evidence**: The `Event` object (`v1 core`, and its restructured `events.k8s.io/v1` counterpart) is a distinct Kubernetes API resource from `Pod.status`, garbage-collected out of etcd by the `kube-apiserver --event-ttl` flag whose **default is 1 hour**. When the API server's `EventAggregator` observes semantically-similar events (same `reason` + `involvedObject`, e.g. repeated `BackOff` / `Pulled` / `Killing`) within its aggregation window, it collapses them: rather than creating N separate Event objects, it increments a single object's `count` field and advances `lastTimestamp`, dropping the individual occurrence's own detail into an aggregated `message` ("(combined from similar events)"). The newer `events.k8s.io/v1` schema formalizes this as a `series: {count, lastObservedTime}` sub-struct alongside a per-event `eventTime`.
**Source**: [event-ttl default 1h — corroborated via kube-apiserver flag reference summarized in multiple independent secondary sources](https://github.com/kubernetes/kops/issues/7484) - Accessed 2026-08-01 (kube-apiserver `--event-ttl` flag, default `1h`, "Amount of time to retain events")
**Confidence**: Medium-High (the flag's exact default was confirmed via kube-apiserver flag-reference paraphrase and cross-referenced across independent secondary write-ups rather than a verbatim scrape of the primary kubernetes.io flag table, which repeatedly truncated on fetch; the *existence* and *mechanism* of TTL + count aggregation is independently corroborated by the CNCF blog and multiple practitioner sources)
**Verification**: [CNCF — Tracking container restarts and termination events](https://www.cncf.io/blog/2022/08/23/tracking-container-restarts-and-termination-events-in-kubernetes/) explicitly notes the gap this split leaves: *"the API doesn't currently include an event type for container restarts or terminations"* — i.e., even the Events object does not guarantee a dedicated, structured "container restarted" event; restart detection via Events is inference from adjacent signals (`BackOff`, `Killing`, `Pulled`), not a first-class event type. [kubernetes.io — Auditing](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/) draws the sharpest line: Kubernetes' actual audit trail is a **separate subsystem** (the audit-log webhook/policy pipeline), explicitly distinguished from the `Event` API object.
**Analysis**: This is the answer to "why is crash history split across `status` and `Events`, and what does the split buy / cost." The split buys **separation of concerns between convergent current-state (small, bounded, always-fresh, cheap to gossip/replicate) and time-series history (larger, unbounded-arrival-rate, explicitly disposable)** — Kubernetes does not attempt to make its convergent state store (etcd `Pod.status`, single-writer-per-field) also serve as an unbounded audit log. The cost is real and explicitly documented as a known gap by CNCF: Events are **lossy** (TTL expiry, count-aggregation collapses distinct occurrences into one counter + one "most recent" message, and there's no dedicated per-restart event type), and Kubernetes' own docs steer users toward a **third-party durable sink** (e.g., shipping Events to Elasticsearch/long-term storage) the moment retention beyond ~1 hour matters. Kubernetes explicitly does NOT treat `Events` as an audit log — a real audit trail requires the separate audit-logging subsystem. This is a load-bearing precedent for Overdrive: **the object that answers "is the system converged" is not the same object that should answer "what happened," and the latter is expected by Kubernetes' own design to be lossy/TTL'd unless paired with an external durable sink.**

### Finding 3: Nomad bounds task-event history to a hard-coded ring buffer of 10 events per task, and explicitly tells operators to use the durable Event Stream API for anything beyond that
**Evidence**: Nomad's `TaskState` struct (`nomad/structs/structs.go`) carries `Events []*TaskEvent` alongside scalar fields `Restarts uint64` and `LastRestart time.Time`. The events slice is capped by a constant documented in-source as *"defaultMaxEvents is the default max capacity for task events on the task state"*, set to **10**, and is described by HashiCorp community/maintainer commentary as existing specifically **"to avoid bloating its database."** Once the cap is reached, new events evict the oldest — a bounded FIFO / ring buffer, not an unbounded append-only log. `nomad alloc status` surfaces this as a "Recent Events:" block plus the two scalars `Total Restarts` and `Last Restart`; `-short` collapses even that to "only the most recent task event."
**Source**: [HashiCorp Discuss — "Can I obtain all events of the task?"](https://discuss.hashicorp.com/t/can-i-obtain-all-events-of-the-task/26962) - Accessed 2026-08-01
**Confidence**: Medium-High (primary source is HashiCorp's own community/support forum on the official `hashicorp.com` domain quoting the actual in-source doc comment verbatim; the raw GitHub source fetch for `structs.go` truncated before reaching the constant definition during this research session, so the exact line was not independently re-verified against a second direct source read — see Knowledge Gaps)
**Verification**: [`nomad alloc status` command reference (developer.hashicorp.com, official)](https://developer.hashicorp.com/nomad/commands/alloc/status) confirms the operator-facing surface shape (`Total Restarts`, `Last Restart`, `Recent Events`, `-short` for most-recent-only) independently of the source-code claim; [`restart` block docs (developer.hashicorp.com, official)](https://developer.hashicorp.com/nomad/docs/job-declare/failure/restart) confirms `attempts`/`interval`/`delay`/`mode` govern *retry policy*, which is orthogonal to *event retention*.
**Analysis**: Nomad's design independently converges on the same shape as Kubernetes — a **bounded, current-state-adjacent event window** (10 events, not 1 like Kubernetes' `lastState`, but still a hard bound) plus a **monotone scalar counter** (`Restarts`) that survives arbitrarily many crash-loop iterations without growing. Critically, HashiCorp's own guidance for anything beyond that bounded window is explicit and load-bearing for this research: **"use the Event Stream API to subscribe to the `Allocation` topic and store events externally for long-term retention and querying."** Nomad does not claim its bounded in-memory/etcd-equivalent (Raft-backed state store) event slice is sufficient for durable crash history — it hands that responsibility to an external, durably-retained subscriber. This directly validates the requester's suspicion in research question 6: **the in-process/ephemeral event stream (`LifecycleEvent` broadcast) is only a viable "just use the event stream" answer when paired with durable retention** — Nomad's own prior art treats the live event stream as a *notification* mechanism, not a *record*, and explicitly tells the operator to attach durable storage if history matters.

### Finding 4: The state-vs-event architectural split (CQRS / Event Sourcing) is the general pattern both Kubernetes and Nomad instantiate — and its own literature already tells you what NOT to keep in the current-state side
**Evidence**: Martin Fowler, defining Event Sourcing: *"every change to the state of an application is captured in an event object, and that these event objects are themselves stored in the sequence they were applied... we can discard the application state completely and rebuild it by re-running the events from the event log on an empty application."* On the performance/practicality tradeoff of a pure event-sourced read path, Fowler's own pragmatic guidance is: *"store the current application state and if someone wants the special features that Event Sourcing offers then that additional capability is built on top."* CQRS (microservices.io, Chris Richardson's canonical pattern language) formalizes the resulting split: a **command/write side** that owns authoritative mutations and *publishes* events, and a **query/read side** — "a view database, which is a read-only 'replica' that is designed specifically to support" a given query shape — that subscribes to those events and is allowed to be "replication lag/eventually consistent."
**Source**: [Martin Fowler — Event Sourcing (martinfowler.com, official/primary author site)](https://martinfowler.com/eaaDev/EventSourcing.html) - Accessed 2026-08-01
**Confidence**: High
**Verification**: [microservices.io — CQRS pattern (Chris Richardson, domain-specific canonical reference)](https://microservices.io/patterns/data/cqrs.html) - Accessed 2026-08-01, independently corroborates the write/read split and the "CQRS becomes necessary in an event-sourced architecture... because event-sourced systems store immutable event logs rather than current state, making direct queries difficult" framing; cross-validated structurally by Findings 1-3 above, where Kubernetes and Nomad each independently arrived at the identical shape (a small, converged current-state projection + a separate, larger, explicitly-lossy event/history side) without citing CQRS/ES literature by name.
**Analysis**: This is the general pattern the requester asked to name explicitly. The current-state projection (`PodStatus`, Nomad `TaskState`) is the CQRS "read model materialized from converged writes" — small, cheap to replicate/gossip, always reflects "now." The event stream (`Events`, Nomad's Event Stream API / task events) is the append-only log side. Two things the literature is explicit about that bound the design space for Overdrive: (1) the read-model/current-state side is *expected* to be lossy relative to the full history — that is the entire point of the split, not an oversight; (2) a *pure* event-sourced system (state derivable ONLY by replaying the full log) is explicitly called out by Fowler as a *performance/practicality tax* most systems don't pay in full — the pragmatic middle ground everyone actually ships is "materialized current-state snapshot + a bounded amount of recent/derived history alongside it," which is exactly the Kubernetes/Nomad shape, not full event-sourcing purity. Overdrive already has a durable current-state row (`alloc_status`) and an in-process (non-durable) event broadcast (`LifecycleEvent`) — the gap this research question set out to close is that the event side isn't durable yet, i.e., Overdrive currently ships CQRS's write side and the *notification* mechanism, but not the durable *read-log* side.

### Finding 5: CRDT theory formally distinguishes a per-actor G-Counter (component-wise max, safe under ANY concurrent writers) from a scalar LWW-Register carrying a monotone value (safe ONLY under a single-writer-per-key invariant) — the two are not the same primitive
**Evidence**: The G-Counter CRDT (Almeida, *"Approaches to Conflict-free Replicated Data Types"*, ACM Computing Surveys / arXiv:2310.18220, formalizing Shapiro et al.'s original definitions) maintains state as **"a map from replica identifiers to natural numbers"** (𝕀⇀ℕ) — i.e. one counter slot **per writer/actor**, not one shared scalar. Its merge function is **componentwise**: `m ⊔ m' = {j ↦ max(m[j], m'[j]) | j ∈ dom m ∪ dom m'}` — the max is taken *per slot*, and the externally-visible value is the **sum** of all slots (`value(m) = Σ m[j]`). PN-Counter is the Cartesian product of two G-Counters (one for increments, one for decrements) merged the same way. By contrast, the CRDT literature's LWW-Register resolves conflicting writes to the *same single slot* by picking one winner (highest logical timestamp, or a secondary tiebreak) and **discarding the other entirely** — this is corroborated directly by Corrosion's own documentation (Finding 6 below): *"No intermediate value preservation — only final merged states persist; intermediate conflicting values are discarded."*
**Source**: [Almeida, P.S. — "Approaches to Conflict-free Replicated Data Types" (arXiv:2310.18220, ACM Computing Surveys)](https://arxiv.org/abs/2310.18220) - Accessed 2026-08-01
**Confidence**: High
**Verification**: [Shapiro, Preguiça, Baquero, Zawirski — "A comprehensive study of Convergent and Commutative Replicated Data Types" (INRIA Research Report RR-7506, 2011)](https://inria.hal.science/inria-00555588/en/) - Accessed 2026-08-01 (the foundational paper the Almeida survey formalizes and the requester explicitly asked to be cited; abstract/metadata confirmed, full-text PDF fetch was blocked by an access-control gateway during this session — see Knowledge Gaps); cross-referenced against [Corrosion's own CRDT documentation](https://superfly.github.io/corrosion/crdts.html) confirming the plain-LWW discard behavior independently.
**Analysis**: This is the precise, falsifiable answer to research question 5's first sub-bullet: **does `max`-merge give correct semantics for a single-writer-per-key counter?** Answer: **yes, but only under that exact invariant, and it is a materially weaker guarantee than a true G-Counter.** A scalar `restart_count` column merged under Corrosion's plain LWW rule (highest `col_version` wins; value used only as an SQL `max()` tiebreak on an exact `col_version` tie — see Finding 6) converges correctly **if and only if** every write to that column is causally ordered after every prior write for that same allocation — i.e., a true single-writer-per-key discipline, which is exactly the invariant Overdrive's existing `LogicalTimestamp{counter, writer}` per-row design already assumes for the whole row today. Under that invariant, a monotonically-incrementing writer-side counter is safe as an ordinary LWW column because the write with the highest `col_version` is *by construction* also the write with the highest counter value — there is no scenario where an older write "wins" and silently reverts the counter, because col_version IS the causal order for a single writer. **The moment that invariant is violated — e.g. two nodes concurrently believe they own the same allocation during a failover/split-brain window and both increment independently — a plain LWW-merged scalar can genuinely lose a legitimate increment** (one writer's `restart_count=5` write can be entirely overwritten by a concurrent competing writer's `restart_count=3`, with the higher-attempt writer's *history*, not just its value, vanishing). A true G-Counter (per-writer slot, summed) would NOT lose it — both writers' contributions survive and sum. **This is the load-bearing nuance the requester's research question anticipated and the literature confirms: a scalar monotone-LWW-column is gossip-safe under Overdrive's current single-writer-per-key architecture, but is a strictly weaker/more fragile primitive than a true G-Counter, and the fragility is invisible until ownership genuinely becomes concurrent** (which Phase-2 HA/failover explicitly introduces as a possibility). See Finding 6 for whether Corrosion, as actually shipped, exposes a true G-Counter primitive at all.

### Finding 6: Corrosion (as actually shipped) is LWW-per-column by default; a native counter/OR-Set CRDT type exists in the underlying cr-sqlite engine but is not confirmed as exposed through Corrosion's own schema surface — and Corrosion's LWW merge explicitly discards intermediate/losing values
**Evidence**: Corrosion's own CRDT documentation states its conflict resolution as: *"Biggest `col_version` wins. In case of a tie, the 'biggest' value is used"* (SQLite `max()` over the column's serialized value as final tiebreak, with the originating node's `site_id`/actor id as a last-resort tiebreaker), and explicitly: *"No intermediate value preservation — only final merged states persist; intermediate conflicting values are discarded."* Corrosion's schema is defined purely via standard `CREATE TABLE` / `CREATE INDEX` SQL DDL with no documented custom column-type syntax for declaring a column as a counter, OR-Set, or any non-LWW CRDT type in the schema docs examined. Fly's own engineering blog post on Corrosion independently confirms the top-level model: *"Updates to tables are applied last-write-wins using logical timestamps (that is, causal ordering rather than wall-clock ordering)"* and that per-column changes are tracked via a `crsql_changes` table. The underlying `cr-sqlite` engine (which Corrosion embeds) documents COUNTER and PERITEXT (rich-text) column types as **still in development** as of the version of the README examined: *"LWW, Fractional Index, Observe-Remove sets are available now. Counter and rich-text CRDTs are still being implemented."*
**Source**: [CRDTs — Corrosion (superfly.github.io, official project docs, Fly.io)](https://superfly.github.io/corrosion/crdts.html) - Accessed 2026-08-01
**Confidence**: Medium-High (Corrosion's own docs are unambiguous on LWW-only default behavior and the discard-on-merge property; the claim that Corrosion's *schema surface* has no exposed non-LWW column type is an absence-of-evidence finding from the examined Schema doc page and README, not a confirmed absence from the full codebase — flagged in Knowledge Gaps)
**Verification**: [vlcn-io/cr-sqlite README (github.com)](https://github.com/vlcn-io/cr-sqlite/blob/main/README.md) - Accessed 2026-08-01, confirms Counter CRDT is separately implemented at the underlying-engine level but described as still-in-development in the examined revision, independent of whether Corrosion's own schema layer surfaces it; [Fly.io engineering blog — "Corrosion"](https://fly.io/blog/corrosion/) - Accessed 2026-08-01, corroborates the top-level LWW-with-logical-timestamps model from the primary author organization.
**Analysis**: This directly answers the requester's framing question — "cross-reference cr-sqlite/Corrosion's merge-semantics claims against the CRDT literature rather than relying on the README alone" — and the cross-reference **holds**: Corrosion's documented behavior (highest-version-wins, losing value discarded) is a textbook LWW-Register, exactly matching the CRDT literature's LWW-Register semantics (Finding 5), not a G-Counter or OR-Set. **Practical consequence for Overdrive**: any candidate design that wants a *true* multi-writer-safe counter (immune to the split-brain/concurrent-ownership edge case in Finding 5) cannot rely on a hypothetical native "COUNTER column" in Corrosion without further verification that Corrosion's schema layer actually exposes it (this research did not find that confirmation). The safe, verified-available primitive is: **plain LWW columns, correct under the existing single-writer-per-key invariant only.** Any bounded-history / discrete-event design (research question 5's OR-Set / op-based-log sub-bullet) must be built as an **append-only table with a unique per-row primary key** (e.g. `(allocation_id, event_seq)` or `(allocation_id, occurred_at_logical_ts, writer)`) — new rows are `INSERT`s, never `UPDATE`s to a shared key, which sidesteps LWW entirely (each row has exactly one writer for its whole lifetime, so there is no conflict to resolve) and is the closest practical analogue to an OR-Set / G-Set (grow-only set) available on Corrosion's actually-documented primitives. This is the CRDT-literature-grounded justification for "separate append-only crash/event table" as the gossip-safe candidate in research question 6.

### Finding 7: Bounding a gossiped event log to "last N" is possible as a READ-TIME projection over a total order, but physically pruning storage to stay bounded requires "causal stability" — a distinct, non-trivial protocol property, not a free consequence of LWW or OR-Set semantics
**Evidence**: The CRDT survey literature (Almeida, arXiv:2310.18220, formalizing Shapiro et al.) defines **causal stability** precisely: *"message with timestamp t is causally stable at node i when all messages subsequently delivered at i will have timestamp t′ ≥ t"* — i.e., a node can only safely discard/compact information about an operation once it is certain no further concurrent (not-yet-seen, potentially-earlier-in-the-eventual-order) operation can still arrive. The same source states causal stability is the mechanism that *"allows the system to discard timestamps for operations that become causally stable"* and is *"usually necessary for garbage collection actions, but tricky to ensure."* Determining causal stability without a central coordinator requires tracking, per peer, what every other peer has already observed (a version-vector / dotted-version-vector style exchange) — which is itself extra gossip protocol machinery layered on top of whatever the base CRDT (OR-Set, G-Set, LWW-per-row) already provides.
**Source**: [Almeida, P.S. — "Approaches to Conflict-free Replicated Data Types" (arXiv:2310.18220)](https://arxiv.org/abs/2310.18220) - Accessed 2026-08-01
**Confidence**: Medium-High (the causal-stability *definition* and its role in GC is drawn from a strong academic source; the specific claim that Corrosion/cr-sqlite does NOT itself implement causal-stability-gated garbage collection for a hand-rolled bounded event table is inferred from the absence of any such feature in Corrosion's examined documentation, not from an explicit "we do not support this" statement — flagged in Knowledge Gaps)
**Verification**: Independently corroborated in substance (though at lower individual reputation, so treated as directional rather than load-bearing) by community CRDT engineering write-ups describing the same tombstone/GC tension — e.g. that "tombstones are safe to remove only when all known peers have seen the deletion" and that ordinary 2P-Set-style tombstoning "makes the state grow forever" absent such a mechanism; this is consistent with, and does not contradict, the primary academic definition above.
**Analysis**: This is the precise answer to research question 5's final sub-bullet and the requester's own suspected answer ("no, not without a total order"). Two distinct claims must be kept separate, because conflating them is the likely failure mode for a design review:
1. **Deterministic ordering of "the last N events" IS achievable without a total order in the strict distributed-systems sense** — Overdrive's existing `LogicalTimestamp{counter, writer}` per event already supplies a deterministic tiebreak-total-order *over the fully-merged set of events seen so far* (sort by `(counter, writer)` descending, take first N). Any two peers that have gossiped the same set of events will compute the identical top-N, because the ordering function is pure and deterministic over that set.
2. **What is NOT free is bounding *storage*** — i.e., physically deleting the (N+1)-th-oldest event row so the table doesn't grow forever. A peer that deletes row N+1 locally, believing it is "the oldest, safe to drop," cannot be sure a concurrently-in-flight (not-yet-gossiped) event from a partitioned peer won't later arrive and causally belong ahead of what's already been kept — the deletion is only safe once that event is **causally stable**, which (per Finding 7's academic source) requires additional cross-peer acknowledgment tracking that plain LWW-per-row or a bare append-only table does not provide out of the box.

The practical resolution used throughout the prior art (Findings 1-3) is to **never rely on the gossiped/replicated layer itself to enforce the bound** — Kubernetes bounds `lastState` to depth-1 by simple overwrite (an LWW field, not a pruned log), and Nomad's 10-event ring buffer lives in **each node's own local, non-gossiped Raft-backed state store**, not in a CRDT-merged, multi-writer structure — HashiCorp's own guidance for anything needing durable, unbounded-but-queryable history is to **externalize it entirely** (the Event Stream API → an external durable sink), sidestepping the causal-stability problem by moving retention outside the gossiped system altogether. This is a genuine gap the prior art does not solve *within* a gossiped LWW/CRDT store — it works around it by not attempting unbounded durable history inside that store at all.

### Finding 8: Retention bounding in practice uses a small fixed cap (not TTL-based expiry) for the operator-facing surface, and treats "crash-looped thousands of times" as an out-of-band problem solved by backoff, not by history growth
**Evidence**: Kubernetes' `CrashLoopBackOff` mechanism caps the *rate* of crash recurrence itself (exponential backoff, "10s → 20s → 40s → 80s → 160s → 300s, capped at 5 minutes, resets after 10 minutes of successful operation" per the cross-referenced practitioner sources in Finding 1's search results) rather than capping stored history growth directly — because `restartCount` is an O(1) scalar and `lastState` is depth-1, **neither grows regardless of how many times a workload crash-loops**; a workload crash-looping 10,000 times produces a `restartCount` of 10,000 and an unchanged-size `lastState` struct. Nomad's `RestartPolicy` (`attempts`/`interval`/`delay`/`mode`) governs the same rate-limiting concern independently of its event-log retention; its `Restarts uint64` scalar is likewise unbounded-value-but-fixed-size, and its 10-event ring buffer is a hard cap unaffected by how many times the cap has been exceeded (old events are simply evicted, not summarized).
**Source**: [Nomad `restart` block docs (developer.hashicorp.com, official)](https://developer.hashicorp.com/nomad/docs/job-declare/failure/restart) - Accessed 2026-08-01
**Confidence**: Medium (this finding is a synthesis across Findings 1-3 rather than a single new primary quote; it is well-supported by the already-cited official sources but was not independently re-verified against a source specifically discussing "what breaks at 10,000 crash-loop iterations" — no source examined during this research directly addresses that extreme scenario, which is itself a knowledge gap, see below)
**Verification**: Cross-referenced against Finding 1 (Kubernetes `restartCount` as scalar `int32`, no documented ceiling found in this research) and Finding 3 (Nomad `defaultMaxEvents = 10` ring buffer).
**Analysis**: The retention strategy both systems converge on is **"cap the size of what's kept, not the rate of what's counted."** The scalar counters (`restartCount`, `Restarts`) are O(1) storage regardless of crash-loop depth — this is the key property that makes "monotone counter" the cheapest and safest candidate in research question 6's ranked list for the specific "was there a crash-loop, and how bad" question. The bounded event structures (`lastState` depth-1, Nomad's depth-10 ring) are likewise O(1) storage by construction — a ring buffer, not a TTL'd/expiring collection — so "what breaks when a workload crash-loops thousands of times" is, by design, **nothing breaks in the current-state-adjacent storage**; what's lost is fidelity (only the most recent 1 or 10 events are visible), which is precisely the tradeoff CQRS/Event Sourcing literature (Finding 4) predicts and accepts. Neither Kubernetes nor Nomad documentation examined in this research describes an *unbounded* durable history structure that must cope with crash-loop-scale growth — that responsibility is externalized (Kubernetes Events + TTL/count-aggregation as a lossy compromise; Nomad's Event Stream API to an external sink as an explicit non-answer within the platform itself). This is a genuine, honestly-documented knowledge gap in the prior art for a design that wants *unbounded, durable, in-platform* crash history — see Knowledge Gaps below.

### Gap 3: No source examined directly addresses "what breaks when a workload crash-loops thousands of times" for either Kubernetes or Nomad
**Issue**: Finding 8's conclusion (scalar counters and fixed-depth structs/ring-buffers are O(1) regardless of crash-loop depth, so "nothing breaks" in that specific storage) is a structural inference from the documented field *types*, not a direct source statement addressing extreme crash-loop counts. **Attempted**: Searched for CrashLoopBackOff behavior at scale, Nomad restart-policy exhaustion behavior; found rate-limiting (backoff) documentation but no source specifically discussing storage/observability behavior at very high crash counts. **Recommendation**: If Overdrive's design needs a documented ceiling (e.g., does `restart_count: u32` risk overflow at extreme scale, does Nomad's `Restarts uint64` field ever get reset), this needs either direct source-code inspection of both systems or a targeted follow-up query — flagged as unresolved rather than guessed at.

### Gap 4: The prior art does not answer how to keep genuinely unbounded, durable crash history *inside* a gossiped/CRDT-merged store with safe, automatic pruning
**Issue**: Both Kubernetes and Nomad avoid this problem rather than solve it — Kubernetes bounds to depth-1 via plain LWW-shaped overwrite; Nomad bounds to depth-10 via a **non-gossiped, per-node, Raft-local** ring buffer and explicitly externalizes anything beyond that to a durable subscriber outside the platform's own replicated state. Neither system demonstrates a pattern for "durable, unbounded, unbound-growth-safe, gossip-merged event history with automatic garbage collection" — which is closer to what a naive reading of "make the crash durably observable" might aim for if taken to its logical extreme. **Attempted**: Searched CRDT literature specifically for causal-stability-gated garbage collection (Finding 7) — found the *theoretical* mechanism (causal stability, version-vector tracking) but no production orchestrator example applying it to a bounded event log under gossip. **Recommendation**: This is the single most important gap for Overdrive's design phase to explicitly resolve: **decide up front whether "durably observable" means (a) bounded-depth history embedded in/beside the existing gossiped row (matches all examined prior art), or (b) genuinely unbounded durable history (matches no examined prior art within a gossiped CRDT store, and would require Overdrive to design new machinery — e.g., a causal-stability watermark, or accepting an external durable sink the way Nomad does).** This document recommends (a) as the near-term answer precisely because it is prior-art-backed; (b) is a legitimate follow-up research question but not answered here.

### Gap 5: This research synthesizes general CRDT theory + Corrosion's documented behavior against Overdrive's *stated* architecture; no external source discusses Overdrive's exact `LogicalTimestamp{counter, writer}` design directly
**Issue**: Every claim in Findings 5-7 about how Overdrive's specific row-per-allocation, `LogicalTimestamp`-merged design interacts with the single-writer-per-key invariant is original analysis applying sourced, general CRDT/Corrosion facts to the problem statement supplied by the requester — it is not itself independently sourced (because no third party has written about Overdrive). **Recommendation**: Treat Findings 5-7's *general CRDT claims* as High confidence (well-sourced) and their *application to Overdrive's specific architecture* as reasoned interpretation, clearly labeled as such in the Recommendation section below — per this agent's principle of distinguishing facts (sourced) from interpretations (analysis).

## Conflicting Information

No direct source-to-source factual conflicts were identified during this research — the Kubernetes, Nomad, CQRS/Event-Sourcing, and CRDT-theory sources examined are consistent with and reinforce one another (all four independently converge on "small bounded current-state + separate/external larger history," per Finding 4's cross-validation). The one nuance worth flagging as a *potential source of confusion* rather than a true conflict:

### Nuance: "Deterministic ordering" vs. "safe physical pruning" of a bounded gossiped event list are frequently conflated in practitioner CRDT write-ups
**Position A (academic/primary, Almeida arXiv:2310.18220 + Shapiro et al.)**: Causal stability — a precise, formally-defined, non-trivial protocol property — is required before an operation can be safely garbage-collected/pruned from a CRDT's state without risking loss of a not-yet-seen concurrent event.
**Position B (several medium-trust practitioner blogs surfaced during search, not independently fetched/cited in Findings above)**: Some community write-ups describe "keep the last N by timestamp" as if it were a simple, free consequence of having a total order (e.g., an HLC), without distinguishing "sort deterministically" from "safely delete beyond N."
**Assessment**: Position A is authoritative (peer-reviewed/formal academic literature, directly cited in Finding 7) and Position B, where it appears, understates the difficulty — it was not relied upon for any claim in this document and is noted here only to warn a future reader against the same conflation when reading secondary CRDT material online.

## Recommendation

Ranked against the two hard constraints stated by the requester — **(1) durably observable** (an operator can see that a crash-then-recover happened) and **(2) correct under LWW gossip merge** (no coordinator, must converge identically on every peer) — using only the sourced findings above.

### Ranking

**1. `last_terminated`-style sub-struct on the existing `alloc_status` row (Kubernetes' `lastState` shape) — RECOMMENDED as the minimum viable fix**
- **Durably observable**: Directly closes the exact gap in the reported defect. `Running(1) -> Failed(2) -> Running(3)` becomes `state=Running, last_terminated={reason, exit_code, terminated_at, recovered_at}` — the crash is visible in the same durable row an operator already polls via `overdrive workload describe`, with zero new query surface. Per Finding 1, this is bounded to the **most recent** crash only — a second crash before the first is acknowledged/observed overwrites it, exactly matching Kubernetes' own documented (and accepted) limitation.
- **Gossip-safety**: **Not disqualified.** These are ordinary additional columns on the same row, written atomically in the same transition write that already carries the row's `LogicalTimestamp{counter, writer}`. This introduces **no new CRDT primitive and no new correctness argument** beyond what Overdrive's row already relies on today — it inherits exactly the same guarantee (and exactly the same single-writer-per-key precondition) the rest of the row already has. This is the CRDT-safest candidate specifically *because* it adds nothing new to reason about.
- **Trade-offs**: Storage growth is O(1) — fixed-width fields, never grows regardless of crash-loop depth (Finding 8). API/migration cost is small (additive columns; per the codebase's rkyv-envelope-evolution discipline this is a `V_{N+1}` envelope bump, not a breaking change). The known limitation — depth-1, second crash overwrites the first — is explicitly the same limitation Kubernetes ships in production; it is a **documented, prior-art-accepted trade-off**, not a novel risk.

**2. Monotone `restart_count` scalar on the same row — RECOMMENDED as a companion, not a substitute**
- **Durably observable**: Alone, insufficient — a bare counter tells an operator *that* crashes have accumulated but not *what* the most recent one was. Combined with candidate 1, it answers "how many times has this happened overall" (Nomad's `Restarts`/Kubernetes' `restartCount` role) alongside "what was the most recent occurrence" (`last_terminated`).
- **Gossip-safety**: **Conditionally safe — flag the condition explicitly.** Per Finding 5, a scalar counter merged by Corrosion's plain LWW rule (highest `col_version` wins) is correct **only under the single-writer-per-key invariant** Overdrive's row-per-allocation design already assumes. It is **not** a true G-Counter (which merges per-writer slots component-wise and is safe under *any* concurrent writers). If Phase 2 HA/failover ever produces a genuine window where two nodes concurrently believe they own the same allocation, a plain-LWW `restart_count` can silently lose a legitimate increment (Finding 5) — this is a real, sourced, CRDT-theoretic caveat, not speculation. **This document recommends shipping it as a plain LWW scalar now** (matching Overdrive's existing row-merge model exactly, zero new machinery) **while explicitly tracking the split-brain/concurrent-ownership edge case as a documented, not-yet-closed risk** — promoting to a true per-writer G-Counter shape is a legitimate future hardening step if/when concurrent ownership becomes a real production scenario, not before.
- **Trade-offs**: Trivial storage/API cost (one more scalar field); the correctness caveat above is the only cost, and it is a **documented risk carried forward, not a design flaw introduced by this recommendation** — it is the same risk profile the rest of the row already carries today.

**3. Separate append-only crash/event table — RECOMMENDED as a follow-up, not the immediate fix**
- **Durably observable**: The most complete answer — preserves full crash history (not just the latest), directly answering "was there a crash-loop and what did each occurrence look like." Requires a new query surface (analogous to `kubectl get events --field-selector` or `nomad alloc status`'s "Recent Events" block).
- **Gossip-safety**: **The most theoretically clean of all four candidates.** Per Finding 6, an append-only table keyed by a per-row-unique key (e.g. `(allocation_id, logical_ts, writer)`) has exactly one writer for each row's entire lifetime — there is no LWW conflict to resolve at all, and the structure is the practical analogue of a G-Set/OR-Set (Finding 5's convergent, coordinator-free primitives). This is **not disqualified** by the gossip constraint; it is the candidate that most cleanly satisfies it.
- **Trade-offs**: The real cost is **retention**, not correctness. Per Finding 7, if the design goal is *unbounded* durable history, physically bounding storage while staying gossip-safe requires either (a) never physically deleting (accept unbounded growth, mirror Nomad's advice to externalize long-term retention if that becomes untenable), or (b) building causal-stability-gated garbage collection — genuinely new protocol machinery with no prior-art precedent found in this research (Gap 4). The pragmatic middle ground, matching what Nomad does locally (a fixed-depth ring), is to cap the table at N rows **per allocation** with monotonic eviction of the oldest **by the row's own writer** (never cross-writer pruning) — this keeps pruning inside the single-writer-per-key safety envelope candidate 1/2 already rely on, sidestepping the causal-stability problem by only ever deleting rows the deleting writer itself created.

**4. "Just use the existing in-process `LifecycleEvent` broadcast, made durable" — NOT a standalone candidate; collapses into #3 or is disqualified**
- If "durable retention" means persisting the broadcast into the same gossiped/queryable Corrosion store, this is **structurally identical to candidate 3** — evaluate it as #3, not as a separate design.
- If "durable retention" means persisting it only in **per-node local durable storage** (mirroring Nomad's non-gossiped local ring buffer), it is **disqualified from being the durably-observable answer at the cluster level**: an operator polling `overdrive workload describe` from an arbitrary peer would not see history recorded only on the node that happened to run the crashed allocation, breaking the gossip-based "any peer answers" observability model the rest of Overdrive's `alloc_status` row already provides. It may still be a reasonable **local debugging aid** (e.g., a per-node ring buffer of recent lifecycle events for `journalctl`-style local inspection) but is explicitly not a substitute for durable, cluster-visible crash observability.

### What is disqualified by the gossip constraint, and why

**A single LWW-merged blob column encoding "the last N events" as one value (e.g., a JSON array overwritten wholesale on each write) is disqualified.** Per Finding 7, physically bounding a list to "last N" while remaining correct under concurrent gossip merge requires either a single-writer-per-key invariant applied to the *whole blob* (in which case it degenerates to no better than candidate 1/2, but with worse ergonomics and larger diffs per write) or causal-stability tracking this repo has no precedent for. Under LWW, two peers concurrently appending to their own copies of the blob and racing to write it back will have one peer's entire contribution — not just the conflicting entry, the *entire list* — silently discarded by the other's higher `col_version`, which is a strictly worse failure mode than any of candidates 1-3. Notably, **neither Kubernetes nor Nomad uses this shape** (Finding 1's `lastState` is plain fields, not a blob; Finding 3's Nomad ring buffer is per-node local state, never gossiped/CRDT-merged) — the absence of this pattern in either system's design is itself corroborating (if indirect) evidence that the shape does not compose well with a distributed merge model.

### What this document is NOT answering

Per Gap 4/5: this document does not resolve whether Overdrive should eventually build genuinely unbounded, causal-stability-gated durable history inside the gossiped store — no examined production orchestrator does this, so there is no prior art to recommend for it. The recommendation above is scoped to what the prior art *does* support: bounded current-state extension (candidates 1-2) as the immediate, low-risk fix for the reported defect, with a bounded-and-single-writer-pruned append-only table (candidate 3) as the natural next step if bounded-depth-1/N history proves insufficient in practice.
