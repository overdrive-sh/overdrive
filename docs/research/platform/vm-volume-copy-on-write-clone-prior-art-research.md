# Research: Copy-on-write cloning of VM disks — prior art from boxlite, hyper, kubeswift

**Date**: 2026-11-17 | **Researcher**: nw-researcher (Nova) | **Confidence**: Medium-High (source reading; no code executed) | **Sources**: 3 repositories read at code level, 1 Overdrive file set, Linux v7.0 source, 7 GitHub issue pages

## Executive Summary

The three projects use three different CoW layers, and between them they cover the mechanism space that matters for Overdrive issue #348:

- **boxlite** clones with a **qcow2 backing chain** it writes itself. A clone is a 4 KiB-ish qcow2 header pointing at an immutable, renamed-into-place base file, and the VMM (libkrun, or its own `imago`-based virtio-blk backend) resolves the chain. Base lifecycle is a SQLite refcount table backed by a filesystem-scan garbage collector that does not trust the table alone.
- **hyper** (Firecracker, Elixir) uses **device-mapper**: `dm-snapshot` stacks for read-only image layers and a **dm-thin pool** whose thin volumes (with an external read-only origin) are the per-VM writable rootfs. A VM fork is a dm-thin internal snapshot of a suspended parent. The pool is **rebuilt empty on every node start**; per-VM disks are ephemeral by design, and the repo's own issues list leaked thin ids and pool exhaustion as open problems.
- **kubeswift** (Cloud Hypervisor) has the closest fit to Overdrive: an opt-in **node-local dm-thin pool** where a base image is written once into a thin volume and every guest disk is `create_snap` of it, handed to Cloud Hypervisor as `--disk path=/dev/mapper/...,image_type=raw,direct=on`. Its registry code is the most careful treatment of crash-safe create, never-re-snapshot-on-restart, and base eviction of the three. Its `cloneFromSnapshot` is **not** a disk clone: the Cloud Hypervisor memory snapshot does not capture the disk, and shared-base guests are refused for that feature. Disk cloning and memory snapshotting are separable, and the repo keeps them separate.

None of the three enforces single-writer at the storage layer; each relies on its orchestrator never launching two VMs on one disk. Overdrive's existing `FICLONE` rootfs path is a fourth mechanism (reflink of a raw image) and is the only one of the four with no host-kernel module dependency beyond a reflink-capable filesystem. Its per-launch semantics (replace-on-retry, delete-on-failure) are correct for an ephemeral clone and would be wrong for a persistent volume (see Synthesis).

**Recommendation (reasoned, separate from evidence):** for the dev-environment use case (many VMs from a warm `target/`), a **reflink of a raw image on a reflink-capable filesystem** is the lowest-dependency fit with Overdrive's appliance model, with **dm-thin** as the alternative to evaluate if a measured need for block-level discard/space accounting or non-reflink filesystems emerges. A qcow2 backing chain is the weakest fit: it needs qcow2 support in the CH fork's block path, adds chain-pinning lifecycle that the other two mechanisms push down into the kernel/filesystem, and boxlite's own GC code shows how much bookkeeping that costs. Three claims that would change this ranking are unverified (see Knowledge Gaps).

## Findings

### F1 — Overdrive's existing path (baseline)

**Evidence.** `ficlone_rootfs` removes any existing `clone_dest` (replace, never adopt), opens `create_new`, calls `ioctl_ficlone`, and on failure removes the destination; `EXDEV` maps to `ConfinementUnavailable { UidDrop }` with no copy fallback (`od:crates/overdrive-host/src/vmm.rs:684-732`). `create` calls it via `spawn_blocking` before spawn, and removes the clone if the hypervisor is absent (`vmm.rs:461-479`). The clone destination is in a platform-owned staging dir and carries the allocation id in its filename; an **index symlink is created before the clone and removed after**, so "no link implies no clone" and reclamation walks the index (`od:crates/overdrive-core/src/vm/config.rs:592-634`, `681-698`). The GH #97 comment records the two constraints: same filesystem (else cryptic cross-device failure, no copy fallback) and traversability by the dropped uid; both hold by construction on the appliance.
**Kernel.** `vfs_clone_file_range` returns `-EXDEV` when source and destination superblocks differ (`vendors/linux/fs/remap_range.c:384-385 @ v7.0`) and `-EOPNOTSUPP` when the filesystem has no `remap_file_range` (`:391-392`). `.remap_file_range` is wired in btrfs, XFS and overlayfs (`fs/btrfs/file.c:3866`, `fs/xfs/xfs_file.c:2042`, `fs/overlayfs/file.c:650`); a grep of `fs/ext4/file.c` finds no `.remap_file_range`, so **ext4 cannot serve FICLONE** on this kernel. FICLONE is dispatched at `fs/ioctl.c:540-541`.
**Confidence**: High.

### F2 — boxlite: qcow2 backing chain written by the host process

**Clone mechanism.** `clone_boxes` takes N and does three phases: (A) inside a VM-quiesce bracket, `create_base_disk` renames the source box's live `disk.qcow2` to `bases/<id>.qcow2` and writes a fresh COW child at the original path so the source keeps running; (B) for each clone, write an empty qcow2 overlay header whose backing file is the shared base; (C) provision each clone and record a ref (`bx:src/boxlite/src/litebox/clone_export.rs:46-189`; quiesce at `:91`, overlays at `:126-132`). `fork_qcow2` is the rename-plus-child step: `rename`, falling back to copy+remove on `EXDEV`, then `create_cow_child_disk(dest, Qcow2, source, virtual_size)` (`bx:src/boxlite/src/disk/mod.rs:206-251`, rename `:214`, EXDEV copy `:215-230`, child `:243`). The overlay is built by hand in Rust, not `qemu-img`: `write_cow_child_header` writes a qcow2 v3 header, backing path (canonicalised, `:555-566`), backing-format extension, zeroed L1 table and one refcount block (`bx:src/boxlite/src/disk/qcow2.rs:543-742`), then `sync_all` (`:730-739`). A code comment claims this cuts COW-disk creation from ~28 ms (qemu-img subprocess) to ~1 ms (`qcow2.rs:176-180`): **claimed, no benchmark for it found**.
**What the VMM sees.** A qcow2 file with a backing chain. libkrun path: `krun_add_disk2(ctx, id, path, KRUN_DISK_FORMAT_QCOW2, read_only)`; the doc comment warns that a non-raw image "can reference other files, which libkrun will automatically open" (`bx:src/boxlite/src/vmm/krun/context.rs:521-523`, `533-574`). Boxlite also ships its own virtio-blk backend on the `imago` crate which "opens the backing chain its header names" (`bx:src/vmm/src/virtio/blk/imago.rs:4-47`). No cache-mode / `O_DIRECT` flag is passed on the libkrun call (`context.rs:565-573`). Which VMM is the default was not determined.
**Write path / durability.** In the `imago` backend a virtio write with the sync bit set, and any flush request, call `image.flush()` then `image.sync()` (`imago.rs:58-62`, `94-97`). The libkrun path's host-side cache/flush behaviour lives in libkrun, which is not in this repo: **unverified**.
**Base lifecycle.** Bases are flat files named by id under `bases/`, tracked in a DB table (`bx:src/boxlite/src/disk/base_disk.rs:298-331`: rename, then DB insert, then `add_ref` for the source). A clone's ref is added after `provision_box`; if `add_ref` fails the code only logs a warning (`clone_export.rs:164-175`). `try_gc_base` deletes a clone-base only when the DB shows no dependents, failing closed on DB error (`has_dependents(..).unwrap_or(true)`, `base_disk.rs:337-373`), and cascades to the parent base. Because a crash between rename and DB insert orphans a file invisible to the DB, `gc_orphans` starts from the filesystem: a file is deleted only if **both** no DB row names it **and** no overlay or base header backs onto it, and only if older than a 5-minute grace (`base_disk.rs:84-86`, `178-289`). Chain walks cap at depth 8 (`qcow2.rs:1065`) and "can under-report", which is why two independent guards exist (`base_disk.rs:108-127`). Changing a base is not supported: a base is immutable by construction (renamed away from the writer); `set_backing_file_path` is a header-only rebase valid only when "the backing data is identical but stored at a different path" (`qcow2.rs:947-960`). Deleting the base under live clones is prevented by refcount/chain scan, not tolerated.
**Single writer / concurrency / crash.** A runtime-wide `flock(LOCK_EX|LOCK_NB)` allows one runtime per home dir (`bx:src/boxlite/src/runtime/lock.rs:62`). Disk-mutating operations (clone, snapshot, export) serialise on a per-handle `tokio::sync::Mutex` (`clone_export.rs:71`); an open upstream issue says that after `stop()` invalidates the cache a second handle can enter the same critical section, and that disk work has no coordination with a second process (`boxlite-ai/boxlite#2738`, open, via fetched summary). Clone staging dirs are made inside `boxes_dir`, renamed into place by `provision_box` (`bx:src/boxlite/src/runtime/rt_impl.rs:1357-1411`), and on boot `recover_boxes` runs `cleanup_orphaned_directories` for dirs with no DB record and then `gc_orphans` (`rt_impl.rs:1414-1429`, `1658`, `1673`). That is converge-on-boot in spirit: the filesystem is scanned and reconciled against the DB, not trusted blindly.
**Space / performance.** Sparse qcow2; overlay "starts empty, all reads go to the backing file" (`qcow2.rs:546-547`). Flatten to a standalone image exists for export (`qcow2.rs:253-475`); it errors on compressed clusters (`:1334-1338`). README claim of "per-box QCOW2 disk with copy-on-write" (`bx:README.md:164`) is backed by the code above. Online grow is a design issue, open (`boxlite#2717`).
**Host requirements.** Any filesystem; no kernel modules; no external daemon (`qemu-img` helpers exist but are `#[allow(dead_code)]`, `qcow2.rs:124-126`, `744-746`).
**Confidence**: High on mechanism and lifecycle (single code base, read directly); Low on libkrun durability.

### F3 — hyper: device-mapper (dm-snapshot layers + dm-thin mutable layer)

**Clone mechanism.** Images are chains of read-only layer files composed with `losetup` + `dm-snapshot`; the VM's writable disk is a **dm-thin volume with that composed device as read-only external origin** (`hy:docs/cookbook/architecture.md:114-124`; `hy:lib/hyper/node/img/thin_pool.ex:6-12`). A fork of a running VM calls `ThinPool.create_volume(name, ro_dev, parent)`; the suid helper opens the parent thin device and runs `snapshot` then `activate`, deleting the thin id on failure (`hy:native/suidhelper/src/cli/thin.rs:117-144`). `snapshot` is **suspend origin, send `create_snap <new> <origin>`, resume (retried once)** (`hy:native/hyperrs-linux/src/dm/thin.rs:292-314`). Fork is documented as disk-only, crash-consistent, guest asked to `sync` best-effort first; memory forking is "future work" (`hy:docs/cookbook/architecture.md:316-339`). A slower "materialize" fork reads the pool metadata (`thin_dump`) to copy divergent blocks into a `dm-snapshot` COW file published as a new delta layer (`hy:lib/hyper/node/img/publish.ex:1-16`; `thin_dump` need at `hy:docs/cookbook/install.md:62-65`).
**Kernel check.** The kernel docs say an active origin "must" be suspended before `create_snap`, "NOT enforced" (`vendors/linux/Documentation/admin-guide/device-mapper/thin-provisioning.rst:186-188 @ v7.0`), which matches hyper's suspend bracket. `create_snap` is a pool message handled by `process_create_snap_mesg` (`drivers/md/dm-thin.c:3724-3750`, dispatch `:3858-3859`) and the message handler commits pool metadata on success (`dm-thin.c:3876-3877`).
**What the VMM sees.** A `/dev/mapper` block node, mknod'ed into the jail, as a Firecracker drive with `is_read_only: false` and `path_on_host` (`hy:lib/hyper/node/fire_vmm/boot_spec.ex:48-53`). No `cache_type` or `io_engine` setting appears anywhere in `hy:lib/` (grep), so Firecracker's default applies. Firecracker's default cache type is a Firecracker fact I did not verify in this study: **unverified**.
**Base lifecycle.** Layers are immutable files on a shared "layer storage medium" with a PostgreSQL metadata DB of dependencies and VM leases (`architecture.md:87-104`). Layer GC prunes only blob rows whose file is already gone; it never deletes a layer file, and a dangling referenced blob is reported, never deleted (`hy:lib/hyper/img/db/gc/prune.ex:1-19`; open issue `harmont-dev/hyper#126`: no layer file is ever deleted, fork chains have no depth limit, reaper never sends `delete <thin_id>`). Base refresh is not an operation: a new image is a new chain.
**Persistence.** The pool is **recreated empty at every node start**: `init` materialises two sparse files in `scratch_dir`, zeroes the metadata, and creates the pool (`thin_pool.ex:76-81`, doc at `:3-7`); the suid helper zeroes the metadata header on pool create (`hy:native/suidhelper/src/cli/thin.rs:92-108`); `terminate` removes the pool (`thin_pool.ex:132-136`). `Mutable` is `restart: :temporary` and destroys its thin volume on idle (`hy:lib/hyper/node/img/mutable.ex:19-27`). **Inference (labelled):** per-VM disks do not survive a node restart. They are ephemeral by design, so hyper's thin usage is not prior art for a persistent volume.
**Single writer / crash.** One `Mutable` server per VM id via a `Registry` name (`mutable.ex:71-73`), thin ids from a bump pointer plus freed stack inside one GenServer, and a `:global.trans` lock serialising operations on a fork parent (`thin_pool.ex:60-64`, `139-151`). Failed deletes "retire" the id (never reused) with a log line (`thin_pool.ex:147-151`). Cleanup after a crash is a periodic reaper that needs two orphan sightings; a `TODO(arch)` in the code states the cleanup is not yet a primary reconciler and that correctness depends on BEAM process lifetime (`hy:lib/hyper/node/reaper.ex:73-82`). This is the anti-pattern Overdrive's reconciler rules name.
**Space.** Pool is a fixed 64 GiB data / 1 GiB metadata **sparse file** pair, 64 KiB blocks (`hy:lib/hyper/cfg/img.ex:25-35`). Open issue #119 (reported by code reading, "not reproduced"): one guest can fill the pool and stall every VM on the node for 60 s then error; pool uses kernel defaults and low-water 0; nothing monitors usage. No benchmarks or timing numbers were found in hyper's docs (grep for ms/benchmark returned none relevant).
**Host requirements.** Kernel modules `dm_snapshot dm_thin_pool loop`, `thin-provisioning-tools` (`thin_dump`), `dmsetup`/`losetup`, a setuid helper so the node runs unprivileged (`hy:docs/cookbook/install.md:37-48`, `96-110`, `308-311`).
**Confidence**: High on mechanism; Medium on issue content (title + fetched summary only).

### F4 — kubeswift: node-local dm-thin shared-base disks on Cloud Hypervisor (closest fit)

**Clone mechanism.** `SwiftGuestClass.spec.sharedBaseDisk: true` gives a guest a thin snapshot of a per-node base (`ks:docs/shared-base-disks.md:3-14`). `Manager.CreateBase` = `create_thin <id>` + `dmsetup create ... thin`; `SnapshotBase` = `create_snap <guest> <base>` + `dmsetup create ... thin` + `dmsetup mknodes` (`ks:internal/thinpool/thinpool.go:162-211`). Pool table is `thin-pool meta data BlockSectors lowWater` with block zeroing **on**, `queue_if_no_space` and discard passdown left default; the code gives the reasons (a measured leak of a prior tenant's bytes with `skip_block_zeroing`, "3824 occurrences ... in a single 64 KiB block", ~6% cost on first-touch partial-block writes) (`thinpool.go:122-140`). Kernel confirms those are the knobs: `skip_block_zeroing`, `error_if_no_space` feature args (`dm-thin.c:3166`, `3178`).
**Origin is not suspended** because a base is written once and its device removed before any snapshot, so there is no active origin to quiesce and no per-guest serialisation point (`thinpool.go:185-188`). This is the main design difference from hyper (which snapshots a live, running parent) and it sidesteps the "NOT enforced" suspend hazard above.
**Disk size is independent of the base.** A snapshot may present a larger thin length than its origin; the extra reads as zeros and "the existing clone-grow step applies" (`thinpool.go:179-183`).
**What the VMM sees.** A `/dev/mapper/<name>` raw block device passed opaquely to Cloud Hypervisor `--disk path=<value>` (`ks:internal/runtimeintent/build.go:15`, `build_test.go:103`); root and PVC data disks use `path=...,image_type=raw,direct=on` (O_DIRECT, "cache=none parity"); emptyDir/tmpfs-backed disks cannot (`ks:rust/swift-ch-client/src/config.rs:360-435`).
**Write path and durability.** For file-backed pool devices it attaches a loop device with `--direct-io=on` and **reads the flag back, failing if DIO is off**, because the default loop path acknowledges O_DIRECT guest writes from host page cache and "a node crash loses writes the guest was told were durable" (`ks:internal/thinpool/backing.go:77-137`). The production shape is a block device or LV with no loop layer (`backing.go:13-19`); file backing is the fallback at ~18% cost (claimed in the comment). Kernel: loop honours `LO_FLAGS_DIRECT_IO` only if `lo_can_use_dio`, silently dropping the flag otherwise (`vendors/linux/drivers/block/loop.c:194-207 @ v7.0`) which confirms the silent-downgrade risk they guard. dm-thin commits metadata when a flush/FUA bio arrives for a device that changed in the current transaction (`dm-thin.c:735-739`), so a guest flush reaching `/dev/mapper/...` is what makes new mappings durable. Pool data files are `fallocate`d (never sparse), built beside the final path, `Sync`ed, renamed, then the directory is synced (`backing.go:215-284`).
**Base lifecycle.** `EnsureBase(key)` takes a per-key flock so exactly one writer populates a base and others wait; the registry flag `BaseReady` is set only after the writer syncs; a base with an allocated id but no ready flag is a crashed populate and is **thrown away and recreated under the same id** (`ks:internal/thinpool/materialize.go:18-29`, `47-57`, `244-251`; `registry.go:269-293`). Population skips all-zero pool blocks, because dm-thin allocates on any write including zeros (`materialize.go:294-304`). Bases are a **cache**: dm-thin refcounts shared blocks, so deleting a base leaves derived guests byte-identical and writable; eviction is LRU with bases that live guests were snapshotted from evicted last (`materialize.go:126-136`; `ks:docs/shared-base-disks.md:110-125`; also "measured, §7.5" in the comment — the §7.5 measurement document itself was not located). A guest is never re-snapshotted: `EnsureGuest` checks "already mapped", then "registry knows and marked created → `Activate` the existing thin id", because re-snapshotting would "hand it a pristine disk: every write it had made, silently gone" (`materialize.go:27-29`, `371-398`; `thinpool.go:213-222`). Refreshing a base for existing guests is not a feature: a new image content key yields a new base; existing guests keep their blocks.
**Single writer / crash-safety.** Guests are pinned to the node holding their disk (`shared-base-disks.md:82-89`); one launcher pod per guest is Kubernetes' guarantee, not a storage-layer lock. The registry is written atomically under a lock and "is NOT authoritative about which ids exist — the pool's own metadata is" (`registry.go:19-29`); `Advance` recovers a registry that fell behind the pool after `create_thin` "File exists" (`registry.go:187-210`, `materialize.go:442-477`). A guest id that is allocated but not marked created is dropped and a **fresh** id taken, never activating the old one (`materialize.go:399-410`). `MarkGuestCreated` is called only after `create_snap` succeeds (`registry.go:234-250`). Freed ids are never reused (`registry.go:204-210`). `ReleaseGuest` is idempotent and deletes the thin device **before** forgetting its mapping (`materialize.go:486-496`). This is the clearest observe → diff → converge-shaped code in the three repos, applied to a persistent per-guest id.
**Space and performance.** Pool preallocated (default 40 GiB), refuses to be created if it would leave the filesystem under 10% free (`shared-base-disks.md:49-60`, `backing.go:159-197`). Status is `dmsetup status` used/total 64 KiB blocks (`shared-base-disks.md:127-140`). **Doc-stated measurements** (no raw output in the repo found): second guest's first boot costs 25 MiB of pool vs 1.75 GiB for a copy; disk ready in 15 s vs 55 s, on a 3.5 GiB Ubuntu image (`shared-base-disks.md:6-11`). Metadata sized at ~0.75 MiB/GiB (comment, `thinpool.go:38-45`).
**Restrictions the project itself chose.** Node-local; no migration; no CSI snapshots; no full-state snapshots; **`cloneFromSnapshot` refused** (`shared-base-disks.md:62-76`).
**How CH snapshot/restore and disk clone interact.** They are separable and deliberately kept separate. A Tier B memory snapshot "does **not** capture the disk"; a `cloneFromSnapshot` clone's root disk "is a fresh copy from the source SwiftImage", so the clone resumes memory that may expect writes the fresh disk lacks (`ks:docs/snapshots/local-snapshots.md:273-282`). In-place restore against a disk that has since moved on is refused as `DiskDiverged` with an override annotation because it "can corrupt the guest's filesystems" (`local-snapshots.md:89-96`; `ks:internal/controller/swiftrestore/local.go:115-171`). The snapshot staging step is a plain `cp -a`-style copy plus `Sync`, no reflink (`ks:cmd/snapshot-stager/main.go:11-29`, `219-237`). `cloneFromSnapshot` for shared-base guests is blocked because "a fresh disk built from the image would not match" the captured memory (`shared-base-disks.md:73`). Open: no in-place disk rollback (`kubeswift#711`); copy-on-write *memory* restore is a design item with a lab measurement (per-clone PSS 2050 vs 412 MiB with CH v54 `memory_restore_mode=copyonwrite`, experimental build, `kubeswift#869`, open).
**Other disk-clone paths in the repo** (not dm-thin): `cloneStrategy: copy` (`cp` job) vs `snapshot` (CSI VolumeSnapshot + `dataSource`). A measured table (seconds to guest IP) shows on Longhorn the CSI clone is a full copy and slower than `cp` (79 vs 160 s for one guest), while on Rook Ceph RBD it is ~2x faster (132 vs 72 s) (`ks:docs/images/clone-strategies.md:16-23`). Deleting the seed under live clones is blocked by a finalizer because deleting it mid-clone "corrupts active clones" on true CoW drivers (`clone-strategies.md:97`). A `volumeMode: Block` clone "binds with no error" and boots to a fresh empty GPT: a silent wrong-clone failure (`clone-strategies.md:111-119`).
**Host requirements.** dm-thin kernel module, `dmsetup` (with `--noudevsync` and manual `mknodes` inside containers, `thinpool.go:104-118`, `197-211`), a labelled node, a preallocated pool file or a spare block device/LV; privileged launcher.
**Confidence**: High on mechanism; Medium on numbers (claimed in docs, no raw artefacts read).

### F5 — Cross-project observations

1. **Nobody enforces one-writer at the disk.** boxlite: process lock plus per-handle mutex (open issue #2738 shows the gap). hyper: Registry name per VM id. kubeswift: Kubernetes pod identity and node pinning. Overdrive must supply its own. The kernel offers an exclusive claim on block devices (`vendors/linux/block/bdev.c:119-126`, `950-951 @ v7.0`, `bd_prepare_to_claim` at `:586-630`); whether an `open(O_EXCL)` from the CH fork reaches that path was **not verified**.
2. **Every project that persists clone identity keeps an id registry separate from the storage layer and treats the storage layer as authoritative** (boxlite filesystem scan vs DB; kubeswift pool metadata vs registry). Both found, by experience, that the registry can lose a race with a crash.
3. **A clone must never silently become "fresh".** kubeswift (`Activate` never `SnapshotBase`), CSI block-mode clone, and the disk-diverged guard all concern the failure where a retry produces a valid-looking empty or pristine disk. Overdrive's current `ficlone_rootfs` replace-on-retry is the correct behaviour only because the clone is ephemeral.
4. **dm-thin projects both pay for pool-level resource exhaustion** (hyper#119; kubeswift's 10%-free refusal, low-water, ENOSPC window). qcow2 and reflink exhaust the filesystem instead, which the host already monitors as one resource.

| Persistent across node restart | n/a (ephemeral) | yes (qcow2 files) | **no** (pool zeroed at start) | yes (pool + registry; `Activate`) |
| Single-writer enforcement | caller | runtime flock + mutex (gap #2738) | Registry name per VM | K8s + node pin |
| Durability (guest flush to disk) | inherits CH/FS | imago: `flush`+`sync`; libkrun unverified | FC default unverified | O_DIRECT + dm-thin commit on flush; DIO verified on loop |
| Space accounting | `df`/fs-specific (not read) | file size of overlay | pool used/total blocks; no monitor (#119) | pool used/total blocks; 10%-free refusal |
| Host dependency | reflink FS (XFS/btrfs; **not ext4** `fs/ext4/file.c`) | none | dm modules, thin-provisioning-tools, suid helper | dm-thin module, dmsetup, pool file or LV |
| Published numbers | none | "~28→1 ms" claimed (comment) | none | 25 MiB vs 1.75 GiB, 15 vs 55 s (doc-stated); CSI table seconds (doc-stated) |

### Trade-offs for #348, per mechanism

**Reflink of a raw image (extension of the existing path).**
- *Single writer*: not provided by the mechanism; a clone is an ordinary file, so exclusion is Overdrive's (a holder record plus the existing one-VMM-per-launch discipline). Same as every other option.
- *Converge-on-boot creation*: simplest of the three. A clone is a single file; create it under a temporary name, then rename into place. Today's `ficlone_rootfs` removes an existing destination and deletes on failure (`vmm.rs:694-731`); that is right for ephemeral clones but **must not be reused unchanged for a persistent volume** (observation F5.3: a retry must not replace an existing volume). The observe step is "does the final-named file exist and is it complete", which a rename-into-place makes binary. Boxlite's rename-staging-dir (`rt_impl.rs:1371-1381`) and kubeswift's build-beside, sync, rename, sync-dir (`backing.go:215-284`) are the two precedents.
- *fsync*: the guest's flush reaches the clone file as a normal file fsync. Durability of the *clone operation itself* (the new inode and shared-extent metadata) needs an fsync of the file and its directory; neither the kernel's per-filesystem reflink durability nor CH's flush-to-fsync mapping was read here: **unverified**.
- *Base refresh with live clones*: trivial in effect, because clones are independent files; replacing the base file affects only future clones. (Kernel extent refcounting for XFS/btrfs not read; the analogous guarantee for dm-thin is only doc/comment-backed in kubeswift.)
- *Space accounting*: shared extents make per-volume physical cost non-obvious (`du` vs `df`); filesystem-specific, not researched here.
- *Appliance dependency*: none beyond the data filesystem supporting reflink. ext4 cannot. EXDEV/same-filesystem constraint is already satisfied by the appliance's one VM data partition (GH #97 comment). Fits the CH fork's existing raw `--disk` path with no change.

**dm-thin snapshot (kubeswift shape).**
- *Single writer*: not provided; a thin device can be mapped once by name, but exclusion across VMMs is still Overdrive's. Block-device exclusive claim exists in the kernel (`bdev.c:950-951`) but its reach from CH is unverified.
- *Converge-on-boot creation*: workable but costly in bookkeeping: an id registry that is **not** authoritative, an `Advance` recovery for registry-behind-pool, never-reuse-id rules, idempotent release ordering, `Activate`-vs-`SnapshotBase` discrimination (`materialize.go:371-478`, `486-496`; `registry.go:187-210`). Pool metadata is the observe surface, which is a good property (the kernel is the truth), but the id-to-owner mapping must be persisted and reconciled by Overdrive.
- *fsync*: strongest documented analysis of the three. Guest flush → dm-thin commit if the device changed (`dm-thin.c:735-739`); pool backing must not hide writes in host page cache (`backing.go:77-137`; `loop.c:194-207`); prefer a block device/LV over a loop file. On an immutable appliance image, a dedicated block device or LV is a disk-layout decision for the image, not for the runtime.
- *Base refresh*: kernel-level refcounting makes base deletion safe; new content is a new base. Cheap eviction. Snapshots of a **live** origin need suspend (`thin-provisioning.rst:186-188`), so a "refresh the base from `main`" flow should write a new base while quiesced, as kubeswift does, not snapshot a running one as hyper does.
- *Space*: block-level, discard passdown returns space (`thinpool.go:134-136`); but a shared pool is a shared failure domain (hyper#119), requiring low-water, `error_if_no_space` vs queue policy, and metadata sizing (`thinpool.go:38-45`).
- *Appliance dependency*: `dm_thin_pool` in the pinned kernel config, `dmsetup` (or ioctl/netlink) and a pool device; a new image requirement and a new privileged surface. Under Overdrive's "only Overdrive writes node kernel state" rule this adds device-mapper state to what must be reclaimed and converged on boot.

**qcow2 backing chain (boxlite shape).**
- *Single writer*: not provided.
- *Converge-on-boot creation*: a clone is a small file whose validity depends on a named, canonical backing path; the observe surface is the header (`read_backing_file_path_checked` distinguishes IO fault from corruption, `qcow2.rs:847-930`). Boxlite had to build a DB ref table, a filesystem-scan GC with two independent guards, and a grace period to be safe (`base_disk.rs:84-289`), and still only warns when a ref insert fails (`clone_export.rs:169-175`).
- *fsync*: header written then `sync_all` (`qcow2.rs:730-739`); runtime flush semantics depend on the VMM's qcow2 implementation (imago: `flush`+`sync`, `imago.rs:94-97`; libkrun unverified). **For the CH fork the relevant fact is CH's own qcow2 support and flush path, which was not read.**
- *Base refresh*: backing file is pinned by path; changing it is only safe for identical data (`qcow2.rs:947-955`); deleting a base needs a reference count. Chain depth is a performance and robustness limit (boxlite caps walks at 8; hyper#126 reports unbounded chain depth as a defect in its own layering).
- *Space*: sparse and portable across filesystems (the one genuine advantage: works on ext4), file size is a clean per-clone cost; but dedup against the base is per-cluster only, and a guest rewriting a large file (e.g. `target/`) allocates fresh clusters.
- *Appliance dependency*: none in the kernel; requires the VMM to read qcow2 safely. Boxlite's own security note says qcow2 backing references let the image make the VMM open other host files (`context.rs:521-523`). On Overdrive's confined, uid-dropped VMM (`vmm.rs:734-777`) a backing path outside the traversable staging directory would also fail.

### Recommendation (interpretation, separate from the evidence above)

1. For the stated use case (many concurrent dev VMs from a warm Rust `target/` built from `main`, shared unchanged blocks), **reflink of a raw image is the best fit**. It adds no kernel module, no pool, no registry of kernel ids, reuses the constraint set already ratified for the rootfs (same filesystem, EXDEV fail-closed), and the base is a plain file whose refresh does not touch live clones. It makes the volume a normal file, which composes with the existing staging, index-link and reclamation discipline. Its weakness is the filesystem requirement (XFS/btrfs, not ext4) and filesystem-specific space accounting.
2. **dm-thin is the credible alternative** and kubeswift is a working reference on the same VMM. It is preferable if a measured need for block-level discard and exact pool accounting outweighs a new kernel module and a persisted id registry. The reference cost is substantial: one pool per node, sizing, the exhaustion policy, and the whole registry-reconcile discipline. Hyper shows what happens when that discipline is skipped (leaked ids, no monitoring, ephemeral pool).
3. **A qcow2 backing chain is the weakest fit** for an appliance whose VMM is a CH fork: it moves lifecycle work (pinning, GC, chain depth) from the kernel/filesystem into Overdrive, and Overdrive would own correctness of that bookkeeping.
4. Independent of mechanism, the evidence argues that **volume create must be separable from VM launch and non-replacing**: persistent-volume clone creation should not inherit the ephemeral clone's replace-on-retry. All three projects that persist per-guest disks learned this (kubeswift most explicitly).
5. Keep **disk clone and memory snapshot decoupled** if snapshots are ever added (kubeswift: a memory snapshot restored over a different disk is a corruption path; #348 already scopes snapshots out).

These are research inputs, not design commitments; no API, issue or schema is proposed here.

## Conflicting Information

- **README vs code (boxlite).** README claims "clone ... as `.boxlite` archives" and per-box QCOW2 CoW (`bx:README.md:164`). Code backs per-box CoW and clone (`clone_export.rs`, `qcow2.rs`). A comment on `clone_disk_pair` says "Used by clone operations (not yet wired)" (`qcow2.rs:809`); the live clone path is `clone_boxes`, which does not call it. No real conflict, but the dead helper should not be read as the live path.
- **README vs code (kubeswift).** README advertises `cloneFromSnapshot` "for fast VM fan-out" (`ks:README.md:32`). Code and docs show the clone's disk is a fresh image copy, not the source's disk, and the feature is refused for shared-base guests (`local-snapshots.md:273-282`, `shared-base-disks.md:73`). Position B (code) is more authoritative; the README does not say the disk is not captured.
- **hyper "COW rootfs" claim.** True for per-VM mutable layers; but they are ephemeral (pool recreated at start), so "CoW rootfs" does not imply durable clones.
