# Research: Porting Overdrive's In-Guest Transparent mTLS Mechanism (GH #303) to Unikraft and Nanos

**Date**: 2026-09-26 (revised same day) | **Researcher**: nw-researcher (Nova) | **Confidence**: High (structural mechanism, both unikernels; Cloud Hypervisor vsock backend) / Medium (effort sizing; CH boot-protocol compatibility) | **Sources**: 13 (5 primary local trees, 8 external)

## Orchestrator verification (2026-09-26)

The orchestrator spot-checked this revision's boot-protocol finding against the
local trees and found two errors. Both are corrected in place below.

- **Nanos does have a Cloud Hypervisor-compatible boot path.** Its kernel ELF
  carries a PVH entry note: `nanos:src/x86_64/crt0.s:393-401` (`.note.Xen`,
  type 18 = `XEN_ELFNOTE_PHYS32_ENTRY`, pointing at `pvh_start32`), with the
  32-bit entry at `nanos:src/x86_64/init.s:105-163` and the C entry
  `pvh_start(hvm_start_info)` at `nanos:platform/pc/service.c:436`. Cloud
  Hypervisor boots an ELF without a Linux setup header through PVH
  (`cloud-hypervisor:arch/src/x86_64/mod.rs:1243-1252` →
  `configure_pvh`, `:1338`). The MBR loader the revision cited is only the
  disk-boot path. What remains open is a real boot test under CH.
- **Unikraft's x86 KVM platform is not multiboot-only.** `plat/kvm/x86` also
  has `lxboot.S`/`lxboot.c` (the Linux 64-bit boot protocol, boot parameters in
  RSI, `unikraft:plat/kvm/x86/lxboot.S:23-32`), selected for Firecracker
  (`unikraft:plat/kvm/Config.uk:46-50`), and an EFI stub
  (`unikraft:plat/kvm/x86/efi_entry64.S`, QEMU-only per `Config.uk:58-60`).
  None of the three is PVH, and CH's direct boot accepts only a bzImage with
  a setup header or an ELF with a PVH note. So the conclusion stands for
  Unikraft (no confirmed CH direct-boot path), but the reason is "no PVH
  entry", not "multiboot only". The likely fix is adding a PVH note and entry,
  as Nanos already has.

  answer — Nanos ships an existing, exported `swap_syscall_handler()` kernel

  needs. **No core-kernel patch is required for Nanos** — this reverses the

  the per-socket `posix_socket_node.driver` field is confirmed mutable and

## Executive Summary

GH #303's mechanism — hook `connect`/`accept`, hold the app's first read/write until an out-of-band (vsock) handshake completes, relay TLS records to a host agent that holds the private key and makes the policy decision, then encrypt/decrypt in the guest using the returned traffic secrets — is **structurally portable to both Unikraft and Nanos**, and both already ship the two hardest primitives GH #303 needs: a complete virtio-vsock transport with a POSIX `AF_VSOCK` front-end, and a genuine thread-blocking primitive that can hold a syscall until an asynchronous condition is met. This revision closes all seven of the original research's Knowledge Gaps and, in doing so, resolves what was previously each target's largest open uncertainty — in opposite directions. **Nanos's core-patch question is now answered NO**: an existing, exported, already-precedented kernel primitive (`swap_syscall_handler`) lets an ordinary out-of-tree klib intercept syscalls directly, with zero core-kernel source changes. **Unikraft's core-patch question is now answered YES, definitively** (not merely "likely"): the two alternatives to a core patch (family re-registration; the generic socket-events mechanism) are each confirmed closed off by direct evidence, and a SECOND patch — against the separate `lib-lwip` repository — is additionally required to suppress poll/epoll readiness, a complication invisible to the original pass because `lib-lwip` was not yet cloned.

**Nanos is the better structural fit, more decisively than the original pass concluded.** Its `struct sock` (`src/unix/socket.h:76-111`) is a plain function-pointer table populated PER SOCKET INSTANCE at allocation time — architecturally close to Linux's `sk_prot` swap — but the mechanism this revision actually recommends operates one layer up: `swap_syscall_handler(linux_syscalls, SYS_connect, guard_connect)` (`src/unix/syscall.c:2651`), a primitive with TWO independent, already-shipping production precedents (`klib/sandbox.c`, `klib/shmem.c`). Nanos also already builds and ships mbedTLS (including AES-GCM, `library/gcm.c`) as a production klib, and this revision confirms Nanos implements no raw-packet/`AF_PACKET` socket family at all — closing off the one bypass class Unikraft cannot close. The one confirmed gap, AES-NI exclusion from the build, remains a small, scoped, well-understood fix.

**Unikraft is feasible, with its prerequisites now precisely named rather than hedged.** A patch to core `lib/posix-socket/socket.c` is confirmed necessary (not merely likely): a family-wide "decorator" second-registration is explicitly forbidden by an internal API-violation assertion, and the generic `CONFIG_LIBPOSIX_SOCKET_EVENTS` notification mechanism — real, and reachable from an out-of-tree library — turns out to carry no socket/file handle its receiver could act on. Reading the now-cloned `lib-lwip` directly surfaces a genuinely new complication: lwIP pushes poll/epoll readiness straight onto the socket's shared file state from its own internal callback, bypassing whatever driver is installed — so a SECOND small patch (against `lib-lwip`, not core) is needed to cover the non-blocking-readiness half of GH #303's mechanism. On the positive side, AES-NI is now confirmed present in `lib-mbedtls`'s build (previously an open question), and binary-compat coverage is now a direct code trace (app-elfloader → core's syscall-shim dispatcher) rather than a docs-only inference.

**A materially important, unplanned finding: Cloud Hypervisor's `--vsock` device is NOT what Overdrive's own architecture record assumes.** Reading CH's actual vsock implementation shows a pure-userspace, Firecracker-derived Unix-domain-socket muxer with zero dependence on `/dev/vhost-vsock` or `CONFIG_VHOST_VSOCK` anywhere in its source — directly refuting ADR-0068 §4's stated host-kernel prerequisite (which traces to a stale copy of Firecracker's own docs, still present verbatim in CH's own `docs/vsock.md`). This is reported to the user for correction; it is not fixed in this document. Closing that question surfaced a boot-protocol question (corrected after orchestrator verification). Cloud Hypervisor's direct boot accepts a bzImage with a Linux setup header or an ELF with a PVH note. **Nanos's kernel has a PVH note** (`src/x86_64/crt0.s:393-401`), so it matches CH's direct-boot path; a real boot test is still needed. **Unikraft's x86 KVM platform has no PVH entry** (it offers multiboot, lxboot and an EFI stub), so Unikraft has no confirmed CH direct-boot path. Adding a PVH note and entry is the likely fix. For Unikraft this gates the port; for Nanos it is a verification step.

## Findings

### Unikraft

#### F-UK-1: Socket path and interception point
**Evidence**: Unikraft's socket path is: syscall entry (`UK_SYSCALL_R_DEFINE`) → generic `lib/posix-socket` dispatch → per-address-family `struct posix_socket_ops` vtable → (for `AF_INET`) the lwIP glue driver (`unikraft/lib-lwip`, a separate repository from core; cloned and read in full this revision — see the "Additional finding" below and Gap 1's closure).

- `connect(2)` is implemented at `lib/posix-socket/socket.c:663-709` (`UK_SYSCALL_R_DEFINE(int, connect, ...)`). It resolves the fd to a `struct uk_ofile`, write-locks the file, then calls `posix_socket_connect(of->file, addr, addr_len)` (`socket.c:683`), which is the inline wrapper at `lib/posix-socket/include/uk/socket_driver.h:584-592` that dereferences `struct posix_socket_driver *d = posix_sock_get_driver(sock)` and invokes `d->ops->connect(sock, addr, addr_len)`.
- `accept`/`accept4` follow the same shape: `socket.c:434-444` → `do_accept4` (`socket.c:406-432`) → `uk_sys_accept` (`socket.c:373-398`) → `uk_socket_accept` (`socket.c:334-371`), which calls `posix_socket_accept4(sock, ...)` (the `d->ops->accept4` dispatch, `socket_driver.h:512-521`) in a retry loop that itself performs the blocking wait (`socket.c:347-355`, see F-UK-2).
- `read`/`write` on a socket fd route through the *generic* `uk_file_ops` on the socket's `struct uk_file`: `socket_read`/`socket_write` (`socket.c:103-133`, `135-165`) call `posix_socket_read`/`posix_socket_write` (or fall back to `recvmsg`/`sendmsg`) via the same per-family `d->ops` vtable.
- The vtable itself is `struct posix_socket_ops` (`lib/posix-socket/include/uk/socket_driver.h:471-500`) — one static instance per address family, registered via `POSIX_SOCKET_FAMILY_REGISTER(fam, vops)` (`socket_driver.h:750-761`), which places a `static struct posix_socket_driver` into a named linker section (`_POSIX_SOCKET_FAMILY_SECNAME`). `lib/ukvsockdev/vsock.c:1680-1681` shows the concrete pattern: `POSIX_SOCKET_FAMILY_REGISTER(AF_VSOCK, &socket_vsock_ops)`.
- **Binding granularity, REVISED this revision — the driver POINTER is per-socket-instance and mutable, though its INITIAL value is a family-wide static lookup.** A socket's `struct posix_socket_node { void *sock_data; struct posix_socket_driver *driver; }` (`lib/posix-socket/include/uk/socket.h:49-54`) is embedded, one per socket, inside the CORE-private `struct socket_alloc` (`lib/posix-socket/socket.c:78-86`, heap-allocated per socket by `uk_socket_create`, `socket.c:265-289`). `_socket_init` (`socket.c:238-244`) COPIES the family-static lookup result (`d = posix_socket_driver_get(family)`, `socket.c:267`) into `al->node.driver` — a plain, non-const struct field. The accessors `posix_sock_get_node()` / `posix_sock_get_driver()` (`lib/posix-socket/include/uk/socket_driver.h:94-130`) are `static inline` functions in a PUBLIC header, and `struct posix_socket_node`'s fields are NOT opaque — so an OUT-OF-TREE library that already holds a `posix_sock *` (== `struct uk_file *`, obtained the same way any socket-consuming code obtains one) CAN write `posix_sock_get_node(sock)->driver = &guard_driver;` on that ONE socket instance, without touching any other socket of the same family. This is a MEANINGFUL CORRECTION to the initial read of this code: the earlier conclusion ("every AF_INET socket forever dispatches through the ONE static lwIP posix_socket_ops table") described the *initial* value correctly but overstated its immutability — the per-instance STORAGE is a closer structural match to Linux's per-socket `sk_prot` swap than first assessed.
- **A family-wide "decorator" alternative is CONFIRMED FORBIDDEN, not merely undocumented.** `lib/posix-socket/driver.c:93-115` (`posix_socket_family_lib_init`) explicitly asserts, at boot, `UK_ASSERT(posix_socket_driver_get(d->family) == d)` for every registered driver, with the comment "Ensure that there are not two drivers that want to register the same address family. **Since this would violate the API**, we do this check in debug builds only." `posix_socket_driver_get()` itself (`driver.c:57-70`) linearly scans a linker-section-backed array and returns the FIRST match — so a second `POSIX_SOCKET_FAMILY_REGISTER(AF_INET, &guard_ops)` from a new out-of-tree library would either silently lose the race (if it registers after lwIP) or silently shadow lwIP (if it registers first, an undefined-order outcome), and trips the API-violation assertion in debug builds either way. **This closes the "nothing overtly prevents registering a synthetic decorator family" open question from the prior revision — it is prevented, and documented as prevented.**
- **The one genuine, generic, out-of-tree-usable extension point (`CONFIG_LIBPOSIX_SOCKET_EVENTS`) exists but is CONFIRMED INSUFFICIENT for this purpose.** `lib/posix-socket/events.h` and `lib/posix-socket/include/uk/socket_event.h` implement a real pub-sub mechanism: `UK_SOCKET_EVENT_RECEIVER(family, event, recvfn)` registers a callback that fires synchronously, inline, within the `CREATE` / `CONNECT` / `ACCEPT` / `BIND` / `LISTEN` / `CLOSE` syscall handlers themselves (`socket.c:287` for CREATE, `:705` for CONNECT, `:396` for ACCEPT — all called BEFORE the syscall returns to the app, so timing is right in principle). **But the event payload (`struct uk_socket_event`, `socket_event.h:35-54`) carries only an opaque `id` (`= (uintptr_t)&al->evd`, a pointer into the PRIVATE, `socket.c`-local `struct socket_alloc` whose layout is not exposed in any public header), family/type/protocol, and copied local/remote addresses — NOT a `struct uk_file *` / `posix_sock *` handle.** A receiver cannot recover the socket object from `id` without knowing `struct socket_alloc`'s private layout (confirmed private: it is declared in `socket.c:78`, a `.c` file, with no public counterpart). This mechanism is real and usable for notification/telemetry/policy-trigger purposes, but it CANNOT by itself install the driver-swap identified above.
- **Consequence, CONFIRMED (not merely "leans toward") this revision: a small patch to `lib/posix-socket/socket.c` IS the practical mechanism** — not because the driver field is immutable (it isn't) but because nothing short of a patch to the four dispatch points (`connect()` `:663-709`, `uk_socket_accept()` `:334-371`, `socket_read`/`socket_write` `:103-165`) has access to the freshly-created `struct uk_file *` at the moment a decision needs to be made. The patch is narrow: one call-out per dispatch point that (a) checks whether this socket should be mesh-guarded and (b) on first qualifying call, does the `node->driver = &guard_driver` swap. This confirms, rather than merely inferring, the prior revision's F-UK-6 hedge.
- **Analysis (interpretation)**: this is architecturally closer to how Linux kTLS's `TCP_ULP` mechanism wraps `sk_prot` (a thin shim around the existing ops that adds pre/post processing) than to a full swap of the transport. Overdrive's mechanism would wrap the generic `lib/posix-socket/socket.c` dispatch, not replace the whole `AF_INET` driver.

**Confidence**: High (direct code read across core `lib/posix-socket` AND, this revision, the previously-uncloned `unikraft/lib-lwip`; the family-registration and event-mechanism findings are now both confirmed rather than inferred).

#### Additional finding (discovered while closing Gap 1): lwIP pushes readiness directly to the socket's `uk_file` state, bypassing whatever driver is installed
**Evidence**: `unikraft/lib-lwip/sockets.c:467-509` (read in full, local clone). `lwip_posix_socket_event_callback()` (`:467-484`) is lwIP's own internal netconn callback (fired from lwIP's own thread/event context, entirely independent of any `posix_socket_ops` dispatch) — it computes readiness bits via `get_lwip_socket_events()` (`:428-465`, purely a function of lwIP-internal state: `sock->lastdata.pbuf`, `sock->rcvevent`, `sock->sendevent`, `sock->errevent`, `sock->conn->pcb.tcp->state`) and calls `posix_sock_event_assign(sockobj, events)` (`:483`) directly on the socket's OWN `posix_sock` handle. `posix_sock_event_assign()` (`lib/posix-socket/include/uk/socket_driver.h:153-157`) is `uk_file_event_assign(sock, events)` — it writes straight into the `uk_file`'s OWN state/pollqueue (the same `al->fstate` every `poll()`/`epoll()` call reads), **with no reference to `posix_sock_get_driver(sock)` or `node->driver` anywhere in the call chain.** Confirmed further: `lwip_posix_socket_ops` (`sockets.c:511-533`) sets `.poll_setup = lwip_posix_socket_poll_setup` but leaves `.poll` unset (NULL) — so the driver-consulting `posix_socket_poll()` path (`socket_driver.h:702-712`, gated behind `CONFIG_LIBPOSIX_SOCKET_POLLED`, only invoked `if (d->ops->poll)`) is never exercised for `AF_INET` sockets at all; lwIP uses the event-push model exclusively.
**Consequence**: the driver-swap mechanism above is sufficient to gate the BLOCKING call path (`connect`/`sendmsg`/`recvmsg`/`read`/`write` all dispatch through `d->ops`, confirmed unaffected) but is **NOT sufficient, by itself, to withhold poll/epoll readiness** on an `AF_INET` socket while the mTLS handshake is pending — a non-blocking app calling `epoll_wait()` on a mesh socket whose underlying TCP connection is already established would see `EPOLLOUT`/`EPOLLIN` fire from lwIP's own push, regardless of what the swapped driver's ops say, because nothing in that push path consults `node->driver`. Two structurally sound fixes, neither precedented in this tree: (a) an ADDITIONAL small patch to `unikraft/lib-lwip/sockets.c`'s `get_lwip_socket_events()`/`lwip_posix_socket_event_callback()` to consult a per-socket guard-state flag before assigning events (a second core-adjacent patch, this time against a SEPARATE repository from `lib/posix-socket`); or (b) a "proxy `uk_file`" design where the app's fd points at a NEW, guard-owned `uk_file` with its OWN independently-managed pollqueue, which internally holds and drives the real lwIP-backed socket — materially more code than the driver-swap, with no existing precedent in the tree (the `AF_VSOCK` driver builds its OWN `uk_file` from scratch; it does not wrap a second, pre-existing one). This is a genuinely new, previously-unidentified complication — see the Knowledge Gaps / New Gaps section.
**Confidence**: High (direct, complete read of the exact callback chain in the previously-uncloned `lib-lwip` repo, cross-referenced against the core `posix_socket_poll()` gating logic already on file).

#### F-UK-2: Blocking hold primitive / poll-epoll readiness
**Evidence**: Two independent mechanisms compose to give the "hold + suppress readiness" behavior GH #303 needs.

1. **Blocking retry loop is built into the syscall layer itself, not the family driver.** `connect()` (`lib/posix-socket/socket.c:683-694`): if `posix_socket_connect` returns `-EINPROGRESS` and the fd is blocking, the code calls `(void)uk_file_poll(of->file, UKFD_POLLOUT | UKFD_POLL_ALWAYS)` (`:688`) to block until writable, then re-reads `SO_ERROR`. `uk_socket_accept()` (`socket.c:334-371`) loops calling `posix_socket_accept4` and, on `-EAGAIN`/`-EWOULDBLOCK` (the `_ERR_BLOCK` macro, `socket.c:75`) for a blocking fd, calls `(void)uk_file_poll(sock, UKFD_POLLIN)` (`:354`) and retries. The same shape recurs for `recvfrom`/`recvmsg`/`sendmsg`/`sendto` (`socket.c:771-781`, `822-832`, `866-876`, `912-922`).
2. **`uk_file_poll` blocks on a poll-queue of readiness events** (`lib/ukfile/include/uk/file.h:502-513`, `uk_pollq` type in `lib/ukfile/include/uk/file/pollqueue.h`), which is driven by explicit rising/falling edge signaling from the driver: `uk_file_event_set`/`uk_file_event_clear` (`file.h:516-531`, wrapping `uk_pollq_set`/`uk_pollq_clear`). The vsock driver's own use is instructive and directly transferable: `uk_vsock_conn_response` sets `EPOLLOUT` only once the connection is actually usable (`lib/ukvsockdev/vsock.c:556-566`), and `uk_vsock_rx_payload` sets `EPOLLIN` only once data has actually landed in the socket buffer (`vsock.c:508-534`). **Withholding an event bit is exactly how a non-blocking caller is kept from observing readiness** — a modified `AF_INET`-socket wrapper can defer calling `uk_file_event_set(sock, EPOLLOUT)` (or `EPOLLIN`) until the vsock-relayed TLS handshake completes, so `poll`/`epoll`/`select` on a non-blocking mesh socket does not report writable/readable early, without any busy `EAGAIN` loop on the app's side (the suppression is structural, not a spin).
3. **The underlying thread-block primitive is `uk_waitq`** (`lib/uksched/include/uk/wait.h`): `uk_waitq_wait_event(wq, condition)` (`:198-200`) parks the *calling* Unikraft thread on a wait queue until `condition` holds, implemented via `_uk_waitq_block_until`/`uk_sched_thread_blocked` (`:76-81`) and woken via `uk_waitq_wake_up`/`_up_one` (`:262-288`). This is the general-purpose "block this thread until an external event fires" primitive `uk_file_poll` itself is built on, and is directly usable to block the calling thread's first `sendmsg`/`connect` on "vsock handshake response received" without needing to route everything through the poll-queue abstraction.

**Confidence**: High for the mechanism's existence and shape (direct code read); Medium for "this composes correctly for a first-write-blocks-until-ready TLS gate" claim, which is Analysis (interpretation) — no existing Unikraft driver in this tree implements exactly this "block first I/O on an out-of-band completion signal, independent of the underlying transport's own readiness" pattern; the vsock driver's own EPOLLOUT-gating is the closest existing analogue but gates on connection completion, not on an externally-injected async handshake.

### Nanos

#### F-NA-1: Socket path and interception point
**Evidence**: Nanos has NO separate "binary compatibility layer" the way Unikraft does — every workload is a standard Linux ELF binary whose syscalls trap directly into Nanos's own syscall-numbered dispatch (`src/unix/exec.c:1-6` includes `<elf64.h>` and loads binaries as ordinary ELF64 images; there is exactly one execution model, not a native/binary-compat split). Concretely:

- **`socket(2)` is one function with a domain switch, no separate registration mechanism**: `sysreturn socket(int domain, int type, int protocol)` (`src/net/netsyscall.c:1475`) dispatches `case AF_INET: case AF_INET6:` → the lwIP-backed path (`netsock_open`, inferred from context — not the exact line read, but the case block starts at `:1478`), `case AF_UNIX:` → `unixsock_open` (`:1487`, confirmed against `src/unix/socket.c:1022-1033`), `case AF_VSOCK:` → `vsock_open` (`:1491`, confirmed against `src/unix/vsock.c:781+`). **This one function is the single, unavoidable entry point for every socket-creating call in the entire system** — there is no separate ELF-loader dispatch table to also patch, unlike Unikraft's syscall_shim/native split (F-UK-5).
- **The per-socket dispatch table is a genuine, Linux-`sk_prot`-style, PER-INSTANCE function-pointer struct**: `struct sock` (`src/unix/socket.h:76-111`) declares `bind`, `listen`, `connect`, `accept4`, `getsockname`, `getsockopt`, `setsockopt`, `sendto`, `recvfrom`, `sendmsg`, `recvmsg`, `shutdown` as plain function-pointer FIELDS (not a shared static vtable looked up by family, contrast Unikraft F-UK-1). Every concrete socket type embeds `struct sock sock` as its first field (`struct unixsock { struct sock sock; ... }`, `socket.c:14-15`; `typedef struct netsock { struct sock sock; ... }`, `netsyscall.c:84-85`; the vsock type analogously, confirmed by field assignment shape below) and POPULATES these pointers on the individual heap-allocated object at allocation time: `unixsock_alloc` (`socket.c:986-996`: `s->sock.connect = unixsock_connect; s->sock.accept4 = unixsock_accept4; ...`), `netsock_alloc` (`netsyscall.c:1418-1426`: `s->sock.connect = netsock_connect; s->sock.accept4 = netsock_accept4; ...`), `vsock_alloc` (`src/unix/vsock.c:742-749`: `s->sock.connect = vsock_connect; s->sock.accept4 = vsock_accept4; ...`).
- **Every top-level syscall is a two-line indirect call through this per-instance table**: `connect(2)` (`netsyscall.c:1805-1815`) is `struct sock *sock = resolve_socket(current->p, sockfd); ... return sock->connect(sock, addr, addrlen);` — a direct dereference-and-call through the FIELD, not a lookup by family.
- **Direct implication for the sk_prot-swap analogy — this is a much closer structural match than Unikraft**: because the dispatch table lives on the individual socket object (not a shared static per-family table), a wrapper mechanism can, after a real `netsock_alloc()`-created socket is returned to the app (e.g., immediately after `socket(2)` returns, or at `connect(2)`/`accept4(2)` time), SAVE the original `sock->connect`/`sock->sendmsg`/`sock->recvmsg`/`sock->sendto`/`sock->recvfrom` pointers and OVERWRITE them with wrapping functions on that ONE socket instance — precisely Camblet's Linux `sk->sk_prot`-swap technique, translated verbatim. No Unikraft-style "which layer do I patch, the per-family static table or the generic dispatcher" ambiguity exists here — the natural interception point is unambiguous: the per-object `struct sock` function-pointer fields.
- **Where the swap must be inserted (open design question, not fully closed)**: `struct sock`'s pointers are populated INSIDE `netsock_alloc`/`unixsock_alloc`/`vsock_alloc`, all core-kernel functions in `src/net/netsyscall.c` / `src/unix/socket.c` / `src/unix/vsock.c` — none of which are klibs (see F-NA-6). A klib CANNOT reach inside another translation unit's static-scope allocation function to swap pointers post-hoc unless the kernel EXPORTS a hook (e.g. a socket-creation notifier) or the swap is done by patching these three allocation functions directly. No such hook was found in the code read so far (Knowledge Gap — not exhaustively searched). The pragmatic options are the same two as Unikraft's F-UK-6: (a) patch the three `_alloc` functions in core (small, well-localized diff — 3-6 lines each) to call a new gate-check/wrap hook for AF_INET/AF_INET6 sockets only, or (b) find/introduce a generic post-allocation hook in `resolve_socket()`/`allocate_fd()` that a klib can register against.

**Confidence**: High for the mechanism's existence and per-instance-swappability (direct, extensive code read across three independent socket-type implementations, all showing the identical pattern). The "no existing hook exists for a klib to install the swap without a core patch" sub-claim is SUPERSEDED this revision — see F-NA-6 below, which closes Gap 6 with a definitive positive finding (`swap_syscall_handler()`) that makes the per-`struct sock`-instance question moot: the interception can be installed at the SYSCALL level instead, entirely from a klib, with no need to reach inside `netsock_alloc` at all.

#### F-NA-2: Blocking hold primitive (blockq) / poll-epoll readiness
**Evidence**: `src/unix/blockq.c` (read in full, 355 lines) implements exactly the "hold the caller until an external event fires" primitive GH #303 needs, and it is already the primitive EVERY socket type in Nanos uses for blocking I/O — reusing it, rather than inventing a new mechanism, is the natural design.

- **Mechanism**: `blockq_check_timeout(bq, action, in_bh, clkid, timeout, absolute)` (`blockq.c:173-246`) first calls `apply(a, 0)` (the caller-supplied `blockq_action` closure) immediately (`:210`). If the action returns `BLOCKQ_BLOCK_REQUIRED`, the calling thread is registered on the blockq's waiters list (`:229`, `list_insert_before(&bq->waiters_head, &t->bq_l)`) and put to sleep via `thread_sleep_interruptible()` (`:244`) — a genuine scheduler block, not a spin. `blockq_wake_one`/`blockq_flush` (`:124-143`, `:253-267`) are called by whatever async event should unblock waiters (in the existing TCP path, lwIP callbacks like `lwip_tcp_sent`/`connect_tcp_complete` call `wakeup_sock()`, `netsyscall.c:1636-1646`, `1706-1724`, which internally wakes the relevant blockq) — the action is then RE-INVOKED (`blockq_apply`, `:52-62`, via `async_apply_1`), and if it now returns a real result (not `BLOCKQ_BLOCK_REQUIRED`), the thread's syscall return value is set and it resumes.
- **Directly transferable to GH #303's hold-and-relay design**: a new `blockq_action` for a mesh-bound socket's first `sendmsg`/`recvmsg`/`connect` checks "has the vsock-relayed TLS handshake completed?" — if not, returns `BLOCKQ_BLOCK_REQUIRED`; the vsock-relay completion handler (running the vsock callback path, see F-NA-3) then calls `blockq_wake_one`/`blockq_flush` on that socket's dedicated blockq once the host agent's Allow/Deny response and traffic secrets arrive. Every existing socket type already carries `rxbq`/`txbq` fields on `struct sock` (`socket.h:82-83`) precisely for this purpose — new code can either reuse these or allocate a purpose-specific blockq per intercepted socket.
- **Non-blocking readiness suppression**: `struct sock` embeds `struct fdesc f` (`socket.h:77`), and each concrete type wires an `events` closure (`fdesc_events`) that computes the current `EPOLLIN`/`EPOLLOUT`/etc. bitmask on demand — e.g. `netsock_events_locked` (`netsyscall.c:197-213`) computes `EPOLLOUT` conditionally on lwIP's own `ESTABLISHED` state and send-buffer availability; `unixsock_events` (`socket.c:523-558`) computes `EPOLLIN`/`EPOLLOUT` from queue occupancy; `vsock_events`/`vsock_events_internal` (`src/unix/vsock.c:337-372`) does the analogous thing for vsock. A wrapping "events" closure installed on the intercepted socket's `fdesc` (again, an assignable FIELD, per F-NA-1) can AND-mask out `EPOLLIN`/`EPOLLOUT` while the handshake is pending and let the real (wrapped) events closure's result through once ready — `poll`/`epoll`/`select` on a non-blocking mesh socket then correctly reports not-ready without any busy loop, structurally identical to the mechanism identified for Unikraft (F-UK-2) but riding on a per-instance closure field rather than a poll-queue event-bit toggle.

**Confidence**: High (direct, full-file code read of the primitive plus three independent call-site examples of its use for exactly the "block calling thread on an async condition" pattern GH #303 needs).

#### F-NA-4: In-guest crypto (TLS/AES-GCM availability)
**Evidence**: Unlike Unikraft, Nanos already ships an in-tree, building, mbedTLS-based crypto stack as an optional **klib** — this is the strongest, most concrete crypto evidence gathered in this research, including a specific negative finding on hardware acceleration.

Internally it manages a `tls_conn` struct (`mbedtls.c:9-23`, with its own `refcount`), implements `tls_send`/`tls_recv` callbacks bridging mbedTLS's BIO callback interface to Nanos's own async `buffer_handler`/`connection_handler` primitives (`mbedtls.c:55-82`, `114-210`), and provides the standard mbedTLS platform bindings a from-scratch port needs: `mbedtls_calloc`/`mbedtls_free` (`:283-300`, backed by Nanos's own allocator, not libc), `mbedtls_hardware_poll` (`:301-306`, mbedTLS's entropy-source callback), and `mbedtls_platform_gmtime_r` (`:307-317`, for certificate date validation without a libc). **This proves mbedTLS compiles and links against Nanos's kernel environment today** and is used in production-shipped klibs (`aws.c`, `azure.c`, `cloud_init.c`, `digitalocean.c`, `gcp.c` all list `tls`/mbedtls-derived sources as a dependency per `klib/klib.mk`).

It is evidence that the crypto library builds and runs, NOT evidence of an existing transparent-interception mechanism (that is wholly new work, matching Unikraft's finding, F-UK-4).
- **AES-NI is NOT compiled in — confirmed negative finding, not inference**: `klib/klib.mk`'s `SRCS-mbedtls-crypto` list (`klib.mk:99-168`, 68 file paths, read in full) includes `$(MBEDTLS_DIR)/library/aes.c` (software AES) and `$(MBEDTLS_DIR)/library/padlock.c` (VIA PadLock hardware engine — a legacy, rare x86 crypto co-processor, not AES-NI) and `$(MBEDTLS_DIR)/library/gcm.c` (GCM mode, confirming AES-GCM is available). **`$(MBEDTLS_DIR)/library/aesni.c` — upstream mbedTLS's actual AES-NI intrinsics file — is ABSENT from the build list.** This is a directly observed negative: Nanos's existing mbedTLS build produces software-only AES (or VIA PadLock, essentially never present on modern cloud/Cloud-Hypervisor hosts), NOT AES-NI-accelerated AES-GCM. A new port would need to add `aesni.c` to this list and confirm the Unikraft/Nanos build toolchain enables the needed compiler flags (`-maes`/`-mpclmul` or upstream's runtime-detection shim) — a concrete, scoped, but real task.
- **What a minimal in-guest record layer needs**: identical requirements to F-UK-4 (AEAD encrypt/decrypt on host-supplied traffic secrets, per-direction sequence numbers, `application_data`-only framing, reject-on-other-content-type). Given mbedTLS's `gcm.c`/`ssl_msg.c` are already present and building, the realistic implementation path for Nanos is arguably SHORTER than Unikraft's Rust-record-layer path: call mbedTLS's own low-level `mbedtls_gcm_crypt_and_tag`/`mbedtls_gcm_auth_decrypt` primitives directly against the host-supplied secrets, bypassing mbedTLS's own handshake state machine entirely (the handshake itself happens on the host per GH #303's design) — this reuses already-compiling, already-linked code rather than introducing a new crypto stack (contrast Unikraft, where NO crypto exists in the local core tree and a fresh Rust or C library integration is required either way).

**Confidence**: High (direct code + build-file read, including a specific negative finding on AES-NI that is unusually concrete for this kind of research).

#### F-NA-6: Build and packaging (klib mechanism, license) — Gap 6 CLOSED this revision, DEFINITIVELY REVERSING the prior hedge
**Evidence**:

A klib is declared by adding its name to the `KLIBS` list (`:5-23`) and a `SRCS-<name>` variable listing its source files (`:25-96` for the shipped klibs; `:83-85` for `tls` = `mbedtls.c` + the full mbedTLS source list). Klibs compile with `KLIB_CFLAGS` (`:218`: `-fPIC` plus `-DKLIB` and any klib-specific defines like `-DMBEDTLS_USER_CONFIG_FILE=...`) and link with `KLIB_LDFLAGS` (`:220`: `-shared -Bsymbolic -nostdlib -T$(ARCHDIR)/klib.lds`).
- **The klib LOADER was located and read this revision (`src/kernel/klib.c`, 377 lines, in full) — this directly resolves Gap 6, and resolves it the OPPOSITE way the prior revision's `-Bsymbolic` inference suggested.** `load_klib_complete()` (`klib.c:121-155`) maps the klib's ELF into freshly-allocated kernel address space (`elf_apply_relocs`, `load_elf`) and calls `klib_initialize()` (`:112-119`), which calls `elf_dyn_link(kl->elf, load_range.start, stack_closure_func(elf_sym_resolver, klib_sym_resolve))`. `klib_sym_resolve` (`:106-110`) resolves EVERY one of the klib's undefined symbol references **by name, at load time, against a live, growing, kernel-wide symbol table** (`symtab_get_addr(name)`) — and `autoload_klib_complete()` (`:214-279`, specifically `:227`) calls `add_elf_syms(kl->elf, kl->load_range.start)` on successful init, which ADDS the just-loaded klib's own symbols into that SAME table for subsequent klibs to resolve against. **`-Bsymbolic` (a link-time flag governing intra-klib PLT resolution ONLY) does not govern this — dynamic linking of a klib's undefined (extern) references happens later, at Nanos's own load time, via `symtab_get_addr`, a fundamentally different and much more permissive mechanism than the prior revision's inference assumed.** This alone establishes that a klib CAN call arbitrarily-named kernel-internal functions, provided they are present in the live symtab (i.e., not `static`).
- **A klib can go further than merely CALLING kernel functions — it can SUBSTITUTE a syscall's handler wholesale, and this is an EXISTING, EXPORTED, PRODUCTION-PROVEN primitive, not a hypothetical.** `src/unix/syscall.c:2464-2470` declares `static struct syscall _linux_syscalls[SYS_MAX];` and the public `struct syscall * const linux_syscalls = _linux_syscalls;` (declared `extern` in `src/unix/unix_internal.h:224`, i.e. visible to any code, including a klib, that includes this header). `src/unix/unix.c:590` (`p->syscalls = linux_syscalls;`) confirms this global table IS the live dispatch table every syscall trap consults (`syscall.c:2549-2551`: `struct syscall *s = t->p->syscalls + call; ... sysreturn (*h)(...) = s->handler; ...`). **`swap_syscall_handler(struct syscall *m, int n, sysreturn (*f)())`** (`syscall.c:2651-2654`, declared in `unix_internal.h:808`) replaces the handler at index `n` with `f` and **returns the OLD handler** — the exact shape needed to wrap-and-pass-through.
- **Direct, in-tree, PRODUCTION precedent for exactly this technique — two independent klibs, not a hypothetical**: `klib/sandbox.c:23-49` (`init()`, the klib's own entry point) calls, for every syscall number with a registered sandbox rule, `sbsc->default_handler = swap_syscall_handler(linux_syscalls, i, sb_handler);` (`:46`) — saving the ORIGINAL handler and installing `sb_handler` (`:7-21`) as a wrapper that runs registered checks and, if none intervene, calls `sbsc->default_handler(arg0, ..., arg5)` (`:18`) — a byte-for-byte structural match to GH #303's "hook the syscall, decide, optionally call through" requirement. `klib/shmem.c:44` (`swap_syscall_handler(linux_syscalls, SYS_memfd_create, memfd_create);`) is a second, independent klib using the identical primitive to replace a syscall outright. **Both are ordinary, out-of-tree klibs — neither required a core-kernel source patch.**
- **Conclusion — REVERSES the prior "-Bsymbolic implies core patch needed" inference**: a GH #303-style mTLS guard for Nanos can be shipped as a single klib that calls `swap_syscall_handler(linux_syscalls, SYS_connect, guard_connect)` (and similarly for `SYS_socket`/`SYS_accept4`/`SYS_sendmsg`/`SYS_recvmsg`/`SYS_sendto`/`SYS_recvfrom`) at klib-init time, using the saved original handler for pass-through. This makes the `struct sock`-per-instance-swap design from F-NA-1 an available BUT NO LONGER NECESSARY alternative — the syscall-level wrap is simpler (it sees the raw fd/buffer arguments directly, before any `struct sock` involvement) and is the one with a shipping precedent.
- **License — CLOSED this revision (Gap 7, Nanos-side).** Nanos core is **Apache License 2.0** (`LICENSE`, read in full, copyright "NanoVMs, Inc." 2019). Nanos's vendored mbedTLS is fetched from a NanoVMs-maintained fork, confirmed via `Makefile:58`: `$(MBEDTLS_DIR)/.vendored: GITFLAGS= --depth 1 https://github.com/nanovms/mbedtls.git` (`MBEDTLS_DIR = $(VENDORDIR)/mbedtls`, `Makefile:13`; no `.gitmodules` entry — it is fetched at build time via a shallow git clone, not vendored in-tree). `github.com/nanovms/mbedtls`'s own README (fetched 2026-09-26) states files are provided under Apache-2.0 by default, with contributors additionally accepting dual Apache-2.0/GPL-2.0-or-later licensing for LTS-branch purposes — matching upstream Mbed-TLS/mbedtls's own licensing scheme exactly; the NanoVMs fork does not appear to have altered the license.

**Confidence**: High for the packaging mechanism, core license, and (this revision) the klib-interposition mechanism — the loader code, the exported `swap_syscall_handler` primitive, and two independent production call sites were all read directly and in full. This is now one of the most strongly-evidenced findings in the document.

- The `ApplyLandlock for VsockConfig` impl (`vm_config.rs:869-879`) sandboxes the parent directory and the socket path itself with read/write access — consistent with an ordinary Unix-domain socket, not a device-node open.

**Conclusion**: Cloud Hypervisor's `--vsock` device needs ONLY a filesystem path for an `AF_UNIX` socket on the host — it does **not** need `/dev/vhost-vsock`, and does **not** need `CONFIG_VHOST_VSOCK` on the host kernel. The CH-authored `docs/vsock.md` text making that claim is a stale carry-over from Firecracker's own documentation (`docs/vsock.md:5`: "The `virtio-vsock` is based on the Firecracker implementation") that does not describe CH's actual, current, source-verified implementation. **This directly refutes ADR-0068 §4's claim** ("`CONFIG_VHOST_VSOCK=y` host-side (the `/dev/vhost-vsock` backend Cloud Hypervisor's `--vsock` device needs)," `docs/product/architecture/adr-0068-pinned-appliance-kernel-floor.md:113-116`). The GUEST-side requirements ADR-0068 §4 also names (`CONFIG_VSOCKETS=y`, `CONFIG_VIRTIO_VSOCKETS=y`) are unaffected by this correction — those are needed regardless of which host-side backend is in play. This correction is reported to the user; this research document does not edit the ADR.
**Confidence**: High — direct, repository-wide source read; the doc/source discrepancy is itself directly observed, not inferred.

#### F-CH-2: Virtio transport and feature-bit compatibility with the Unikraft and Nanos vsock drivers
**Evidence**: `virtio-devices/src/vsock/device.rs:381-393` — CH's vsock device advertises `avail_features = (1u64 << VIRTIO_F_VERSION_1) | (1u64 << VIRTIO_F_IN_ORDER)`, plus `VIRTIO_F_ACCESS_PLATFORM` only under IOMMU (`:391`). **No vsock-specific feature bit is offered at all.** Cross-referenced against both guest drivers:
- Unikraft (`drivers/virtio/vsock/virtio_vsock.c:1942-1986`): negotiates `VIRTIO_VSOCK_F_NO_IMPLIED_STREAM` / `_F_STREAM` / `_F_SEQPACKET` only if the HOST offers them (`VIRTIO_FEATURE_HAS(host_features, ...)`), and explicitly treats the ABSENCE of `VIRTIO_VSOCK_F_NO_IMPLIED_STREAM` as "stream support implied" (`:1973`, debug log). **Compatible** with CH's zero-vsock-feature-bit offer.
- Nanos (`src/virtio/virtio_socket.c:51`): `#define VIRTIO_SOCK_DRIVER_FEATURES VIRTIO_VSOCK_F_STREAM`, passed as the driver's REQUESTED feature set to `attach_vtpci`/`attach_vtmmio` (`:148`, `:161`). Standard virtio negotiation ANDs the driver's requested set with the host's offered set; since CH offers no vsock-specific bits, the negotiated result would have `VIRTIO_VSOCK_F_STREAM` unset. **Whether Nanos's `attach_vtpci` treats this as a hard failure or a tolerated soft miss was NOT verified in this pass** (the negotiation-enforcement code itself, in `virtio_pci.c`, was not read) — flagged as a small residual gap, not a blocking one, since Nanos's vsock code implements only `SOCK_STREAM` semantics regardless (no `SEQPACKET` code path was observed), so the bit's absence is unlikely to change behavior even if unenforced.
- Both CH (`docs/vsock.md:3`: "cloud-hypervisor only supports stream VSOCK sockets") and both guest drivers are STREAM-only in practice — a consistent, compatible baseline for GH #303's needs (which only requires `SOCK_STREAM`).
**Confidence**: High for the feature-bit offer itself and Unikraft's compatibility (direct code read both sides). Medium for Nanos's exact negotiation-failure behavior (one layer of the call chain not read).

#### F-CH-3: Boot protocol compatibility (corrected after orchestrator verification)
**Evidence**: Cloud Hypervisor's x86_64 direct boot takes one of two paths (`cloud-hypervisor:arch/src/x86_64/mod.rs:1243-1252`): a kernel with a Linux setup header (bzImage) goes to `configure_32bit_entry`; an ELF without a setup header goes to `configure_pvh` (`:1338`), which needs a PVH entry note. A repository-wide `Grep` of Cloud Hypervisor for `multiboot` returned zero matches.
- **Nanos matches the PVH path.** Its kernel ELF has a `.note.Xen` section with type 18 (`XEN_ELFNOTE_PHYS32_ENTRY`) pointing at `pvh_start32` (`nanos:src/x86_64/crt0.s:393-401`). The 32-bit PVH entry switches to long mode (`nanos:src/x86_64/init.s:105-163`), and the C entry `pvh_start(hvm_start_info)` is at `nanos:platform/pc/service.c:436`. `platform/pc/service.c:342` also references Firecracker v1.6.0, so the direct-boot path is exercised on another VMM. The MBR loader in `platform/{pc,virt,riscv-virt}/boot/` is the disk-boot path, not the only one. The earlier text in this revision said Nanos boots only through the MBR loader; that was wrong.
- **Unikraft has no PVH entry.** `plat/kvm/x86` offers three boot protocols: multiboot (`multiboot.S`, QEMU only, `unikraft:plat/kvm/Config.uk:40-44`), lxboot, the Linux 64-bit boot protocol with boot parameters in RSI (`unikraft:plat/kvm/x86/lxboot.S:23-32`, selected for Firecracker, `Config.uk:46-50`), and an EFI stub (`efi_entry64.S`, QEMU only, `Config.uk:58-60`). A `Grep` for `hvm_start_info`/`XEN_ELFNOTE`/`PVH` under `plat/kvm` returned zero matches. lxboot expects a 64-bit entry with a zero page in RSI; CH offers a 32-bit bzImage entry or PVH. The earlier text in this revision said Unikraft is multiboot-only; that was wrong, but the conclusion (no CH direct-boot path) holds.
- **Neither project lists Cloud Hypervisor as a supported target.** Unikraft names QEMU and Firecracker for KVM [unikraft.org/docs/cli/running, accessed 2026-09-26]. Nanos's wiki "Platform Support" (fetched 2026-09-26) lists AWS, Google Cloud, Xen, KVM, ESX, Azure and Hyper-V.
- **Analysis (interpretation)**: Nanos should boot on CH through PVH, subject to a real test that its root image and devices come up over CH's virtio-pci. Unikraft needs a PVH ELF note plus an entry that parses `hvm_start_info`, the same shape Nanos already has, or a firmware boot of its EFI stub through CH (untested; its Kconfig ties the EFI stub to QEMU).
**Confidence**: High for the code facts on all three trees. Medium for "Nanos boots on CH" until it is run. High that Unikraft needs a PVH entry or a firmware route.

## Knowledge Gaps

### Gap 1 — CLOSED: `unikraft/lib-lwip`'s internal connect/accept4/read/write bodies
**Resolution**: Cloned and read `sockets.c` in full (539 lines). Confirms the core-side `POSIX_SOCKET_FAMILY_REGISTER(AF_INET, &lwip_posix_socket_ops)` mechanism directly (superseding the prior GitHub/DeepWiki-only citation), and surfaces a genuinely new complication: lwIP pushes poll/epoll readiness directly onto the socket's shared `uk_file` state from its own internal callback (`lwip_posix_socket_event_callback` → `posix_sock_event_assign`), bypassing whatever driver is installed on that socket. The driver-swap mechanism (F-UK-1) is confirmed sufficient for the blocking read/write/connect path but NOT sufficient, alone, to withhold non-blocking poll/epoll readiness — a second patch (this time against `lib-lwip`, a separate repository from `lib/posix-socket`) or a proxy-`uk_file` design is needed to close that half of the mechanism. See F-UK-1's "Additional finding."

### Gap 2 — CLOSED: `unikraft/app-elfloader`'s exact syscall-to-handler wiring
**Resolution**: Cloned and traced directly. `app-elfloader/Config.uk:1-10` shows it `select`s core's `LIBSYSCALL_SHIM`/`LIBSYSCALL_SHIM_HANDLER` rather than implementing its own dispatch; `lib/syscall_shim/uk_syscall_binary.c:68-118` (`ukplat_syscall_handler`) confirms every trapped binary syscall is dispatched via `uk_syscall6_do_e`, the SAME generic dispatcher native `UK_SYSCALL_R_DEFINE` calls use. No separate binary-compat dispatch table exists. This closes the gap with a direct code trace, superseding the prior docs-only citation.

### Gap 3 — CLOSED (vsock backend) / PARTIALLY CLOSED (boot protocol, now the leading open risk): Cloud Hypervisor compatibility
**Resolution**: Cloned CH and read its vsock implementation directly. CH's `--vsock` is a pure-userspace, Firecracker-derived Unix-domain-socket muxer (`virtio-devices/src/vsock/unix/muxer.rs`) requiring only a host filesystem path — NOT `/dev/vhost-vsock` (zero references anywhere in CH's source; see F-CH-1). This **refutes ADR-0068 §4's claim** that CH's `--vsock` needs the host `/dev/vhost-vsock` backend — that claim traces to CH's own doc text, which is a stale copy of Firecracker's docs, not a description of CH's actual implementation. ### Gap 5 — CLOSED (negatively, for the bypass — a good outcome): Raw-socket / `AF_PACKET` support in Nanos

### Gap 6 — CLOSED, DEFINITIVELY, REVERSING the prior hedge: Nanos's klib-loading mechanism and symbol interposition
**Resolution**: Located and read `src/kernel/klib.c` (377 lines, in full) and `src/unix/syscall.c`'s syscall-dispatch internals. Two independent findings close this decisively: (1) `elf_dyn_link`/`klib_sym_resolve` (`klib.c:106-119`) resolve a klib's undefined symbols by NAME against a live, growing, kernel-wide symbol table (`symtab_get_addr`) populated incrementally by `add_elf_syms` (`klib.c:227`) — this is a fundamentally different and more permissive mechanism than the link-time `-Bsymbolic` flag the prior revision reasoned from, which governs only intra-klib PLT resolution. (2) Far more directly: Nanos exports a first-class `swap_syscall_handler(struct syscall *m, int n, sysreturn (*f)())` primitive (`syscall.c:2651-2654`, declared in `unix_internal.h:808`, operating on the exported `linux_syscalls` table, `unix_internal.h:224`) that swaps a syscall's handler and returns the original for pass-through — and TWO independent, already-shipping klibs use it for exactly this shape (`klib/sandbox.c:46`, `klib/shmem.c:44`). **No core-kernel patch is needed for Nanos** — this reverses, rather than merely refines, the prior "-Bsymbolic implies core patch needed" conclusion.

## Per-Unikernel Verdict

### Unikraft: **Feasible with named prerequisites** (verdict unchanged; prerequisites now more precise)

The mechanism GH #303 describes is buildable on Unikraft, but it requires (a) a small, CONFIRMED-necessary (not merely inferred) patch to Unikraft **core** (`lib/posix-socket/socket.c`), because a family-wide "decorator" alternative is explicitly forbidden by an internal API-violation assertion (`lib/posix-socket/driver.c:93-115`) and the generic `CONFIG_LIBPOSIX_SOCKET_EVENTS` notification mechanism, while real, carries no socket handle its receiver could act on; (b) a SECOND, separate patch against `unikraft/lib-lwip/sockets.c` — a newly-discovered requirement — because lwIP pushes poll/epoll readiness directly onto the shared `uk_file` state, bypassing whatever driver is installed, so the driver-swap alone covers the blocking I/O path but not the non-blocking readiness-suppression half of GH #303's mechanism; (c) AES-NI is now CONFIRMED PRESENT in `lib-mbedtls`'s build (a risk retired, not merely resolved-favorably); and (d) Unikraft has no confirmed way to boot under Cloud Hypervisor: `plat/kvm/x86` offers multiboot, lxboot and an EFI stub but no PVH entry, and CH's direct boot needs PVH or a bzImage setup header (corrected after orchestrator verification). Adding a PVH entry is the likely prerequisite. All the necessary LOW-LEVEL primitives — virtio-vsock + `AF_VSOCK` (`lib/ukvsockdev/vsock.c`), a genuine thread-blocking wait-queue (`lib/uksched/include/uk/wait.h`), and edge-triggered poll/epoll event suppression (`lib/ukfile/include/uk/file.h`) — already exist in the local tree and were read in full, and CH's vsock transport is now confirmed compatible with Unikraft's driver (F-CH-2). Binary-compat (Dockerfile-image) apps are confirmed, via a direct code trace this revision (not merely docs), to route through the same interception point as native apps; only a deliberately netdev-linked native app could bypass it, which is outside Overdrive's stated target workload.

### Nanos: **Feasible, no core patch confirmed** (verdict strengthens — strictly stronger claim than the prior revision's "Feasible")

Nanos remains the stronger structural fit of the two, and this revision resolves its one open mechanical question decisively in Nanos's favor.
