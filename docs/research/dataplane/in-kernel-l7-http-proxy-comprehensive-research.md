# Research: In-kernel L7 HTTP/1.1 proxying for the Overdrive public ingress gateway

**Date**: 2026-11-02 | **Researcher**: nw-researcher (Nova) | **Confidence**: High (v7.0, v7.2 working tree, and v7.3 tag source; see "v7.3 re-check") | **Sources**: ~20 kernel files + 10 web

Labels: FACT = read from source, cited `path:line @ tag`. INFERENCE = reasoned from facts. UNKNOWN = not settled by source.

## Executive Summary

**Headline (FACT, v7.0 vs v7.2 source):** sockmap and kTLS are *supported together* in v7.0 (`net/tls/tls_sw.c:853-983, 2075-2198`) but are **mutually exclusive from v7.2** (`net/tls/tls_main.c:636-645`; `tls_sw.c` `bpf_exec_tx_verdict` reduced to `tls_push_record` at `/Users/marcus/git/linux/net/tls/tls_sw.c:701-713`). The removal was merged via net-next-7.2 ("tls: reject the combination of TLS and sockmap", J. Kicinski, June 2026: "There are no known TLS+sockmap users and it has some known hard to solve bugs"). Any design that needs a BPF program to see or edit plaintext on a kTLS socket therefore dies on the first kernel pin bump past 7.0 (and may die on a 7.0.y stable update if the AUTOSEL backport is taken — UNKNOWN for 7.0.y). v7.3 was subsequently read from the `v7.3` tag and confirms the rejection is still present (see "v7.3 re-check (2026-11-02)").

**Verdict on the earlier claim — PARTLY.** "A pure in-kernel sk_msg HTTP parser would cost keep-alive or header policy" is **not supported as stated**: on plaintext sockets the stock helpers can follow Content-Length framing across sendmsg calls (`apply_bytes`/`cork_bytes`), insert and remove header bytes (`msg_push_data`/`msg_pop_data`, `skb_adjust_room`), and an academic system (XLB, arXiv 2602.09473) does persistent-connection HTTP/1.1 L7 balancing in-kernel — though with ~3000 lines of kernel modification and one outstanding request per connection. But the **conclusion that a pure-BPF gateway cannot deliver the accepted feature set is CONFIRMED, for different and stronger reasons**: (1) TLS 1.3 handshakes (public listener and exact-peer mTLS) cannot run in the kernel or in BPF; (2) after the handshake BPF can only see plaintext on a kTLS socket in v7.0, only inside a `recvmsg()` by a userspace process, one TLS record at a time, and not at all from v7.2; (3) sk_skb has no cross-invocation buffer, strparser cannot frame a chunked body or consume trailers, and no helper originates a fresh 404/502/503 response; (4) KeyUpdate needs userspace. The hybrid (userspace TLS handshake + head parsing, kTLS crypto, splice for bodies) uses only mechanisms that remain in v7.2 (`tls_sw_splice_read`, `MSG_SPLICE_PAGES`, KeyUpdate API all present in `/Users/marcus/git/linux`).

## Findings

### F1. Where each BPF program type sits (FACT)
- `sk_msg` programs (BPF_SK_MSG_VERDICT) run on the **sender's `sendmsg()` data of a socket that is in a sockmap** — `tcp_bpf_sendmsg` builds an `sk_msg` from the caller's iov then calls `tcp_bpf_send_verdict` (`net/ipv4/tcp_bpf.c:518-594`, `:404-515`). They do not see received data. A userspace process (or a kernel sender) must call sendmsg/splice on that socket. FACT.
- `sk_skb` programs (stream_parser / stream_verdict / skb_verdict) run on the **receive path**: `sk_psock_verdict_data_ready` -> `ops->read_skb(sk, sk_psock_verdict_recv)` runs the stream_verdict (or skb_verdict) prog once per skb (`net/core/skmsg.c:1236-1294`); with a stream_parser the strparser framing path is used (`sk_psock_strp_read`, `:1109-1136`; `sk_psock_strp_parse`, `:1143-1158`).
- Verdicts: `__SK_PASS` queues the skb to the socket's own ingress (readable by the app), `__SK_REDIRECT` hands the skb to another psock (ingress queue, or egress via `skb_send_sock`), `__SK_DROP` frees it (`skmsg.c:1030-1089`; egress/ingress choice `sk_psock_handle_skb`, `:646-655`).
- INFERENCE: a design with **no userspace process in the data path** can only use sk_skb on the receive side plus redirect; sk_msg is a hook on a *local sender's* writes, so it applies to a hybrid design (userspace writes heads) but not to a process-less proxy.

### F2. Helper surface per program type (FACT)
- `sk_msg` helpers: `msg_redirect_map/hash`, `msg_apply_bytes`, `msg_cork_bytes`, `msg_pull_data`, `msg_push_data`, `msg_pop_data`, `sk_storage_get/delete`, `perf_event_output`, `get_netns_cookie`, plus base sk helpers (`net/core/filter.c:8604-8632`).
- `sk_skb` helpers: `skb_store_bytes`, `skb_load_bytes`, `skb_pull_data`, `skb_change_tail`, `skb_change_head`, `skb_adjust_room`, `sk_redirect_map/hash`, `sk_lookup_*`, `get_socket_cookie` (`filter.c:8638-8676`). **No sk_storage helpers for sk_skb** in this list (per-socket state would have to live in a map keyed by socket cookie). FACT (absence in the switch; base helpers via `bpf_sk_base_func_proto` not enumerated here — UNKNOWN whether sk_storage is reachable that way; probe it).
- `sk_skb_adjust_room` is limited to `|len_diff| <= 0xfff`, mode and flags must be 0; growing zero-fills the new bytes; on a kTLS-RX socket it adjusts `strp_msg.full_len` (`filter.c:3666-3695`).
- `bpf_msg_pull_data(start,end)`: linearises (allocs a page and memcpy's) the requested range if it spans sg elements or the element is shared; `end<=start` => -EINVAL; range must lie inside the message (`filter.c:2661-2776`). Return only 0/-errno; the program then re-derives `msg->data/data_end` with the verifier's pointer invalidation (doc `include/uapi/linux/bpf.h:3323-3352`).
- `bpf_msg_push_data(start,len)`: inserts `len` bytes at `start` by allocating a fresh page (not `__GFP_ZERO`; `alloc_pages(__GFP_NOWARN|GFP_ATOMIC|__GFP_COMP,…)`), may fall back to copying the whole element when sg slots are exhausted (`filter.c:2788-2925`). `bpf_msg_pop_data(start,len)` removes bytes (`:2969-`). So variable-length header *insertion* and *removal* inside a single sk_msg are possible in principle. INFERENCE for "header rewrite of variable length": push/pop + store via `msg->data` pointer after pull_data; capped by MAX_MSG_FRAGS = MAX_SKB_FRAGS (`include/linux/skmsg.h:16`), and push copies/allocs with GFP_ATOMIC.
- `bpf_msg_apply_bytes(n)`: verdict applies to the next n bytes, across multiple sendmsg calls; `bpf_msg_cork_bytes(n)`: don't run the program until n bytes accumulated (`filter.c:2619-2637`; doc `bpf.h:3271-3321`). Both just set `msg->apply_bytes/cork_bytes`; `tcp_bpf_send_verdict` converts them into psock-persistent counters (`tcp_bpf.c:404-515`). This is the in-kernel mechanism by which a *byte-count framing* (Content-Length) can be followed across sendmsg calls. FACT mechanism; INFERENCE that chunked framing would need the program to re-run at each chunk-size line, which apply_bytes can only do by setting apply to the chunk length and re-running (the program is re-run when apply_bytes is exhausted — `tcp_bpf.c:453-504`, `psock->eval = __SK_NONE`).

### F3. kTLS + sockmap on one socket (FACT, with order restriction)
- **Order matters**: `sk_psock_init` refuses a socket that already has a ULP: `if (sk_is_inet(sk) && inet_csk_has_ulp(sk)) { psock = ERR_PTR(-EINVAL); …}` (`net/core/skmsg.c:756-759`). Selftest `test_sockmap_ktls_update_fails_when_sock_has_ulp` asserts that a sockmap update on a socket with `TCP_ULP "tls"` fails (`tools/testing/selftests/bpf/prog_tests/sockmap_ktls.c:64-118`). The supported sequence is: insert socket into sockmap/sockhash first, then install kTLS (the cork/push/pop/no-buf selftests do exactly this: `bpf_map_update_elem(map_fd,&one,&c)` then `init_ktls_pairs(c,p)`, `sockmap_ktls.c:189-193`). `tls_update` (`net/tls/tls_main.c:1085`, registered `:1234`) is the ULP hook that keeps the psock proto consistent. FACT.
- **TX with sk_msg on a kTLS socket**: the verdict runs on *plaintext* before encryption: `bpf_exec_tx_verdict` calls `sk_psock_msg_verdict(sk, psock, msg)` on the open record's plaintext sg and handles PASS / REDIRECT / DROP, `bpf_msg_pop_data` shrink compensation, cork (`net/tls/tls_sw.c:853-983`). FACT. Selftests cover cork, push, pop and no-buf on kTLS TX (`sockmap_ktls.c:163-403`).
- **RX with sk_skb on a kTLS socket**: strparser is NOT used for the BPF parser; `sk_psock_strp_data_ready` delegates to the saved handler when `tls_sw_has_ctx_rx(sk)` (`skmsg.c:1161-1179`). Instead `tls_sw_recvmsg` runs the **stream_verdict program per decrypted TLS record** after decryption: `bpf_strp_enabled = sk_psock_strp_enabled(psock)` (`tls_sw.c:2075`), `sk_psock_tls_strp_read(psock, skb)` (`tls_sw.c:2188-2198`, `skmsg.c:1009-1028`); verdict REDIRECT queues the plaintext skb to another psock (`skmsg.c:995-1007`). **It runs inside `recvmsg()`**: a process must call recv on the kTLS socket to pump it. `tls_sw_read_sock` returns -EINVAL when a psock is attached (`tls_sw.c:2354-2358`), so the kernel-side `read_sock` pump is unavailable for psock'd kTLS RX sockets. FACT. INFERENCE: a process-less sockmap proxy over kTLS RX is not supported by this code; a userspace thread blocked in recv is required.
- Zero-copy RX is disabled when a BPF stream parser/verdict is enabled: `zc_capable = !bpf_strp_enabled && …` (`tls_sw.c:2096`); async decrypt disabled too (`:2130-2133`).
- BPF-on-TLS caveat from the sk_skb helpers: the verdict sees one TLS record (<= 16 KiB plaintext) as a skb, not a TCP segment and not an HTTP message. An HTTP head spanning two records is seen as two verdict invocations with no cross-invocation buffer (UNKNOWN whether `skb_load_bytes` across records is possible: no, per-skb only — INFERENCE).

### F4. KeyUpdate (FACT, v7.0)
- TLS 1.3 KeyUpdate is supported on both directions; RX pauses on receipt: `tls_check_pending_rekey` sets `key_update_pending` when a handshake record of type KEYUPDATE is decrypted (`tls_sw.c:1782-1810`); `tls_rx_rec_wait` returns `-EKEYEXPIRED` until userspace supplies the new TLS_RX key (`tls_sw.c:1369-1371`); `tls_sk_poll` masks EPOLLIN while pending (`tls_main.c:423-427`). Docs: `Documentation/networking/tls.rst:205-229` ("There is no pausing on the transmit side"). Stats `TlsRxRekeyReceived` etc. (`tls_proc.c:25-29`).
- Consequence (INFERENCE): a connection that must survive peer KeyUpdate needs a userspace participant that sees EKEYEXPIRED, derives the next traffic secret (it holds the TLS stack state) and re-installs TLS_RX. A purely in-kernel path cannot handle KeyUpdate; it can only reject/close. `splice_read` and `read_sock` return/propagate the same wait error via `tls_rx_rec_wait` (`tls_sw.c:2290`, `:2377`).

### F5. splice with kTLS (FACT)
- RX: `tls_sw_splice_read` decrypts one record (`tls_rx_one_record`, decrypting in the received skb, no copy to user) and `skb_splice_bits` moves it to the pipe; **non-DATA records (alerts, handshake incl. KeyUpdate, close_notify) -> `-EINVAL` and the record is requeued** (`tls_sw.c:2267-2336`; control check `:2310-2314`). It passes `NULL` psock to `tls_rx_rec_wait` and does not call the BPF verdict.
- TX: `tls_sw_sendmsg` accepts `MSG_SPLICE_PAGES` (`tls_sw.c:1278-1296`); `tls_sw_sendmsg_splice` references pipe pages into the plaintext sg (`:1119-1135`), encryption happens into a separate ciphertext buffer; `tls_sw_splice_eof` flushes an open record when splice ends without SPLICE_F_MORE (`:1301-`). ops tables wire `splice_read`/`splice_eof` for TLS_SW (`tls_main.c:943-951, 1013`). Net effect (INFERENCE): body bytes cross user/kernel boundary zero times; kernel does decrypt in place on RX, copy-less reference on TX plus an AES-GCM pass into a new ciphertext buffer.
- Boundary hazard (FACT/INFERENCE): the pipe carries decrypted bytes of **one record at a time**; splice(2) knows nothing about HTTP message boundaries, so userspace must compute the byte count (Content-Length remaining) and splice exactly that many, then resume reading heads with recv on the same socket. A record that straddles the body/next-head boundary: `tls_sw_splice_read` returns `min(full_len, len)` and requeues the remainder (`:2316-2325`), so partial-record splice is supported.

### F6. In-kernel handshake (FACT)
- `Documentation/networking/tls-handshake.rst:28-31`: "As of this writing, there is no TLS handshake implementation in the Linux kernel"; the kernel delegates via netlink to a userspace handshake agent (`tlshd`). `net/handshake/tlshd.c` implements request/accept/done and constructs the CMD_ACCEPT message with peer identity/certificate fields (`tlshd.c:189-265`, `HANDSHAKE_HANDLER_CLASS_TLSHD` `:268`). Kernel consumers (NFS, NVMe/TCP) use it; it is a kernel-consumer-initiated API (`tls_client_hello_anon`, `tlshd.c:286`), not something a userspace gateway needs. No in-kernel TLS 1.3 handshake exists in v7.0.

### F7. Verifier limits (FACT)
- `BPF_COMPLEXITY_LIMIT_INSNS 1000000` (`include/linux/bpf.h:2259`); `MAX_BPF_STACK 512` (`include/linux/filter.h:99`); `MAX_CALL_FRAMES 8` (`include/linux/bpf_verifier.h:324`); `BPF_MAX_LOOPS = 8*1024*1024` (`bpf.h:2266`); `bpf_loop` (`kernel/bpf/bpf_iter.c:727-753`) and open-coded numeric iterators `bpf_iter_num_new/next` (`:770,801`) exist, so header scanning is not forced into unrolled loops. Instruction count limit is not the binding constraint for a CRLF scan; the binding constraints are bytes visible per invocation (one skb / one sk_msg linear range after pull_data), per-socket state storage, and the lack of any blocking/async facility.

### F8. Framing and body mechanics for a pure-BPF path (FACT mechanism, INFERENCE conclusions)
- sk_skb + strparser: the stream_parser program returns the message length (0 = need more header bytes, <0 = error); strparser accumulates, enforces `max_msg_size` and `len` must reach into the *new* skb (`net/strparser/strparser.c:210-250`), and arms a per-message timer (`:219`, `:424-430`). This frames Content-Length messages (head parsed by the BPF parser, total = head_len + CL) but cannot frame chunked bodies or "read until close" responses (RFC 9112 §6.3: length from chunk decoding or connection close) — INFERENCE. Not usable on TLS ciphertext: sockmap+kTLS RX bypasses strparser entirely (F3).
- sk_msg (sender side): `cork_bytes` holds data until N bytes so a head can be parsed whole (`tcp_bpf.c:425-439`); `apply_bytes` gives one verdict to N following bytes, re-running the program after (`:441-514`). A Content-Length body can thus be "applied" with REDIRECT without per-chunk program runs. FACT mechanism. A **DROP** verdict returns `-EACCES` to the *sender* (`:494-499`) — it cannot send a reply to anyone.
- Per-connection state across program runs: sk_msg has `sk_storage_get/delete` (`filter.c:8623-8626`); sk_skb's explicit helper switch lists none (`:8638-8676`) — whether it is reachable via `bpf_sk_base_func_proto` was not read (UNK; map keyed by `bpf_get_socket_cookie` is available, `:8653`).
- Per-request keep-alive tracking: the apply_bytes counter lives in the psock (`psock->apply_bytes`, `tcp_bpf.c:442-459`) so it survives across sendmsg calls — this is the one genuine in-kernel mechanism for "N bytes of body, then re-parse". It does not exist for sk_skb (strparser is length-delimited per message instead).
- RFC 9112 §9.3: persistent connections are the HTTP/1.1 default; §9.3.2 pipelining requires in-order responses; §6.3 requires rejecting/closing on conflicting CL+TE. A pure BPF path must implement these smuggling defences itself (INFERENCE; XLB sidesteps by holding one outstanding request).

### F9. Synthesizing a response from BPF (FACT absence + INFERENCE workaround)
- No helper in `sk_msg_func_proto` / `sk_skb_func_proto` originates a TCP send on a chosen socket (`filter.c:8604-8676`). `sk_psock_verdict_apply` REDIRECT without `BPF_F_INGRESS` calls `skb_send_sock` on the target psock (`skmsg.c:646-655`), so a program can send an *existing skb* out of the client socket's egress. INFERENCE (unprobed): rewrite the request skb in place into a fixed 502/503/404 and redirect it to the *same* socket's egress; sizes limited by `skb_change_tail` / `sk_skb_adjust_room` (<= 0xfff growth). Kernel 7.3 added `bpf_ksock` kfuncs but web sources describe them as UDP-only (kernelnewbies Linux_7.3; not read from source). On a TLS connection the synthesized bytes would need to pass through kTLS TX, which in v7.2 cannot be reached by BPF at all.

### F10. cgroup/connect4 selection and the non-TLS legs (FACT from existing repo design)
Not re-read here; backend selection by `cgroup/connect4` is orthogonal to sockmap: `sock_map_sk_is_suitable`/`sock_map_sk_state_allowed` accept TCP sockets in ESTABLISHED/LISTEN (`net/core/sock_map.c:536-549`) but a socket joining sockmap must not already carry a ULP (`skmsg.c:756-759`). INFERENCE: if the backend leg is an mTLS kTLS socket, it can never be a sockmap member in v7.2.

### F11. Kernel-module route (INFERENCE grounded in FACT API surface)
- APIs exist: `sock_create_kern`, `kernel_accept`, `kernel_recvmsg`, `kernel_sendmsg` (`net/socket.c:1679, 3584, 1120, 785`); TLS ULP is installable on a kernel socket via `tcp_set_ulp`-path `setsockopt(TCP_ULP,"tls")` and `TLS_TX/TLS_RX` (`net/tls/tls_main.c:53,635-740,1231`); `sk_data_ready` upcalls; `net/handshake` lets a kernel consumer ask a *userspace* agent to do the handshake (`tlshd.c:189-286`). So a module could implement accept → handshake via tlshd → kTLS → HTTP state machine entirely with in-tree APIs, but it still has a userspace dependency for the handshake and must carry its own HTTP/1.1 parser, SNI/ALPN extraction (tlshd only returns the outcome), mTLS peer SAN verification, KeyUpdate and timers.
- Rust-for-Linux: `rust/kernel/net.rs` in v7.0 contains only `pub mod phy` (PHY drivers) (`rust/kernel/net.rs:3-6`); no socket, TCP or TLS abstractions. Kernelnewbies Linux_7.3 lists "Rust netlink support" (web; not read from source). So a Rust module would need hand-written bindings to socket APIs — INFERENCE: high cost.
- Policy fit (INFERENCE from repo rules, not a design decision): out-of-tree C modules conflict with the immutable pinned appliance (module signing/ABI per kernel), and security-exposure of a parser on the unauthenticated public edge in ring 0 is the failure mode kHTTPd was removed for.
- Prior art:
  - kHTTPd: in mainline 2.4, handled only static files and passed everything else to userspace; pulled from 2.4.19-pre because of instability — LKML May 2002: "khttpd has been removed from the main kernel" (Hellwig patch); Kegel: "it'd time for khttpd to become a standalone patch again" ([LKML thread](https://lkml.iu.edu/hypermail/linux/kernel/0205.0/1094.html)).
  - TUX (Ingo Molnar, Red Hat): never mainlined; made unnecessary by NPTL/epoll userspace servers (Wikipedia summary; academic analysis: CITI TR 00-8 "An analysis of the TUX web server", Univ. of Michigan, and USENIX 2001 "Kernel-mode approaches", Joubert et al.). Not read in full here; labelled secondary.
  - XLB (Wang et al., PKU, arXiv:2602.09473, Feb 2026): in-kernel L7 LB for HTTP/1.1 and HTTP/2 on Linux 5.10 via *new* hooks in modified socket types + helpers wrapping strcmp/strstr (non-constant-bound loops "cannot be verified") + `bpf_msg_push_data`; ~3000 kernel LOC; HTTP/1.1 limited to one outstanding request per backend connection; **TLS not supported in-kernel**; no mention of chunked encoding or header size limits.
  - Cilium (checked in `/Users/marcus/git/cilium/cilium`): L7 is Envoy as a separate process (`Documentation/security/network/proxy/envoy.rst:13-38`); traffic is steered to it with `sk_assign` at tc (`bpf/lib/proxy.h:13-146`); no sockmap/sk_msg program exists in the Cilium `bpf/` tree (only vendored UAPI header copies in `bpf/include/linux/bpf.h`) — FACT for this checkout. Cloudflare's 2019 SOCKMAP post says Cilium used it for L7 policy (historical, web).
  - Envoy "sockmap socket interface": experimental, same-host only, IPv4 only, accelerates TCP between local sockets with sock_ops+sk_msg; docs do not mention TLS ([envoyproxy.io](https://www.envoyproxy.io/docs/envoy/latest/configuration/other_features/sockmap)).
  - Cloudflare: sockmap splicing measured slowest of splice/read-write/io_submit and found a 64 ms stall bug on 4.14 (2019, [blog](https://blog.cloudflare.com/sockmap-tcp-splicing-of-the-future)); `sk_lookup`/tubular is L4 socket steering, not L7.

## Verdict detail on "pure sk_msg parser costs keep-alive or header policy"
- **Keep-alive**: REFUTED as an in-principle statement on a plaintext socket (apply_bytes/cork_bytes keep per-message state across calls; XLB persists connections). PARTLY CONFIRMED in this product's context: with TLS on both legs, keep-alive per-request tracking by BPF requires plaintext access which exists only on v7.0 kTLS (TX verdict on sender's plaintext, RX verdict per record inside recvmsg), and not on v7.2.
- **Header policy**: PARTLY. Insert/remove bytes: possible via push/pop (FACT helpers). Connection-nominated header removal, Forwarded authoring from authenticated peer facts, strict smuggling rejection and trailer consumption exceed what bounded, stateless-per-segment programs do comfortably (INFERENCE). XLB had to add custom helpers/hooks to parse at all.
- **Overall**: the original wording located the cost in the wrong place. The binding cost is TLS: no handshake in kernel/BPF, and sockmap+kTLS removed in v7.2.

## Compatibility findings for the hybrid (kTLS + splice + cgroup/connect4)
1. kTLS RX/TX with `splice(2)` has no psock dependency: `tls_sw_splice_read` passes `NULL` psock (`tls_sw.c:2290`), TX accepts `MSG_SPLICE_PAGES` (`:1283-1286`). Hence the hybrid is unaffected by the 7.2 sockmap removal. FACT.
2. Zero-copy meaning: RX decrypts in place in the received skb then `skb_splice_bits` refs its pages into the pipe; TX refs pipe pages into the plaintext sg and AEAD-encrypts into a separate buffer. Bodies are never copied to userspace; they *are* read+written once by the kernel crypto path (FACT code, INFERENCE summary). Whether hardware or async crypto changes this: UNK.
3. A record is the unit: splice returns at most one record per call (`min(rxm->full_len, len)`, `:2316`), i.e. up to 16 KiB; many syscalls for large bodies; a body/next-head boundary inside a record requires splicing exactly the body remainder and leaving the rest queued (supported: `:2321-2325`). INFERENCE.
4. Non-DATA records (alert, handshake/KeyUpdate, close_notify) surface as `-EINVAL` from splice (`:2310-2314`), and `recvmsg` returns the record with control type (tls.rst:`recv will never return data from mixed types`). The relay loop must fall back to `recvmsg` with a cmsg buffer, then handle KeyUpdate (EKEYEXPIRED until new RX key). INFERENCE.
5. KeyUpdate in 7.0 and 7.2 is symmetrical: kernel applies no policy; userspace must derive the next secret (needs retained handshake secrets in the userspace TLS library) — which means the library must support exporting/deriving traffic secrets; rustls `dangerous_extract_secrets` / `KernelConnection`-style APIs are outside this research (UNK).
6. Header-only wake: `tls_sk_poll` clears EPOLLIN while a rekey is pending (`tls_main.c:423-427`). Consequence for epoll-driven relays: a connection with pending KeyUpdate looks silent. FACT; INFERENCE on importance.

## Open questions only a real-kernel spike can settle (probe names)
Each probe: run on Linux 7.0 (pinned) and, separately, the newest available; record `uname -r`; per `.claude/rules/spike.md`, in `spike-scratch/`, aya-rs, no C.
1. **P-splice-record-boundary**: two kTLS sockets (loopback), HTTP request head + CL body + pipelined next head in one stream; relay with `splice` exactly CL bytes then `recv` the next head. Measure: does `tls_sw_splice_read` ever return bytes beyond the requested length or leave a partial record in a state `recv` can resume (`tls_sw.c:2316-2325`)? Expect: correct. Falsifies the boundary hazard if not.
2. **P-keyupdate-mid-splice**: peer sends KeyUpdate while the relay is in splice; observe -EINVAL vs -EKEYEXPIRED sequence, poll behaviour, and whether TX can continue during RX pause.
3. **P-splice-throughput-backpressure**: 1 GiB body through client-kTLS -> pipe -> backend-kTLS with a slow backend; record pipe occupancy bound, CPU, copy counts (perf `tcp_sendmsg_locked`/crypto), to substantiate "bounded backpressure" (ADR-0239).
4. **P-sockmap-ktls-reject**: on 7.0, 7.0.y latest, and 7.2: (a) sockmap then `TLS_TX`; (b) `TLS_TX` then sockmap update; (c) record errno. Confirms whether the removal reached the pinned kernel line; decides whether any 7.0-only BPF-on-plaintext design is even stable.
5. **P-skmsg-header-edit**: on a plaintext sockmap socket, sk_msg program using cork/pull/pop/push to delete a variable-length header and insert `Via`; test head split across 1-byte sendmsg calls, 16 KiB heads, `MAX_MSG_FRAGS` exhaustion (`filter.c:2825`), GFP_ATOMIC failure behaviour. Quantifies feasibility for 0237 only if a plaintext leg is ever relevant.
6. **P-bpf-synth-response**: sk_skb stream_verdict that rewrites a request skb into a 503 and redirects it to its own egress; check TCP seq/ACK accounting, tcp_eat_skb, partial writes. Expect fragile (INFERENCE).
7. **P-connect4-selection-then-splice**: cgroup/connect4 picks backend for a userspace `connect()`; verify one attempt, error taxonomy for 502 (ECONNREFUSED vs timeout) — already within the candidate design.
8. **P-sk_skb-sk_storage**: load an sk_skb program calling `bpf_sk_storage_get` on 7.0 and 7.2 to settle UNK in F8.
9. **P-sockmap-redirect-stall**: Cloudflare 2019 64 ms stall reproducer on 7.0 to check if stalls persist (only relevant if sockmap data-plane is considered at all).

## v7.3 re-check (2026-11-02)

Source: tag `v7.3` (Makefile `VERSION = 7`, `PATCHLEVEL = 3`, `SUBLEVEL = 0`) read via `git show v7.3:<path>` from a depth-1 bare repo; v7.0 comparison via `git show v7.0:<path>` in `wellington-v2/vendors/linux`. All cites below are `path:line @ v7.3` unless stated. Method: whole-file diffs v7.0 -> v7.3 of the TLS, sockmap and handshake files, plus targeted greps. Diff sizes (lines of diff output): `tls_sw.c` 664, `tls_main.c` 177, `skmsg.c` 64, `sock_map.c` 105, `tcp_bpf.c` 61, `tlshd.c` 11, `net/Kconfig` 6, `net/tls/Kconfig` 13.

**Result in one line:** every conclusion in this document holds at v7.3; the sockmap+kTLS removal is present and slightly more complete than in the v7.2 tree, and no TLS/HTTP kfuncs or in-kernel handshake exist.

### 1. TLS + sockmap rejection (FACT: present, not reverted)
- `do_tls_setsockopt_conf` returns `-EINVAL` when `sk_psock(sk)` is set: comment "TLS and sockmap are mutually exclusive..." at `net/tls/tls_main.c:636-645 @ v7.3`. Absent in v7.0 (added block between v7.0 `:646` and v7.3 `:635`).
- Reverse order is also refused: `sk_psock_init` still returns `-EINVAL` if `inet_csk_has_ulp(sk)` (`net/core/skmsg.c:757-760 @ v7.3`, unchanged vs v7.0).
- `bpf_exec_tx_verdict` is now only `tls_push_record` plus error cleanup (`net/tls/tls_sw.c:701-713 @ v7.3`); the v7.0 `sk_psock_msg_verdict` / cork / redirect logic (v7.0 `tls_sw.c:853-983`) is gone. Same as the v7.2 tree.
- RX: `sk_psock_tls_strp_read` and `sk_psock_tls_verdict_apply` are deleted from `net/core/skmsg.c` (v7.0 `:995-1029`); `sk_psock_strp_data_ready` no longer has the `tls_sw_has_ctx_rx` branch (v7.3 `skmsg.c:1140-1142`); `tls_rx_rec_wait` no longer takes a psock (v7.3 `tls_sw.c` ~`:1095`); `tls_sk_poll` no longer consults a psock queue (`tls_main.c:417-423 @ v7.3`).
- Leftovers (INFERENCE: harmless, dead): `tls_sw_read_sock` still takes `sk_psock_get` and returns `-EINVAL` if a psock exists (`tls_sw.c:2089-2092 @ v7.3`); `tcp_bpf_push` still computes `has_tx_ulp = tls_sw_has_ctx_tx(sk)` (`net/ipv4/tcp_bpf.c:113-116 @ v7.3`, unchanged vs v7.0); a comment at `skmsg.c:736` still mentions TLS unhash.
- Additional v7.3 changes: `net/tls/Kconfig` no longer `select STREAM_PARSER` and `TLS_TOE` is removed (`tls_main.c` no longer includes `net/tls_toe.h`). Not relevant to the design.
- `sock_map.c` v7.0 -> v7.3 changes are hardening only (refcount, `READ_ONCE(sk_state)`, `sock_map_prog_attach_check` rejecting a stream parser that `changes_pkt_data`, close/unhash retry loops, UDP state check). No TLS-related change in `sock_map.c` (grep for `ulp|tls` returns nothing).
- Status of the earlier open items: "removal reached the pinned kernel line?" - the pinned kernel is v7.0, which does NOT have the rejection (`tls_main.c @ v7.0` has no psock check; v7.0 `tls_sw.c:853-983` still has the verdict path). Whether 7.0.y stable backports it: UNKNOWN (not determinable from tags read). Selftest `sockmap_ktls.c @ v7.3` now contains `test_sockmap_ktls_enable_fails_when_in_sockmap` (`:119`) and `..._update_fails_when_sock_has_ulp` (`:63`) - i.e. the tests assert rejection both ways.

### 2. splice on kTLS (FACT: unchanged semantics)
- `tls_sw_splice_read` (`net/tls/tls_sw.c:1999-2071 @ v7.3`): decrypts at most one record per call (`tls_rx_one_record`, `:2024-2030`), rejects non-DATA with `-EINVAL` and requeues (`:2046-2050`, `splice_requeue`), splices `min(full_len, len)` and requeues the remainder (`:2052-2060`). Same logic as v7.0 (`:2267-2336`); only line numbers moved. It still passes no psock (`tls_rx_rec_wait(sk, nonblock, true, false)`).
- TX: `tls_sw_sendmsg` accepts `MSG_SPLICE_PAGES` (`:1014`), uses `tls_sw_sendmsg_splice` (`:735`, call site `:857-859`); `tls_sw_splice_eof` at `:1031`. Ops tables still wire `splice_read` / `splice_eof` (`tls_main.c:942, 945, 950, 1009 @ v7.3`). Unchanged vs v7.0.
- Consequence: the hybrid (userspace heads + kTLS + splice) design is unaffected by v7.3 (FACT for the mechanism; INFERENCE for the design conclusion).

### 3. TLS 1.3 KeyUpdate / rekey (FACT: present in v7.0 and v7.3, unchanged)
- Re-install via `setsockopt(TLS_TX/TLS_RX)` on an existing TLS socket is the `update` path in `do_tls_setsockopt_conf` (`tls_main.c:670, 682, 725, 745, 762 @ v7.3`; v7.0 `:671, 726`). There are no separate `TLS_TX_REKEY` / `TLS_RX_REKEY` option names; rekey is the same options with `update = true` and `LINUX_MIB_TLS{TX,RX}REKEY{OK,ERROR}` counters.
