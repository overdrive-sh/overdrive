# Test scenarios — `metal-test-placement-attribute` (DISTILL)

Specification text only: nothing here is parsed or executed (`.claude/rules/testing.md`, "No `.feature` files anywhere"). Every scenario is a Rust test in the owning crate, with a complete executable body. A test marked **pending** carries `#[ignore = "pending DELIVER: <slice>"]`, where `<slice>` is the slice file stem under `../slices/`; the crafter removes the marker, records a semantic RED and builds the behaviour. A test marked **active** passes today and keeps an implemented behaviour true.

Contract Shape follows the design's definitions: **pure-function** (value in, value out), **bounded-change** (a declared mutation set over a named universe), **unbounded-preservation** (reads, never mutates). The universe-bound state-delta assertion of the generic nWave skill has no Rust port in this project; the equivalent here is the observation-level oracle each scenario names (whole `OwnerObservation` snapshots, the full output of the checker, a marker file, the timing lines).

Tags: `@ws` walking skeleton (the promoted slice 01, already delivered), `@error` error or fault path, `@boundary`, `@property`, `@real-io` real kernel or real subprocess, `@in-memory` no I/O, `@driving_port`, `@conformance`.

What the replay does and does not check: it compares the projected state after every step. The driver keeps no record of the effects `handle` returns (a driver record of replies would make the oracle the driver's own bookkeeping), so a reply is never observed by the replay. The two invariants that are about replies, `I_DELIVER_ONLY_ATTACHED` and `EveryClientTerminates`, are therefore discharged by the Section A oracle properties (`seeded_event_schedules_keep_the_owner_invariants`, `every_attached_client_that_stays_is_answered_once_when_the_environment_answers_everything`), not by replay.

Projection: `guest` (NoGuest 0, Booting 1, Ready 2), `gen`, `inflight` (0 when none), `queue`, `owners` (1 unless `stopped`), each through `OwnerObservation`. Model-only and not projected: `lock`, `bad`, `execgen`, `execs`, `faults`, `idleLoss`, `conf_step`, the per-client phases. The `conf_step` pick is the `nondet` source. `ExecFinished{pass}` and `ExecBound` read the in-flight client from `observe()` to build the call, as the action map pins.

**Conformance exemption (user decision N-4, 2026-11-14): one row per invariant, each naming its Tier-3 scenario.**

| Invariant | Why replay does not (or does not alone) discharge it | Discharged by |
|---|---|---|
| `I_OWNER_UNIQUE` | the election lock is the kernel's; the instance starts with the owner present | `eight_simultaneous_first_arrivals_elect_exactly_one_owner` |
| `I_NO_ORPHAN` | an owner crash leaves no process to receive an event | `killing_the_owner_during_a_guest_exec_leaves_no_vmm` |
| `I_SERIAL` | (not exempt) the projected `inflight` and `queue` are compared after every replayed step | Section B replay and Section A property |
| `I_NO_REUSE` | (not exempt) the projected `guest` and `gen` are compared after every replayed step | Section B replay, Section A property, and `a_client_killed_while_its_test_runs_taints_the_guest_for_the_next_client` |
| `I_DETACH_NO_CANCEL` | (not exempt) the projected `inflight` is compared after every replayed step | Section B replay and Section A example |
| `I_DELIVER_ONLY_ATTACHED` | replies are effects, not projected state; the driver discards effects and keeps no bookkeeping, so replay never observes a reply | Section A `seeded_event_schedules_keep_the_owner_invariants` (no reply to a client that went away, none twice) |
| `I_IDLE_NO_LOSS` | (not exempt) the projected `owners` (stopped) is compared after every replayed step | Section B replay and Section A example |
| `EveryClientTerminates` | a liveness property about replies; replies are effects the driver discards, so replay never observes one | Section A `every_attached_client_that_stays_is_answered_once_when_the_environment_answers_everything` |

### F. Metal scenarios (`overdrive-testing`, `tests/integration/`; layer 3, real guests, gated `integration-tests` + `kvm-tests`)

Driving port: a fixture test of this binary run as a child process the way nextest runs it (`--exact <name>`), on a Metal run; oracle: the `OVERDRIVE_GUEST_KIT_TIMING` lines, exit status and output, a host marker file, and the owner binary's processes in the run's own cgroup. Every driver observes the host from outside any guest, so it tests the Metal runner's own placement machinery and is placed `#[overdrive_test(native_launcher)]` through the attribute when it is activated (user ruling D-10, confirmed by the user, 2026-11-14); no table entry exists. The form lands in the lane-and-launcher slice, so the drivers activate there or later.

**RED for this section is carried and re-taken at activation, not taken now.** The scenarios that were active before DISTILL's correction ran with transitional table entries; those entries are gone and every fixture they drive is pending, so no RED run of this section is taken in the current run. `red-classification.md` counts the ten non-guard tests of this section as "RED carried" (the first assertion reached in the earlier DISTILL run, with fixtures active) and keeps them apart from the 59 "RED now". Four scenarios assert behaviour the per-test guest of the delivered skeleton already has ("kept true") and are regression guards with no semantic RED: `a_guest_placed_test_never_runs_its_body_on_the_host_on_a_metal_run`, `the_boot_time_of_a_guest_per_test_is_recorded_in_the_run_output`, `guest_placed_tests_outside_a_shared_module_boot_one_guest_each` and `a_guest_placed_test_with_an_invalid_run_id_fails_naming_its_group_and_never_runs_on_the_host`. The others (the shared-guest and owner scenarios, and the in-place scenario) go RED at activation against the scaffold. The whole binary joins `host-kernel-shared` in `.config/nextest.toml`.

The exec bound's duration and the idle period's duration (read only by the owner shell; no test-only override); the client's mapping of `boot_failed`, `guest_lost` and `exec_bound` to `GuestExecution` (a total `match`; the wire encoding is the crafter's; the owner side is covered by sections A and B); a failing body on the per-test path (US-01 AC b is narrowed to the shared path, covered by `one_failing_test_in_a_shared_module_does_not_hide_the_others` and `a_failed_shared_test_is_reported_with_its_status_and_its_guest_is_replaced`); US-PLACE-04's missing-artifact scenarios (dropped; the registry names and the existing `guest_suite` staging tests remain); the real `cargo nextest list` path of `placement-lint` (covered by its own CI and pre-push step); migration parity (a DELIVER procedure). ## Placement of these tests

DISTILL adds no `infra/metal/test-placement.json` entry. A pending test never reaches the Metal wrapper on an ordinary run, so it needs no placement. **Activating a test includes giving it its attribute placement** (`#[overdrive_test(...)]`, `placement!`, `overdrive_test_default!`) in the slice that delivers that form; a test whose form does not exist yet stays pending until then. `native-launcher` is never used for a product test.

Design gap D-10, resolved by the user's ruling (user, 2026-11-14), which also confirms the extension to the three `shared_guest_scenarios` scenarios and the lane missing-fixture scenario (user, 2026-11-14): tests that must observe the host from outside any guest to prove the placement machinery are tests of the Metal runner itself and are placed `#[overdrive_test(native_launcher)]` through the attribute once that form lands (lane-and-launcher slice), never by a table entry. They are the four scenarios named below, the scenarios of `shared_owner_lifetime`, the three of `shared_guest_scenarios` and `a_lane_test_naming_a_missing_fixture_fails_naming_the_fixture_and_the_test`. The reasoning behind the ruling: the four scenarios that were active (`guest_placed_tests_outside_a_shared_module_boot_one_guest_each`, `the_boot_time_of_a_guest_per_test_is_recorded_in_the_run_output`, `a_guest_placed_test_never_runs_its_body_on_the_host_on_a_metal_run`, `a_guest_placed_test_with_an_invalid_run_id_fails_naming_its_group_and_never_runs_on_the_host`) run a guest-placed fixture as a child process and observe the host (a host marker file, the guest kit's own boot of a guest). No guest group can run them: the guest kit, the guest artifacts and the run's namespaces exist only on the host, and inside a guest `inside_guest()` holds, so the fixture would run its body in place and never take the host path. They are tests of the placement machinery, which is Metal-runner tooling, and the rule allows `native-launcher` only for tests of the runner itself. The owner scenarios have the same property and take the same placement.
