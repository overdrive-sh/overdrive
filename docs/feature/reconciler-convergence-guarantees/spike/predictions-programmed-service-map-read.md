# V-6 predictions (written before the first run)

Written 2026-11-17, before any probe executed. Per `.claude/rules/debugging.md` § 4.

**H1 (K-1, K-2, exactness).** Hypothesis: a root process can look up the `HASH_OF_MAPS` `SERVICE_MAP` slot and get the inner map's id, open it with `BPF_MAP_GET_FD_BY_ID`, scan the inner `ARRAY`, and resolve the distinct `BackendId`s in `BACKEND_MAP`, reproducing the programmed `(addr, weight, healthy)` set exactly for 1, 16 and 256 backends. Predicted: exact match in every case, including weight 0, weight 65535 and unhealthy backends (the inner array holds every backend; health lives only in `BACKEND_MAP`). Falsification: any mismatch, an `EPERM`/`EINVAL` from either syscall, or an inner map that is not a 16,381-slot u32 array.

**H2 (consistency).** Hypothesis: the inner map is immutable after the outer swap, but `BACKEND_MAP` is updated in place before the swap and swept after it, so a read with no guard can mix two states, and a read that excludes the whole `update_service` body cannot. Predicted: unguarded reads against a writer that flips between two sets sharing endpoints with different weights show a non-zero count of torn reads (neither set) and some ENOENT; reads under a lock the writer holds for its whole body show zero. Falsification: zero torn reads unguarded (the window would then be too small to matter and the guard unnecessary), or any torn read guarded.

**H3 (restart).** Hypothesis: a fresh `EbpfDataplane` over the same pin directory unlinks and recreates `SERVICE_MAP` and loads a new unpinned `BACKEND_MAP`, so every frontend reads empty. A reboot is the same by construction (bpffs and all maps are in kernel memory). Falsification: any non-empty read from the fresh instance.

**H4 (cost).** Hypothesis: the read is dominated by scanning the 16,381-slot inner array, not by backend count or by how many frontends are programmed. Predicted: single lookups ~16,381 syscalls, 8 to 25 ms; one batch call ~3 to 10 ms (the kernel's generic array batch still does one `get_next_key` + copy per element, so it saves syscall entry, not per-element work); +about 1 microsecond per distinct backend for the `BACKEND_MAP` lookups (256 backends adds roughly 0.1 to 0.3 ms); per-frontend latency flat from 1 to 1000 programmed frontends (outer lookup is a hash probe). Falsification: batch read above 30 ms, or per-frontend latency growing with frontend count.
