# Step 05-03 DISTILL remediation: guest-listener probe fixtures

## Native shared-board wiring test: setup and guest control session

The assigned `guest_listener_board_wiring` integration test failed before entering its observable board scenario: `tempdir_in(default_staging_root())` received `/tmp/overdrive-vm-fixture` in the disposable `cgroup-default` guest, but that parent did not exist. The exact native Metal rerun reproduced `PathError ... No such file or directory` at `Node::boot` (`.context/step-05-03-wiring-before.log`). `guest-kit-prepare` did not create this per-test parent. The fixture now creates that chosen staging root before `tempdir_in`; it keeps the data directory and rootfs clone on one filesystem. The next native run reached a committed `Running` allocation with a valid GuestListeners descriptor and declared TCP/UDP listeners, so the directory was the actual setup blocker, not a production board error.

The test then exposed a separate, reproducible composition prerequisite. After the completing `LISTEN udp 5353` line, no startup row appeared in 20 seconds. Failure diagnostics read only existing production/port surfaces: the allocation snapshot remained `Running`, the beacon had written no `EXEC`, and `ServerHandle::guest_flow_observation()` showed the leased CID in `Provisioned` with `session: None` (`.context/step-05-03-wiring-owner-diagnostic.log`). In the real `StartAllocation` path, the `Running` row is written first; `activate_guest_network` then loops while the owner reports `ControlSessionPending`; only after activation does the shim call `VmDriver::on_alloc_running` and release `EXEC` (`action_shim/mod.rs:2573-2721`). The test's `SimVmm` sends READY on `SimBeaconIo` but provides no guest-flow control session to the host `GuestFlowAdapter`, which is opaque outside `overdrive-control-plane`. Its successful Running row therefore does **not** establish that the probe runner was registered. Moving the existing test to a host-pure placement would not supply this missing guest control session: `run_server` still composes the host guest-flow owner.

The test now lives as a source-local `integration-tests` module, so it can use the **existing crate-private** `GuestFlowAdapter(SimGuestFlowIo)` port without adding public surface. It still calls the production `run_server(config, adapters)` root over the host bundle; it replaces only driven ports, following `action_shim/guest_activation_acceptance.rs` for `SimGuestFlowIo::queue_connection(ControlOpen { launch })` and `shared_network_test_ports.rs` for source-local dataplane/DNS test adapters (the external `overdrive-sim` implementations belong to a second compiled copy of the control-plane trait). The leased CID and typed launch token come from `ServerHandle::guest_flow_observation()`. After queuing READY on the real `VmDriver`'s `SimBeaconIo`, the fixture queues the guest's control-session preamble on the existing guest-flow seam. It waits for both the committed Running row and the actual `EXEC` beacon reply before sending LISTEN lines. A held control session is long-lived: a trial `SimGuestFlowIo::settled()` wait timed out and was removed; the production `EXEC` reply is the correct activation-completion observation.

The full Service submission, `run_server` composition, undeclared and partial report complements, exact one-Pass-row oracle and time bound remain. The test never touches the board or directly calls `on_alloc_running`; the shared production board still has to carry the driver's LISTEN line to the probe task. The final source-local test passed in the existing `cgroup-default` guest placement (`.context/step-05-03-wiring-source-local-control-session.log`, 1/1). Its placement key moved from the external integration binary to the control-plane lib test binary; no new lane was added. This is the concrete test-composition choice reviewed by the next independent DISTILL reviewer.

## Restart-authority conformance: a whole-workload ServiceLifecycle tick

The exact `QUINT_SEED=0xd18783b` replay failed at step 20, `SLAnnounceTerminal(1)`, after step 19 wrote `StartupRow(3, "pass")`. The driver maps `SLAnnounceTerminal` to a **whole-workload** production `ServiceLifecycle` tick. That tick both adds terminal predecessors to `terminal_announced` (DG-12) and commits `Stable` for the Running attempt 3 whose latest startup row is Pass (B1); the model previously updated only terminal membership. The production projection showed `stable=true` for attempt 3, while the model expected `false` (`.context/step-05-03-restart-seed-before.log`).

The existing model helper now folds the full allocation map for both terminal membership and eligible Stable claims on every `ServiceLifecycle` action. It touches only `ann` and `stable`, preserving each attempt's row, stop stage, claim and author; the targeted action still applies its own approved transition afterward. The next replay reached a different test-support fault: at `SLLivenessStop(2, "row_write")`, the generic one-shot `SimObservationStore` write failure was consumed by an earlier `WriteServiceBackendRow`, then the stop row succeeded. A temporary diagnostic of the returned production actions showed the backend write and hydrator enqueue ahead of `StopAllocation` (`.context/step-05-03-restart-seed-diagnostic.log`); the diagnostic print was removed. To make `row_write` mean the stop's allocation-lifecycle row as the model already states, the Sim observation adapter now has a test-only allocation-lifecycle write-failure queue. The conformance driver uses that scoped script; other observation writes in the same production dispatch remain real, and the existing generic injection semantics remain available. No production observation-store interface or dispatcher behavior changed.

The same seed then passed. All 22 named/random restart-authority conformance bodies passed, with the existing row, stop, Stable, claim and author projections still compared. Formal Quint was re-recorded: 84/84 checks passed; the pulled evidence has 13 input hashes and `verify-evidence` passed. The temporary seed config was restored byte-for-byte and is clean.

## D9 legacy probe-runner controls

Five source-local worker controls failed together before this correction because their liveness-only/mixed fixtures called `ProbeRunner::start_alloc` and immediately expected Liveness runs. D9 starts Liveness at the existing Stable hook. `after_stable` now checks Liveness is absent, retires Startup and calls the existing runner `start_liveness`, matching the `VmDriver::on_alloc_stable` order. The helper is used before the liveness-only run-count, TCP, HTTP and timeout stimuli; the task is allowed to poll before the first injected clock tick. Their dial, response, timeout, run-sequence, threshold and not-sampled assertions are unchanged.

The eight-descriptor control needed a two-period trajectory: D9 forbids Startup and Liveness tasks being live in the same period. Its first period asserts all three Startup and three Readiness targets dial and six rows land. After the Stable hook, the second period asserts the three Readiness and two Liveness targets dial while Startup has retired. The cumulative target set is still all eight, every dial remains `DialPurpose::Probe`, and all eight distinct descriptor rows are `Pass`. The test was renamed to state the reachable chronology; its existing `host-pure` Metal placement key was updated. The five controls were 0/5 before and 5/5 after on Metal (`.context/step-05-03-d9-fixtures-before.log`, `...after2.log`).
