# Step 05-06 DISTILL remediation: real-boot listener observations

## Failure and production lifetime

The step's activated positive Tier-3 test reached a startup `Pass` while its allocation was `Running` and subsequently observed the terminal row. Its sole failure was the final `console_of(&alloc).contains(BOUND_PREFIX)` assertion after that row. `console_of` reopened `/run/overdrive/vm/<alloc>/console.log` by pathname and returned an empty string when the open failed. In the actual VM owner, `run_exit_watcher` calls `cleanup_driver_artifacts` before it sends `ExitEvent`; that cleanup removes the per-allocation `VmRunDir` and its console path. The post-terminal pathname read was therefore outside the artifact's lifetime. It did not show that either listener was unbound or that a report followed `EXIT`.

The same D13 guest change made the production in-guest test lane's beacon receive `LISTEN tcp 8080` ahead of `EXIT` in three real-kernel guest cells. `run_in_guest_cell` accepted only an immediately adjacent `EXIT`, so those cells failed in the fixture's beacon parser even though the new line is an approved guest-to-host report. The four lane fixtures that use this reader are `the_guest_transport_is_configured_before_ready_in_a_real_guest`, `the_reserved_intake_ports_refuse_application_binds_in_a_real_guest`, `the_guest_kits_module_matches_the_running_guest_kernel`, and `the_guest_accept_path_matches_the_sim_in_a_real_guest`; the original sweep identified three of these as failing. The lane still requires `READY` before it sends `EXEC`.

## Bounded fixture correction

The positive Tier-3 test now opens the production console file **while the allocation is Running** and holds that read handle across the terminal event. It reads the still-open inode after the terminal row and checks both exact guest application `bind: bound` lines (`tcp:0.0.0.0:18091` and `udp:0.0.0.0:18092`). This preserves, and makes more specific, the pre-existing workload-bind observation. The existing startup `Pass` while `Running`, no startup `Fail`, guest-listener descriptor, and subsequent terminal ordering assertions are unchanged. The real host board remains unobserved by the test.

The existing `run_in_guest_cell` fixture now parses each beacon frame after `EXEC`. It accepts only a well-formed `BeaconMessage::Listen` before the exact `BeaconMessage::Exit`, preserving one total `CELL_BOUND` deadline and rejecting any malformed line, unexpected `READY`/`EXEC`/`SHUTDOWN`, EOF, or timeout. The cell's `EXIT` status and libtest console-pass check remain unchanged. This adjusts only the fixture to the D13 wire grammar; it adds no product seam or production behavior.

Fixture code changes are limited to `crates/overdrive-control-plane/tests/integration/guest_listener_real_boot.rs` and `crates/overdrive-testing/src/guest_lane.rs`; `crates/overdrive-init/tests/integration/in_guest_lane.rs` has a comment update for the now-accurate beacon sequence. Both activated Tier-3 tests retain their per-test `CONTRACT_SHAPE: bounded-change.` declarations.

## Existing guest-flow-owner Quint conformance gate

The step's fourth failed `overdrive-init` gate was separate from D13 guest listener behavior. The exact `QUINT_SEED=0x9ab8de37`, `QUINT_VERBOSE=2` replay of `quint_fwd_pair_pair_conf_guest` failed on Trace 42, Step 3 `Abort(g)` before the model edit (`.context/step-05-06-fwd-pair-seed-before.log`). The model set `pr(g).closed=true` while its end record was still `queued`; the actual guest owner had `closed=false`. The real driven path is `FwdPairGuestDriver::guest_abort` → `SimGuestOwnerIo::host_control(Abort)` → `GuestFlowOwner::handle_control` → `abort_tcp_pair` → `hold_close_until_end` and `forwarder_abort`. Only after a later `ForwardEnded` does `handle_forward_end` queue the deferred close, and a subsequent `dispatch_next` applies it. This is the already approved guest `TakeEnd(g)` then separate `OwnerClose(g)` ownership in the netns-density-295 feature delta; it is independent of the new PID 1 listen hooks.

The bounded `fwd_pair.qnt` correction leaves host abort behavior intact and stops marking a non-watch guest pair's descriptors closed in the abort step. The forwarder still aborts, queues exactly one end record, sends its existing vsock shutdown and resets the appropriate far end. The guest's descriptor-close fact remains observable after `TakeEnd(g)` and `OwnerClose(g)`; the projection still compares `closed` against the actual owner and Sim socket.

That first correction exposed a separate, pre-existing contradiction at the same seed's watch-mode `GuestAbort(g)` while the guest held an accepted but unattached V_g. The accepted `fwd_pair` T-5 contract explicitly **discards** that action for `pr(g).ph=unattached`, while the actual guest owner closes the known accepted flow with no pair record (`ph=ended`, `byRel=true`, V_g shut). The independently accepted `owner_flows::GuestRecvAbort` also closes a known accepted flow. The seeded conformance driver reads the real owner and Sim socket, so this contradiction cannot be hidden by a test projection or attributed to D13 listener hooks. [The bounded DESIGN adjudication](../design/guest-flow-abort-contract-adjudication.md) invalidates only that older T-5 premise, returns the other feature's precise roadmap scope to `pending`, and approves no replacement semantic rule. The current service-allocation roadmap remains approved.
