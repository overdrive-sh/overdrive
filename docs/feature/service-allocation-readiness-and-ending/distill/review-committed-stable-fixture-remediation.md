## Exact contract and reproduced need

B1 makes an allocation's **committed** `TerminalCondition::Stable` row, hydrated as `ServiceAllocFact.stable_committed`, the authority for `Stable` re-announcement. R2-2 deletes the `ServiceLifecycleView.stable_announced` field and View-only `has_alloc_mid_startup_window()` method, and requires an older CBOR blob carrying the removed key to decode with that key ignored. D12 admits a startup-probed backend only after its **own** committed Stable, subject to the existing readiness rule; R2-1 removes the separate startup terminal veto and its backend-write splice before the stop. D7/D8 startup-stop action and per-new-row retry remain. These are exact approved interface and observable contracts (`feature-delta.md:1293–1298,1833–1841`; S-38 at `:1815`). The D16 greenfield historical-byte waiver does not waive R2-2's explicit CBOR unknown-key criterion.

The author reproduced the S-38 removed-key test against partial production: the current decoder retained `{svc-0}` in `stable_announced`, while the approved future view has no such field. That is an honest RED on R2-2. Existing tests that construct or read the soon-deleted field and method would fail compilation after the crafter removes them. This remediation updates test oracles and fixtures to the approved committed-row boundary; it does not declare the partial production implementation GREEN.

## Iteration 2 — liveness-threshold fixture after a committed Stable

The original step 02-04 crafter's broader GREEN run exposed one failure in the existing `service_kind_vm_workloads.rs::vm_liveness_threshold_emits_only_the_existing_liveness_stop`: `first_fail.is_empty()` failed on the first below-threshold liveness row. The author reproduced that failure before the fixture edit. The test first called the production `ServiceLifecycleReconciler::reconcile` and asserted a `FinalizeFailed { Stable }` action, but copied the pre-dispatch `ServiceAllocFact` with `stable_committed=false` into every subsequent liveness evaluation. B1 correctly re-announces Stable whenever that fact still reports no committed row. The test's own sequence, however, says liveness rows follow a Stable commit; D9 starts liveness only after `on_alloc_stable`, which the shim invokes after the Stable row write (`feature-delta.md:647–685`). The fixture's false committed value contradicted its stated precondition.

The DISTILL change is one assignment after the initial Stable action and before the first liveness `ProbeResultRow`: `observed.allocs[&alloc_id].stable_committed = true` (`service_kind_vm_workloads.rs:503–508`). It models the committed row input to the next **pure reconciler evaluation**. It does not call a hook, write a row, change a production API, or invent a seam. The composed S-43 and D9 tests remain responsible for proving the real shim write and hook order; this focused property checks the later liveness threshold given that committed fact.

The initial `FinalizeFailed { Stable }` assertion is retained. Subsequent assertions are unchanged: no action after the first and second failures, a `Pass` resetting the streak, no action through the next two failures, exactly one typed `StopAllocation { Stopped { LivenessProbe } }` at the new streak's threshold, `liveness_last_acted_run == 6`, `Running` state and no restart or finalization (`service_kind_vm_workloads.rs:492–591`). The readiness-flap, startup-Stable and WorkloadLifecycle liveness-restart complements are unchanged. The per-test `/// CONTRACT_SHAPE: bounded-change.` declaration remains. This corrects a contradictory fixture chronology without weakening the threshold or D9 outcome.
