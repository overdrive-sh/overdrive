## Evidence and contract mapping

The proposal responds to genuine *documented interface gaps*, not a newly alleged runtime defect. D11 items 5–8 require a stream error from failed `ObservationStore::alloc_status_rows` reads but also say that D11 adds no public surface (`feature-delta.md:856-866`); ADR-0263 repeats both statements. The existing Service stream returns `Result<Bytes, std::io::Error>` and has no read (`crates/overdrive-control-plane/src/streaming.rs:1032-1113`). The production handler passes that stream to `Body::from_stream` (`handlers.rs:605-659`); the CLI sees a failed HTTP body chunk as `CliError::Transport` (`crates/overdrive-cli/src/commands/deploy.rs:690-706`). The proposed Rust error does not become a new NDJSON or HTTP error variant.

|---|---|---|---|
| Open read: `ObservationStoreError::Unreachable { peer }` | `ServiceStreamError::ObservationRead { source: ObservationStoreError::Unreachable { peer } }` | `build_service_stream` yields one `Err` and ends before arming the progress deadline; `Body::from_stream` propagates a body failure | Complete: peer and cause survive. |
| Open read: `ObservationStoreError::Io(error)` | `ObservationRead { source: ObservationStoreError::Io(error) }` | Same end behavior; the original `io::ErrorKind` and source remain inspectable in-process | Complete. Local redb and task-join failures reach `Io` (`observation_backend.rs:938-960`). |

`ObservationStoreError` is an exhaustive three-variant port error (`observation_store.rs:53-68`); `ServiceStreamError` is an exhaustive two-variant stream error. The proposed mapping covers every declared port error at both reads and the existing emitter error. No `Other`/string-only escape, conversion to absence, retry, or fabricated wire terminal is permitted. The nested `source` is the owner-branchable cause; a diagnostic string is ancillary. The proposed public return signature and `Error + Send + Sync + 'static` bound fit the handler's body boundary. `LineEmission` is justified by the existing fallible `emit_service_line` signature (`streaming.rs:989-996`); the review does not assert that each serialization or in-memory write can fail in normal production.

D14/PR-4 names `AllocationSpec::tcp_service_ports()` and pins the TCP filter's declaration order, but omits the receiver and return type (`feature-delta.md:2389-2404,2594-2597`). The proposed `pub fn tcp_service_ports(&self) -> Vec<NonZeroU16>` pins that cross-crate shape. It returns an owned, ordered TCP-only projection from `declared_listeners`, with duplicates retained and no mutation. This fits the two current production consumers: `action_shim::declared_tcp_listen_ports` converts ports to `ListenPort` (`action_shim/mod.rs:1522-1533`), and `MtlsInterceptWorker::start_shared_allocation` builds a capability set and installs an inbound rule per port (`mtls_intercept_worker.rs:2723,2747-2755`). The existing RED scaffold has this signature (`driver.rs:355-364`), but is not approval evidence. No separate stored TCP field, new port, wire change, or persisted change is needed. The two proposed interface amendments are technically coherent **only as proposals**: D11-E1 explicitly changes D11/ADR-0263's accepted no-new-public-surface clause and D14-A1 pins an accepted model's missing signature. Both require the user's exact approval before incorporation.

## Finding 1 — D14 platform-only input rejection still lacks a typed semantic contract

**Blocking `SPECIFICATION_AMBIGUITY` in the downstream F-03 handoff.** `feature-delta.md:2382-2388` requires `GuestListeners` to be the sole startup descriptor of a Service, prohibits operator TOML spelling, and says `from_submit` and the parser reject other placements. The proposal calls this accepted-contract test coverage only (`contract-remediation.md:75-76`), but the accepted prose does not identify the semantic validation-error set, exact public error variants/payloads, or the mapping at each ingress. DISTILL cannot author honest typed rejection assertions, and a crafter cannot select an error representation, under `AGENTS.md`'s typed-error gate.

This is a document-contract gap, not a new production-defect claim. The actual current ingress makes the missing mapping material: `Service::from_submit` calls `validate_probe_mechanics` for all three role vectors and returns the broad `AggregateError::Validation { field, message }` for validation failures (`aggregate/mod.rs:412-447,605-620`); `ProbeMechanic::GuestListeners` currently passes its value validator (`probe_descriptor.rs:79-112`). The handler flattens aggregate validation into `ControlPlaneError::Validation` with a string message (`handlers.rs:294-311`). The TOML mechanic parser currently falls through to `ParseError::UnknownProbeType { probe_idx, found }` for a `guest_listeners` token (`workload_spec.rs:204-213,1261-1296`), even though that mechanic is known to the API. Job/Schedule TOML probe declarations take `ParseError::ProbesNotAllowedOnKind` (`workload_spec.rs:265-283,827-839`); raw Job/Schedule payloads have no probe field in their `deny_unknown_fields` wire shapes (`api/submit.rs:39-65,115-135`, `aggregate/mod.rs:811-830`). Those structural rejections are not a call to `Service::from_submit`.

| Required rejection case | Exact typed representation and mapping in accepted DESIGN | Review disposition |
|---|---|---|
| Raw Service `GuestListeners` in readiness or liveness | Unspecified beyond “reject”; broad `Validation` allows reason only in a message | DESIGN must pin. |
| Raw Service with `GuestListeners` plus another startup descriptor | Unspecified beyond “sole”; neither variant/payload nor precedence against the general probe-count rule is pinned | DESIGN must pin. |
| Operator TOML spelling `GuestListeners` in any role | Unspecified whether the known-but-platform-only mechanic uses an existing typed `ParseError` or a new typed distinction; current `UnknownProbeType` is an implementation fact, not approval | DESIGN must pin. |
| Raw non-Service payload carrying probe fields | The current kind-discriminated, unknown-field-denying wire shape rejects before a Service constructor; the proposal's phrase “raw API ... non-Service” does not name that boundary | DESIGN must state the intended structural rejection and its observable HTTP/typed representation, or correct the F-03 scenario scope. |

**Required disposition:** the architect must pin the exact semantic rejection set, representation and payloads at the applicable aggregate/parser/wire boundary, mapping and caller-visible behavior, including which current structural error is sufficient. The reviewer does not prescribe new variants. The architect should then revise the F-03 handoff so DISTILL writes scenarios against those pinned outcomes. Do not use arbitrary `Validation.message` text or a generic carrier as the semantic taxonomy. No production or test change is authorized by this finding.
