## Necessity, scope and policy

The current roadmap's 05-06 criterion already calls for the **new** guest programs to load and pass `verifier-regress`; the repository Tier-4 rule already pins the 500,000 new-program bound. The proposed text distinguishes the three required receipts: guest-kit/BPF build, two native D13 real-boot outcomes, and a completed quantitative verifier run for the existing dataplane corpus plus the three named guest programs. This does not create a benchmark for V39 or P-12, alter D13's three-program shape or cgroup ownership, change a runtime API, or waive any accepted outcome. The new-program limit is **stronger** than the gate's general 900,000 ceiling-proximity failure. The gate's current executable `GatePolicy::default` tests growth only when both `>5%` and `>50` instructions (`verifier_budget.rs:102-133,219-256`); the older `bpf.md` “+20%” prose does not authorize relaxing that current rule. First landing has no historical guest baseline, so the measured Linux 7.0 counts become reviewed initial entries under the existing append-only record convention. Later counts use the existing growth policy. Counts from other kernel releases are not compared to the Linux 7.0 initial baseline; the kernel matrix still requires program load on its members.

This review is limited to the three **new** D13 hook programs. The general Tier-4 rule speaks of the full BPF corpus, while the pre-existing verifier binary has historically omitted other guest-object programs. This bounded 05-06 clarification does not claim that older corpus-wide coverage is now complete or approve excluding those other programs from the repository-wide rule. It requires the program coverage needed for this step's accepted new-hook criterion and preserves the existing dataplane measurements. Any broader historical corpus repair is separate from this adjudication.

The canonical exclusive Metal invocation remains `cargo xtask metal run --exclusive -- cargo run -p overdrive-dataplane --bin verifier_regress --`. The active external ordinary holder of the maintenance lock is legitimate; the recorded `maintenance_timeout` before START supplies no verifier evidence. The gate must be run when admission is available and must retain actual counts, kernel release, object identity, policy decision and terminal status. No lock bypass, invented result, or new public command is needed. If implementation truly requires a new public interface, it must surface that exact gap before adding one; private harness choices do not trigger a DESIGN blocker.
