## Blocking findings

### F-01 — D16 omits a persisted `Stable` witness carrier and defers exact envelope shapes

**Severity: blocking specification ambiguity.** D16 removes `ProbeWitness.inferred`, a layout change inside `TerminalCondition::Stable`. Its carrier table names the allocation-status envelope but omits `AllocLifecycleOccurrenceRowEnvelope` ([feature delta, D16](../feature-delta.md), lines 2663–2685). The current `AllocLifecycleOccurrenceRowV1.terminal: Option<TerminalCondition>` is a second persisted carrier (`crates/overdrive-core/src/traits/observation_store.rs:475–502`), and `LocalObservationStore::write_alloc_lifecycle_transaction` archives it into redb (`crates/overdrive-store-local/src/observation_backend.rs:650–653`). The omission is mechanically relevant: a changed nested witness layout cannot be written under the old occurrence-row version while preserving the rule that historical archived bytes retain their meaning. ADR-0271 says *each* archived carrier follows the versioned-envelope procedure, while its consequence claims five carriers; D16's table accounts for only four archived carriers.

The same D16 paragraph explicitly leaves “exact envelope names and versions” for the crafter to confirm. It names `ServiceV2` but does not pin the outer `WorkloadIntentEnvelope` payload/variant shape, and says only “new version” for the allocation-status envelope. These are persisted and public payload contracts, not private implementation structure. `.claude/rules/development.md` § Version-bump procedure requires a new variant, latest alias, migration, and historical fixture in the same commit. The designer must enumerate **every** archived carrier of `ProbeDescriptor`, `ProbeResultRow` and `ProbeWitness`, pin the exact outer variants and latest payload shapes and old-to-new projections, and reconcile the D16 table, ADR-0271 and roadmap 05-04/05-05. Preserve historical fixtures and the accepted single cut; do not let a crafter choose an unapproved schema.

This is a normative layout and coverage contradiction supported by the current type and persistence boundary. It does not depend on a speculative runtime schedule or claim that current production already has a D16 defect (D16 is unimplemented).

### F-03 — D15 promises the wrong give-up terminal for a clean exit before startup

**Severity: blocking contract contradiction.** D15's RCA-A outcome table says a Service that exits **“1 (or 0)”** without opening a declared listener gives up as `EarlyExit` ([feature delta](../feature-delta.md), lines 2640–2646). The accepted D6 predicate requires a `Failed` row with `WorkloadCrashedImmediately` or `VmOutOfMemory`, and explicitly excludes a clean `Terminated` exit ([feature delta](../feature-delta.md), D6 item 3 and D6.b; [ADR-0258](../../../product/architecture/adr-0258-the-restart-authority-names-a-pre-startup-crash-loop-at-give-up.md), lines 153–155). The S-15 oracle likewise sends `Terminated` + `Stopped { Process }` to `BackoffExhausted` ([feature delta](../feature-delta.md), S-15). D15 is therefore internally inconsistent about an operator-visible terminal. The designer must reconcile the D15 outcome with the already approved D6 classification and its explicit clean-exit exclusion, or surface an exact changed outcome to the user. Neither a reviewer nor a crafter may silently widen D6's crash classes or weaken D15's asserted outcome.

This is a document-contract contradiction, not a request for a speculative new failure mode: the current exit-observer classification and D6's accepted predicate already distinguish exit 0 from a crash.

### Remaining F-01 blocker — V1 Service intent can contain `GuestListeners`

D16-S1 says historical `ProbeMechanicV1` has **only** `Tcp` and `Http`, and its V1→V2 conversion can never produce `GuestListeners` ([full-review-remediation.md](full-review-remediation.md), Decision 1, historical nested shapes). That premise is contradicted by the current V1 archive boundary and the already approved D14 raw-Service admission shape. `ProbeMechanic` already has fieldless `GuestListeners` at rkyv tag 2 and `validate()` accepts it (`crates/overdrive-core/src/aggregate/probe_descriptor.rs:60–76,87–113`). `Service::from_submit` passes startup descriptors through that validator and the dial-bearing count check, then returns the descriptor unchanged apart from its index (`crates/overdrive-core/src/aggregate/mod.rs:412–474,606–616`). The production `submit_workload` handler's Service arm wraps that result in `WorkloadIntent::Service`, archives it as today's `WorkloadIntentEnvelope::V1`, and calls `IntentStore::put_if_absent` **before** any reconciler/probe task runs (`crates/overdrive-control-plane/src/handlers.rs:295–341,475`). The approved D14-E2 contract likewise expressly admits a correctly role-tagged, sole `GuestListeners` descriptor from raw JSON; it does not impose an origin token.

Thus the current V1 archived Service payload can contain tag 2. A proposed historical V1 enum with only two variants would not represent that existing byte sequence, contradicting D16-S1's own rule that historical V1 payloads and fixtures keep their meaning. This is a static incompatibility at a real public admission and persistence boundary, **not** a newly hypothesized timing/concurrency defect or a request for a test seam. It is not resolved by the old V1 fixture, which has no probe. DESIGN must pin the historical tag-2 representation and V1→V2 projection, or provide production evidence that a V1 Service with `GuestListeners` cannot reach persistence. Add a historical V1 fixture that carries the supported variant if the former is chosen. Do not drop that possible V1 input or weaken D14-E2's accepted raw API admission solely to simplify migration. This review does not author the replacement schema.

**Subtractive and scope check.** D16-S1's separate historical nested types are necessary to preserve old rkyv layouts; `AllocLifecycleOccurrenceRowEnvelope` is an existing persisted table, so its version bump is bounded compiler/schema fallout rather than a new storage mechanism. D13-S1 and D17-S1 add no extra port, timer, model, validation lane or broker policy. The D15 correction removes a contradictory claim. The remaining F-01 fix is within the same accepted five-carrier scheme. No new production defect, recovery protocol or architectural alternative was promoted from a speculative trace.
