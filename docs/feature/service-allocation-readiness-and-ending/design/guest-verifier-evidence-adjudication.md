## Smallest exact required gate extension

1. In the existing `cargo verifier-regress` / `cargo run -p overdrive-dataplane --bin verifier_regress` gate, measure `bpf_prog_info.verified_insns` through aya's `ProgramInfo::verified_instruction_count` for **guest-object** `listen_tcp`, `post_bind4` and `post_bind6`, identifying the object as well as the program so a dataplane count cannot be substituted. A missing program, failed guest-object load, absent count, or failed gate is a failure. The current private `measure` path handles only dataplane `Xdp` and `CgroupSockAddr` program types (`verifier_regress.rs:193-265`); the guest additions require `SockOps` for `listen_tcp` and `CgroupSock` for `post_bind4`/`post_bind6`, with the same `ProgramInfo` count query. The private harness's load setup, file layout and function signatures belong to DISTILL/DELIVER; this clarification adds no public or cross-crate API.
2. On the pinned Linux 7.0 gating kernel, each of those **three new programs** must be at or below **500,000 verified instructions**, the existing `.claude/rules/development.md:2336-2339` Tier-4 limit of 50% of the privileged one-million ceiling. Record each measured integer, kernel release, object identity and initial reviewed baseline under the existing append-only verifier-budget record convention. The existing kernel-matrix invocations must also load these three guest programs; the pinned Linux 7.0 count is the quantitative merge signal, and counts from different kernels are not compared as if they shared one baseline (`.claude/rules/testing.md:1930-1939`; `.claude/rules/bpf.md:229-242`). A new program has no prior `main` count to compare on its first landing; after the initial baseline, the gate applies its existing per-program growth policy to later changes. The current gate's `GatePolicy::default` is growth **>5% and >50 instructions together** plus ceiling-proximity failure at **≥900,000** (`crates/overdrive-dataplane/bin/verifier_budget.rs:102-133,219-256`); the stronger 500,000 new-program limit still applies. `.claude/rules/bpf.md:214-220` delegates gate mechanics to `testing.md`; its older “+20%” prose is not a reason to loosen the executable policy. No initial baseline value is invented from V37's superseded merged arm.
3. Keep the existing dataplane corpus and canonical exclusive invocation. The 05-06 review needs **separate** receipts for: (a) guest-kit/BPF build, (b) both D13 real-boot tests proving guest load/attach and behavior, and (c) the completed Tier-4 measurement output showing the existing dataplane corpus **and** the three named guest-object counts within their bounds. If the existing gate cannot include the guest object without a new public command or policy, stop at that exact interface need and seek user approval before expanding it; a private harness implementation choice is not a DESIGN blocker.

The requirement follows the already accepted 05-06 wording plus `.claude/rules/testing.md:1930-1964` (verifier complexity for the BPF corpus) and `.claude/rules/development.md:2323-2339` (new-program Tier-4 bound). It does not infer a fresh performance target from V37, widen D13 behavior, or declare the pending exclusive gate passed. The live external Metal shared-lock holder is a resource wait, not permission to bypass the canonical exclusive gate or interrupt another run.
